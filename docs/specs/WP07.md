Later work packages (WP08, WP09, WP10) add their own modules to this crate. They get
**additive-only** rights to `src/lib.rs` (new `pub mod` / `pub use` lines) and `Cargo.toml`
(new dependencies). Each of them must leave the frozen API of this WP unchanged (see "Frozen API").

## Scope

- **`model`**: the client-side plan tree (`PlanTree`, `PlanDirectory`, `PlanLeaf`, `PlanNode`)
  that replaces the transient state of `J/dto/sync/*` and the transient fields of the domain sync
  tree. Also the download/delete work items (`DownloadTask`, `DeleteTask`) that WP08 produces and
  WP09/WP10 consume.
- **`events`**: one `SyncEvent` enum (Clone + Send + Sync) replacing every `J/controller/Observer*`
  callback used by check, download, uncompress and upload. Also `EventSender`, which can feed a
  std or tokio channel, a closure (egui repaint), or nothing, plus two small throttling helpers.
- **`options`**: `SyncOptions`, built from a WP03 `Repository` and an optional event (modset):
  destination folder resolution, auto-discover, exact match, connection count, speed limit and
  error limit.
- **`remote`**: fetching repository metadata through `a3s_transport::Transport`. This covers
  `checkRepository` (all five `.a3s` files with Java's partial-failure semantics),
  `importAutoConfig`, the HTTP partial-transfer probe, a bounded multi-repository check (≤ 4
  concurrent), and `RemoteFile` path formatting.
- **`error`**: typed `RemoteError` (replaces `J/exception/remote/*` and the IOException messages
  built by `ConnectionExceptionFactory`). It implements `a3s_error::UserFacing`.
- **`status`**: repository status from `RepositoryService` (`updateRepository` and
  `determineRepositorySyncStatus`), the favorite-server merge, revision handling
  (`updateRepositoryRevision`, `resetRepositoryRevision`), and the `TaskCheckRepositories`
  notification decision as pure functions.
- Port `T/ui/main/tasks/TaskCheckRepositoriesTest`.

## Behaviour contract

### Remote metadata (`remote`)

- B1. A check uses **one** connection (`ConnectionService(protocol)` → `init(1, …)`,
  `service/ConnectionService.java:66-68`). The number of pool connections is `0 → 1`
  (`:59-64`). Unknown protocol types fail with `"Unknown or unsupported protocol."` (`:85-86`).
  Rust: `Transport::connect` errors with `InvalidProtocol` for SOCKS/A3S. Map that to
  `RemoteError::Connect` with kind `InvalidInput`.
- B2. `check_repository` fetches, in this order: `.a3s/serverinfo`, `.a3s/sync`,
  `.a3s/changelogs`, `.a3s/events`, `.a3s/autoconfig` (`service/ConnectionService.java:188-224`).
  Cancellation is checked before each file (`:189,194,214,218,222`).
- B3. Partial-failure semantics (wire-invisible, but they drive the status): every getter stores
  its result in a `finally` block, so a failing file is stored as **null**
  (`:100-106, 116-122, 132-138, 148-154, 164-170`). The exception aborts the remaining fetches, so
  later files keep their **previous** values. Rust: `check_repository(&mut RemoteMetadata)` mutates
  in place. A successful file replaces its field, the failing file's field becomes `None`, later
  fields are left untouched, and the error is returned. Cancellation is reported as
  `Err(RemoteError::Cancelled)`, after setting the file in flight (if any) to `None`.
- B4. Before fetching `sync`, Java logs whether the server info changed (`:203-210`): revision,
  `numberOfFiles` or `totalFilesSize` differ (`:227-238`). The sync tree is **always** refetched
  (`:195-202`). Rust: `server_info_changed(prev, cur)` is public. Log through `tracing::info!`
  with the Java texts `"Repository metadata changed (revision {a} -> {b}), refreshing repository
  layout."` and `"Refreshing repository layout from the current server sync file."`.
- B5. Other log lines (`tracing::info!`): `"Checking repository: {name} on url: {host_url}"`
  (`:182-184`; `prompt + hostname + ":" + port + remotePath` equals WP03 `host_url`) and
  `"Downloading file: /.a3s/{file} from repository: {name}"`
  (`dao/connection/AbstractConnexionDAO.java:153-154`).
- B6. A metadata file is fetched in memory and decoded with `a3s_repo_files::decode_a3s::<T>`.
  Java writes it to `TEMP_FOLDER_PATH/<repo>/<file>` and deletes the folder afterwards
  (`AbstractConnexionDAO.java:144-174`). Rust needs no temp files. Decode `.a3s/sync` in
  `tokio::task::spawn_blocking` (it can be several MB decompressed). Decode the other files
  inline.
- B7. HTTP headers, Basic auth and redirects are already implemented by `a3s_transport::http`
  (`HttpDAO.java:144-168`). This WP adds nothing there.
- B8. `import_autoconfig(protocol, options, ctx)` fetches the relative path `autoconfig`. The
  protocol's URL already ends in `/.a3s`: WP05's URL parser strips `/autoconfig`, see
  `dao/connection/AutoConfigURLAccessMethods.java:158-162`. Java builds `RemoteFile(name, "")`
  (`AbstractConnexionDAO.java:176-201`) and logs `"Importing autoconfig from url: {host_url}/autoconfig"`
  (`service/ConnectionService.java:244-246`). The result is the decoded `AutoConfig`. Java returns
  `null` when the file is absent after download (`:250-253`), and the dialog turns that into
  `RemoteAutoconfigFileNotFoundException` (`ui/repository/dialogs/connection/DescriptionPanel.java:286-316`).
  Rust: transport `NotFound` → `RemoteError::Fetch` with kind `NotFound` (B13). Setting the
  timeouts to `"0"` (`DescriptionPanel.java:261-262`) is the caller's business (WP29, see Q4).
- B9. Partial-transfer probe (`HttpDAO.java:431-446`): `GET .a3s/sync` with `Range: bytes=0-1`
  (`DataRange(0,1)` → `"0-1"`). A 206 means supported. Any other success status means
  unsupported. Errors propagate (`ConnectionService.java:256-266`). FTP, SFTP and WebDAV return
  `null`, i.e. "supported" (`FtpDAO.java:728-731`, `SftpDAO.java:346-348`,
  `WebdavDAO.java:410-413`), but their `getFileCompletion` always returns 0. Rust:
  `probe_partial_transfer` returns `NotApplicable` for non-HTTP transports (deviation DV4). For
  HTTP(S) it calls `Transport::fetch_range(".a3s/sync", 0..2)`: `Ok` → `Supported`,
  `Err(Unsupported{..})` → `Unsupported`, `Err(Incomplete{..})` → `Supported` (the status was 206,
  Java looks at the status only), any other error → `Err`. Java returns the response headers as
  text for `HeaderErrorDialog`. Rust has no public transport API for headers (Q2).
- B10. The probe's caller decides whether to probe at all: Java skips it when
  `serverInfo.noPartialFileTransfer` is set (`ConnectionService.java:286-298`, WP08). The client
  repository setting `usePartialFileTransfer` is an **admin build** setting
  (`dao/repository/RepositoryBuildProcessor.java:157`) and is not a sync option.
- B11. After a check, `FilesCheckProcessor` requires `sync` and `serverinfo`. It also requires
  `events` when an event is selected (`service/synchronization/FilesCheckProcessor.java:41-54`).
  The errors are, in this order: `RemoteSyncFileNotFoundException`,
  `RemoteServerInfoFileNotFoundException`, `RemoteEventsFileNotFoundException`. Rust:
  `RemoteMetadata::require_for_sync(event_name)` returns `RemoteError::MissingMetadata(file)` in
  the same order. The Java events check never fires, because `RepositoryService.getEvents` never
  returns null (`RepositoryService.java:866-892`). Rust enforces it (deviation DV5).
- B12. `RemoteMetadata::events_list()` deduplicates events by exact name, keeping the first
  (`RepositoryService.java:874-886`). It returns an empty vec when `events` is `None`.
- B13. Error messages (local-only, Java parity). `core` depends on the transport and the
  operation:
  - Connect (FTP/FTPS): `"Failed to connect to the FTP server on url: {host_url}"`
    (`FtpDAO.java:204`). SFTP: `"Failed to connect to the SFTP server on url: {host_url}"`
    (`SftpDAO.java:182-183`). HTTP/WebDAV: `"Failed to connect to the HTTP server on url: {host_url}"`
    (`HttpDAO.java:208`, `WebdavDAO.java:213`).
  - Fetch on HTTP/WebDAV: `"Failed to connect to the HTTP server on url: {host_url}/{relative}"`
    (`HttpDAO.java:208-209`: host URL + `RemoteFile.getRelativeFilePath()`).
  - Fetch on FTP/SFTP: `NotFound` uses the connect core (Java detects missing files during
    `connect`, `FtpDAO.java:186-198`). Every other error uses `"Failed to retrieve file: /{relative}"`
    (`FtpDAO.java:408`, `SftpDAO.java:244`).
  - The message is `a3s_error::messages::connection(core, kind, detail)`. `detail` is
    `"Remote file not found: /{relative}"` for `NotFound` (`HttpDAO.java:176`, `FtpDAO.java:196`).
    It is `a3s_error::messages::WRONG_LOGIN_PASSWORD` for `Unauthorized` (`HttpDAO.java:174`,
    `FtpDAO.java:164`). For `Incomplete{expected, actual}` it is
    `a3s_error::messages::incomplete_transfer(relative, actual, expected)`, and `connection` then
    returns the detail alone. Otherwise it is the transport error's `Display`.
  - Decode: `"Failed to read file: {file_name}\n{detail}"`, plus `"\nThe file seems to be
    corrupted."` when the cause is `a3s_repo_files::Error::Gzip` or `TooLarge`
    (`dao/A3SFilesAccessor.java:65-74`, `:26`). `file_name` is the bare name (`sync`).
  - Missing metadata: `a3s_error::messages::remote_file_not_found(RemoteA3sFile::…)`. This keeps
    Java's texts exactly, including `"Remote file no found: /.a3s/sync"` and the missing `/` in
    `"Remote file not found: .a3s/serverinfo"` (`exception/remote/*.java:8-9`).
  - Cancelled: `"Cancelled"`; kind `Cancelled`.
- B14. `ErrorKind` mapping for transport errors: `NotFound`→`NotFound`, `Unauthorized`→`Unauthorized`,
  `Timeout`→`Timeout`, `Cancelled`→`Cancelled`, `Incomplete`→`IncompleteTransfer`,
  `InvalidProtocol`→`InvalidInput`, `InsecureTlsRefused` and `Tls`→`TlsValidation`,
  `Unsupported`→`Unsupported`, `Http(e)` with `e.is_connect()`→`ConnectionFailed`,
  `Ftp(ConnectionError)` and `Ssh`→`ConnectionFailed`, `Io(e)`→`ErrorKind::from_io(e)`, and every
  other variant (`HttpStatus`, `InsecureRedirect`, `Sftp`, other `Http`/`Ftp`)→`Io`. A decode
  error→`InvalidData`. `MissingMetadata`→`NotFound`. `RemoteError::is_connection_lost()`
  delegates to `a3s_transport::Error::is_connection_lost` (false for decode and missing-metadata
  errors).
- B15. `RemoteFile` (`dao/connection/RemoteFile.java:1-66`): the constructor rejects nothing in
  Rust (non-optional `String`s). `relative_file_path()`: an empty parent gives `"/" + name`.
  Otherwise one leading and one trailing `/` are stripped from the parent (an empty result
  counts as empty) and the result is `"/" + parent + "/" + name`. A directory gets a trailing
  `"/"` (`:38-65`). `transport_path()` is the same without the leading `/` and without the
  trailing `/`, as passed to `Transport::fetch`. Java's `setFilename`/`setParentDirectoryRelativePath`
  exist only for HTTP redirects, which the transport handles, so they are not ported.
- B16. Multi-repository check (`ui/main/tasks/TaskCheckRepositories.java:45-76`): each repository
  is checked with its own connection. At most `MAX_CONCURRENT_REPOSITORY_CHECKS = 4` checks run
  at once (`:26, 66`), and all of them complete even if some fail (`invokeAll`, `:69`). A failure
  is logged as `"Error when checking repository {name}:\n{message}"` (`:57-58`) and swallowed.
  Rust: `check_repositories(jobs, ctx)` returns one `(name, Result)` per job, in input order.
  `check_error_message(name, &err)` gives the log text. Logs `"Checking repositories..."` /
  `"Checking repositories done."` (`:43, 76`).

### Repository status and revision (`status`)

- B17. `determine_sync_status(local_revision, server_info, changelogs)`
  (`service/RepositoryService.java:1475-1521`, identical to `:347-386`):
  1. `server_info` is `None` → `Indeterminated`.
  2. `local == server.revision` → `Ok`.
  3. `local < server.revision`:
     - `server.repository_content_updated` → `Updated`;
     - else if `changelogs` is `None` → `Indeterminated`;
     - else build a `BTreeMap<i32, bool>` revision → `content_updated`. Insert in list order, so
       a later duplicate revision overwrites an earlier one (`TreeMap.put`, `:362-365`). If the
       map lacks `local` → `Indeterminated`. Else iterate ascending and look at entries with
       `revision > local`: `change` = that entry's value, stop at the first `true`. `change` →
       `Updated`, otherwise `Ok` (`:366-382`).
  4. `local > server.revision` → `Indeterminated`.
- B18. `update_repository(repository, configuration, metadata)` (`RepositoryService.java:256-388`):
  1. If `server_info` is `Some`: `repository.hidden_folder_paths ∪= server_info.hidden_folder_paths`
     (union, never removes, `:262`). If `repository.number_of_client_connections == 0`, set it to
     `server_info.number_of_connections` (`:263-265`).
  2. If `auto_config` is `Some`: `merge_favorite_servers(&mut configuration.favorite_servers,
     &auto_config.favorite_servers, repository.name)` (B19).
  3. Status = B17 with `repository.revision`, `metadata.server_info` and `metadata.changelogs`
     (`:347-386`).

  Returns `RepositoryUpdate { status, repository_changed, configuration_changed }`. Java persists
  nothing here. The caller (WP14/WP21/WP10) persists when a `*_changed` flag is set.
- B19. `merge_favorite_servers(local, remote, repository_name) -> bool` (`:270-345`):
  - Local list empty: append, for each remote server in order, a **new** `FavoriteServer` with
    `name` = remote name, or `repository_name` if that is null or `""`. `ip_address`, `port`,
    `password` and `modset_name` are copied, `repository_name` = the argument and
    `selected = false` (`:277-297`).
  - Otherwise take a **snapshot** of the local list before any change (`:274-275`). For each
    remote server, find the first snapshot server with equal `ip_address` and equal `port`
    (`:301-308`). Servers added during this merge are not in the snapshot, so duplicate remote
    entries are added twice (quirk, kept).
    - Found: `password` = remote password (even `None`). `modset_name` = remote modset only if it
      is `Some` and non-empty. `repository_name` = argument. `name` = `repository_name` if it is
      null or `""` (`:311-324`). Local name, ip and port are kept.
    - Not found: append a new server as in the empty case (`:325-342`).
  - Afterwards call `Configuration::sort_favorite_servers()` (WP03 B20: Java's getter sorts on
    every read). Return whether anything changed.
  - Java compares `remoteServer.getIpAddress().equals(...)` and throws an NPE for a null remote
    ip, which kills the timer task. Rust compares `Option<String>`s (deviation DV3).
- B20. `mark_synced(repository, metadata) -> RepositoryStatus` (`updateStatusOK`,
  `ui/repository/DownloadPanel.java:970-976`; `RepositoryService.java:754-768`): if
  `metadata.server_info` is `Some`, `repository.revision = server_info.revision`. Returns `Ok`
  (even without server info). Java calls it after a **successful check** as well as after a
  download (`DownloadPanel.java:919-933`). That's the caller's choice (WP25/WP26).
- B21. `mark_failed(repository) -> RepositoryStatus` (`updateStatusError`,
  `DownloadPanel.java:978-984`; `RepositoryService.java:746-752`): `repository.revision = -1`.
  Returns `Error`. Java doesn't write the repository here. Rust callers persist it (DV8).
- B22. Notification tracker (`TaskCheckRepositories.java:173-190`):
  `should_notify(name, notify, auto, server_revision)`:
  - `!notify || auto` → `false`;
  - `server_revision == None` → `true`, with no tracking;
  - else, if the tracked revision for `name` equals `server_revision` → `false`;
  - else track `name → server_revision` and return `true`.

  The tracker is in-memory only (`:31-32, 173-176`).
- B23. `decide_check_cycle(repos, tracker)` (`TaskCheckRepositories.java:85-158`), with `repos`
  in configuration order. Each entry has name, notify, auto, status (after B18) and server
  revision:
  - `updated` = names with status `Updated`. For every other repository the tracker
    **forgets** the name (`:89-98`).
  - `auto_update` = the `updated` names with `auto` (`:111-117`).
  - `notify` = the `updated` names for which `should_notify` is `true`, evaluated in order
    (`:138-158`).
  - `console_message()` = `"The following repositories have been updated: "` followed by
    `"\n" + name` for each updated repository, or `None` if there are none (`:100-107`).

  Opening tabs, auto-update, tray and dialogs are WP21/WP25.

### Plan model (`model`)

- B24. `PlanTree::from_sync_tree(&SyncTreeDirectory)` mirrors
  `ObjectDTOtransformer.transformSyncTreeDirectory2DTO` (`service/ObjectDTOtransformer.java:292-341`).
  The root is named `racine`. A leaf copies name, size, compressed size, `updated`, `deleted`,
  `compressed` and `sha1`, with `selected = false`, `optional = false`, `local_sha1 = None`,
  `destination_path = None` and `complete = 0.0`. A directory copies name, `mark_as_addon`,
  `updated`, `deleted` and `hidden`, with `selected = false`, `optional = false` and
  `destination_path = None`. `download_status = Pending` (`dto/sync/SyncTreeLeafDTO.java:136`,
  `SyncTreeDirectoryDTO.java:23`). Child order is directories first, then leaves, each group
  sorted with `compare_ignore_case` (stable; `SyncTreeDirectoryDTO.java:99-117`). Sizes are
  `u64`, and a negative `i64` becomes 0.
- B25. `changed`: a directory is `changed` if any leaf below it has `updated || deleted`. The flag
  propagates to every ancestor including the root (`ObjectDTOtransformer.java:302-308`).
  `from_sync_tree` computes it. `recompute_changed()` resets every directory's flag and
  recomputes it (WP08 calls it after planning, because Java transforms after `checkForAddons`).
  Directory `updated`/`deleted` flags do not set `changed` (Java only looks at leaves).
- B26. Relative paths: `/`-joined names below the root, without a leading `/`. The root's
  relative path is `""` and a child of the root has its bare name (`SyncTreeNodeDTOMethods.java:40-53`).
  `parent_relative_path(path)` is everything before the last `/`, or `""` (`:55-70`). Rust
  computes paths from the tree structure. Java stops climbing at the first ancestor **named**
  `racine`, which truncates paths below a nested folder with that name. Rust does not reproduce
  that bug (DV9).
- B27. Traversal order is pre-order, a directory before its children, and the root is excluded
  (`SyncTreeNodeDTOMethods.java:72-93`). The leaves-only traversal is in the same order
  (`:95-113`).
- B28. `PlanDirectory::display_name()`: `"{name} (optional)"` if optional, else
  `"{name} (hidden)"` if hidden, else `name` (`SyncTreeDirectoryDTO.java:80-89`). For a leaf it
  is `name` (`SyncTreeLeafDTO.java:192-195`).
- B29. `add_child` keeps the B24 order (`SyncTreeDirectoryDTO.java:99-117`). `PlanTree::get` and
  `get_mut` look up by exact relative path, comparing each segment case-sensitively. `""`
  returns the root.
- B30. `local_path()` = `destination_path.join(name)` (`ConnectionService.java:303,505,522`).
  It returns `None` while `destination_path` is unset.
- B31. `PlanLeaf::download_size()` (`FilesSynchronizationManager.java:92-104`): if
  `complete == 0.0`, it is `compressed_size` when compressed and `size` otherwise. Else it is
  `(size as f64 * (100.0 - complete) / 100.0) as u64` (Java casts the `double` to `long`, which
  truncates).
- B32. `DownloadTask::from_node(relative_path, node)` captures what
  `AbstractConnexionDAO.downloadFile(Repository, SyncTreeNodeDTO)` reads
  (`AbstractConnexionDAO.java:240-339`): the destination directory, the remote relative path
  (the tree path, even when auto-discover redirected the local destination; Java uses
  `getParentRelativePath()`, `:272-279`), the kind (directory, or file with size, compressed
  size, compressed, sha1 and complete), and a mutable `status` (Pending/Running/Done; a resume
  depends on `Running`, `:283-293`). It returns `None` when `destination_path` is unset.
  `DeleteTask` holds `relative_path`, `local_path` and `is_directory`
  (`ConnectionService.java:513-531`).

### Options (`options`)

- B33. `resolve_download_location(repository, event_name) -> Option<String>`
  (`RepositoryService.java:681-727`):
  - `event_name` is `Some(e)` and `events_download_location` contains `e`:
    - if that path exists on disk, return it;
    - else replace it with the default location (below) and return that. Java stores `null`
      for a missing default. Rust removes the entry instead (DV10).
  - Otherwise return the default location.
  - Default location: `repository.default_download_location`. If it is set but doesn't exist on
    disk, set it to `None` and return `None` (`:710-727`).
- B34. `SyncOptions::from_repository(&mut repository, event_name)` resolves B33. It fails with
  `SyncOptionsError::DestinationEmpty` (`"Default destination folder is empty."`) for `None` or
  `""`, and with `DestinationMissing(path)` (`"Default destination folder does not exists: {path}"`)
  if the path doesn't exist (`RepositoryService.java:431-439`). The other fields:

### Errors, cancellation, progress

- No retries. Java doesn't retry metadata fetches. A check aborts at the first error (B3).
- Cancellation: `TransferCtx::cancel` is checked before connect, before each file, and inside
  `Transport` reads. `RemoteConnection::connect` races `Transport::connect` against
  `ctx.cancel.cancelled()`. A cancelled check must return within 1 s on the local slow-server
  test (A5).
- `RemoteError` is `Send + Sync + 'static` and implements `std::error::Error` (with `source()`
  chaining to the transport/decode error) and `a3s_error::UserFacing` (B13, B14).
- `EventError` is the cloneable projection `{ kind, message, relative_path }` used inside events.
  `EventError::from_remote(&RemoteError)` fills it.
- Progress: B42 for checks. Every other event is emitted by WP08/09/10/12.

### Concurrency

- Java: one DAO per check, a fixed pool of `max(1, min(4, n))` threads for the periodic check
  (`TaskCheckRepositories.java:66-74`).
- Rust: `check_repositories` uses `futures::stream::iter(..).map(..).buffered(4)`, so the order
  of results is preserved. Each job owns its `RemoteConnection`, and the shared `TransferCtx`
  cancels all of them. All futures are `Send`.
- `EventSender` is `Clone + Send + Sync`. `emit` never blocks: unbounded channels, and a closure
  that must not block. A send to a dropped receiver is ignored.
- `RemoteMetadata` holds `Arc`s, so snapshots for the UI cost O(1).
- `RemoteConnection` is `Send` but not `Sync` (it owns a `Transport`).

## Acceptance tests

Local-server tests serve `tests/fixtures/java_repos/wog_ftp/*` from an in-process axum server at
`/repo/.a3s/<file>` on `127.0.0.1:0`. The protocol is
`Protocol::new(Http, "127.0.0.1/repo", port, "anonymous", "", false)`.

- A1 (unit, `src/model.rs`) `from_sync_tree` on the WOG fixture: `leaf_count` equals
  `SyncTreeDirectory::leaf_count`. The walk visits every node pre-order with correct relative
  paths (compare against `SyncTreeDirectory::walk`). Directories come before leaves in every
  directory. All flags take their B24 defaults. A hand-built tree with an updated leaf at
  `@a/addons/x.pbo` sets `changed` on `addons`, `@a` and the root, and not on siblings.
  `recompute_changed` clears and recomputes. Covers B24, B25, B27.
- A2 (unit) Paths and lookups: `get("@a/addons/x.pbo")`, `get("missing")`, `directory_mut("")` is
  the root, `parent_relative_path` and `file_name` for `""`, `"a"` and `"a/b/c"`, a nested
  `racine` folder (`racine/x` under the root gives the relative path `"…/racine/x"`). `add_child`
  ordering (`"_x" < "a"`, `"B" == "b"` stays stable). `display_name` optional/hidden precedence.
  `set_selected_recursive`. Covers B26-B29.
- A3 (unit) `download_size` table: complete 0 uncompressed/compressed, complete 37.5 on size 1000
  gives 625, complete 100 gives 0. `DownloadTask::from_node` for a leaf, a directory and a node
  without destination (`None`). `local_path`. Covers B30-B32.
- A4 (local server) `check_repository` into an empty `RemoteMetadata`: all five fields are `Some`
  and decode equal to `a3s_repo_files::decode_a3s` of the fixture files. Events are
  `Phase(CheckingRepository)` followed by 5 × `MetadataFetched`, in B2 order, with byte counts
  equal to the fixture sizes. The server log shows requests in B2 order with
  `User-Agent: ArmA3Sync`. Covers B2, B5, B6, B42.
- A5 (local server, failures)

    `changelogs` are refreshed, `events` is `None`, `auto_config` is the previous value. The
    error has kind `NotFound` and message
    `"Failed to connect to the HTTP server on url: http://127.0.0.1:{port}/repo/.a3s/events\nRemote file not found: /.a3s/events"`.

  - (c) A corrupt gzip body for `sync` → `Decode` with kind `InvalidData`; the message starts

  `Range: bytes=0-1`. Covers B9.
- A7 (local server) `import_autoconfig` with the protocol URL `127.0.0.1/repo/.a3s` fetches
  `/repo/.a3s/autoconfig` and equals the fixture decode. 404 → kind `NotFound`. Covers B8.
