## Scope

- **`event_filter`**: port of `service/EventExtractor` on the WP07 `PlanTree` (keep only the
  addons/userconfig folders of a selected event; set `optional`).
- **`plan`**: port of `RepositoryService.checkForAddons` and its helpers: destination paths
  (default folder + auto-discover through a caller-supplied addon lookup), local SHA-1 with the
  `a3s_hash::Sha1Cache` (port of `RepositorySHA1Processor` in local mode), new/updated detection,
  hidden folders, extra local files to delete (exact match), `changed` recomputation. One blocking
  entry point `plan_repository`, plus each step as a public function for tests and the UI.
- **`plan::summary`**: port of `FilesSynchronizationManager` (selection totals, download size,
  ordered download/delete task lists, userconfig detection, resume helpers, report totals).
- **`completion`**: port of `ConnectionService.determineFilesCompletion`, `FilesCompletionProcessor`,
  `ConnectionCompletionProcessor`, `HttpDAO.getFileCompletion` and jazsync `FileMaker.matchControl`:
  per-leaf `complete` percentage from the remote `.zsync` file and
  `a3s_zsync::match_blocks`, with K concurrent HTTP workers.
- Progress/phase events through the WP07 `EventSender`.
- No Java unit test covers this scope (checked `src/test/java/fr/soe/a3s/**`, 14 files); the
  acceptance tests below are new.

## Behaviour contract

Notation: "local path" of a node = `destination_path.join(name)` (WP07 B30). Paths in the plan are
WP07 relative paths (structural, `/`-joined, root excluded).

### Entry point (`plan::plan_repository`)

- B1. Preconditions, in Java order (`service/RepositoryService.java:421-441`):
  1. `metadata.sync` is `None` → `PlanError::SyncMissing { repository }` with message
     `"File /.a3s/sync not found on repository: {repository}"` (`exception/repository/SyncFileNotFoundException.java`).
  2. `options.event_name` is `Some` and `metadata.events` is `None` → `PlanError::EventsMissing`
     with `"File /.a3s/events not found on repository: {repository}"` (`:429-431`,
     `exception/repository/EventsFileNotFoundException.java`).
  3. `options.destination` is empty → `PlanError::Options(SyncOptionsError::DestinationEmpty)`;
     does not exist on disk → `PlanError::Options(SyncOptionsError::DestinationMissing(path))`
     (`:435-441`; same texts as WP07 B34). `SyncOptions::from_repository` already checked this;
     the plan re-checks because the folder may vanish between the two calls.
- B2. Steps, in this order (`:443-474`), on a fresh `PlanTree::from_sync_tree(metadata.sync)`
  (WP07 B24/B25):
  1. event filter (B4-B11) when `options.event_name` is `Some`;
  2. destinations (B12-B14);
  3. local SHA-1 (B15-B20);
  4. new/updated flags (B21-B22);
  5. hidden flags (B23-B25);
  6. extra local files (B26-B31);
  7. `tree.recompute_changed()` (WP07 B25; Java computes `changed` during the DTO transform that
     follows, `:470-474`, `service/ObjectDTOtransformer.java:302-308`).
  Emits `SyncEvent::Phase(Phase::CheckingFiles)` once before step 1 (the UI label
  `"Checking files..."` is set at this point, `ui/repository/workers/AddonsChecker.java:119`).
  Returns the tree. `plan_repository` is **blocking** (file system + rayon); async callers run it
  in `tokio::task::spawn_blocking`.
- B3. The remote `SyncTreeDirectory` is never mutated. Java mutates `repository.getSync()` in
  place (event re-parenting, added deleted nodes, transient fields) and relies on the next
  `checkRepository` re-download; Rust's `from_sync_tree` copy makes this moot (DV-P2).
  The plan never touches a node's `deleted` flag as decoded from `.a3s/sync` (Java builds always
  write `false`), nor the root's flags other than `changed`.

### Event filter (`event_filter`)

- B4. `find_event(events, name)` returns the **last** event whose `name` equals `name` exactly
  (case-sensitive): the Java loop has no `break` (`service/EventExtractor.java:30-35`). Note that
  WP07 `events_list()` keeps the first duplicate for display; the filter deliberately differs
  (quirk kept).
- B5. `filter(tree, events, event_name)`: if `events` is `None` or `event_name` is `None`, return
  the tree unchanged (`:27, 48`). Otherwise build a **new root** (`racine`, default flags) and fill
  it from the event's `userconfig_folder_names` first, then `addon_names` (`:37-45`). If the event
  is not found, both maps are empty and Java returns an **empty root** (see Q2; proposed:
  `PlanError::EventNotFound`, DV-P9). An event that exists but has both maps empty gives an empty
  root (kept).
- B6. Userconfig (`:93-119`), only when `userconfig_folder_names` is non-empty: take the **first**
  root child that is a directory whose name, lowercased, equals `"userconfig"` (`:99-105`). If
  found, add a **new** directory with the same name and default flags (`mark_as_addon = false`)
  to the new root (`:107-110`), then **move** into it every child **directory** of the old
  userconfig folder whose name is a key of `userconfig_folder_names` (exact, case-sensitive),
  setting its `optional` to the map value (`:111-117`). Leaves of the old userconfig folder are
  dropped. The new userconfig folder is added even if no child matches.
- B7. Addons (`:51-74`), only when `addon_names` is non-empty, iterating the old root's children
  in tree order, directories only (leaves anywhere outside moved addon folders are dropped):
  - directory with `mark_as_addon` and name a key of `addon_names` (exact, case-sensitive): move
    it (with its whole subtree, all flags preserved) into the new parent and set `optional`
    (`:57-61`);
  - directory **without** `mark_as_addon`: run `seek` (B8); if it found something, add a **new**
    directory with the same name and default flags to the new parent and recurse with
    (old directory, new directory) (`:62-71`);
  - directory with `mark_as_addon` whose name is not in `addon_names`: dropped, not descended.
- B8. `seek(dir)` (`:76-91`) returns true if any descendant directory has `mark_as_addon` and a
  name in `addon_names`. It **does** descend into addon folders that are not in the map (the
  `else` branch at `:86-88` covers both non-addon and unmatched addon directories). Quirk kept:
  an addon listed in the event but nested inside an unlisted addon folder makes `seek` true while
  B7 never moves it, so an **empty** synthesized directory remains in the filtered tree.
  (Java's `seek` also sets `optional` on nodes it finds; that has no visible effect because B7
  sets it again on the nodes it moves.)
- B9. Children are inserted with `PlanDirectory::add_child` (WP07 B29 order), matching Java's
  `addTreeNode` re-sort (`domain/repository/SyncTreeDirectory.java:31-49`).
- B10. If B7 synthesizes a directory whose name equals an existing child of the new parent (only
  possible for `userconfig` when the old userconfig folder contains a listed addon folder), Java
  creates a duplicate sibling. Proposed: merge into the existing directory (DV-P10, Q3).
- B11. Relative paths of kept nodes are unchanged by the filter (ancestors are re-created with
  the same names), so the remote paths used by completion and download stay valid.

### Destinations (`plan::assign_destinations`)

- B12. Pre-order over all non-root nodes (`:477-511`; order from
  `domain/repository/SyncTreeNodeMethods.java:26-46`). The root's `destination_path` stays `None`
  (`:484-486`).
- B13. Directory `d` with parent `p` (`:487-499`):
  - `p` is the root (its `destination_path` is `None`) → `d.destination_path = options.destination`
    (the configured path as given, not absolutized);
  - otherwise → `absolute(p.destination_path.join(p.name))` (Java
    `new File(path + "/" + parentName).getAbsolutePath()`; Rust `std::path::absolute`, no symlink
    resolution);
  - then, if `auto_discover && d.mark_as_addon` and `addons.addon_parent_dir(&d.name)` is `Some(dir)`
    → `d.destination_path = dir` (`:494-499`). This applies at **any depth**, not only to root
    children. The lookup key is `d.name.to_lowercase()` (`dao/AddonDAO.java:14`,
    `service/RepositoryService.java:495`); `Addon.path` is the folder **containing** the addon
    folder (`service/AddonService.java:262, 331`).
- B14. Leaf `l` with parent `p` (`:501-508`): `p` is the root → `options.destination`; otherwise
  `absolute(p.destination_path.join(p.name))`. A leaf below an auto-discovered addon folder thus
  lands in `<addon parent>/<addon>/...`.

### Local SHA-1 (`plan::compute_local_sha1`)

- B15. Cache pruning first: remove every cache entry whose path does not exist
  (`Path::exists`, follows symlinks) — the **whole** cache, not only paths of this tree
  (`dao/repository/RepositorySHA1Processor.java:54-67`).
- B16. For each leaf in pre-order with `destination_path` `Some` (`:106-107`): `path =
  absolute(local_path)`. If `path.exists()` is false, skip (`local_sha1` stays `None`, `:110`).
  Otherwise read `mtime = a3s_hash::modified_millis(path)` (on error treat as a miss). A cache hit
  is `cache.get(path, mtime)` → `local_sha1 = Some(cached)` without counting it (`:114-127,
  157-164`). A miss is queued (`:129-156`).
- B17. Hash the queued paths with `a3s_hash::hash_files` (≤ `min(8, cpus)` threads, `:39, 83-85`;
  empty file → `"0"`). Successful results set `local_sha1` and are inserted in the cache
  (`hash_files` does both for the cache; `:145, 97`).
- B18. Progress: `PercentCounter::new(queued.len())` (WP07 B41); each **successful** hash
  increments it from the `on_done` callback (behind a `parking_lot::Mutex`), and each `Some(p)`
  emits `SyncEvent::Progress { phase: Phase::CheckingFiles, percent: p }` (`:170-177`). Cache
  hits emit nothing. Zero misses → no `Progress` event.
- B19. Errors: hashing continues for the other files; then the **first error in input order**
  is returned as `PlanError::Hash { path, source }` with message `"{path} ({source})"` (mirrors
  Java's `FileNotFoundException` text style), kind `ErrorKind::from_io` (`:146-151, 99-101`). The
  successful entries stay in the cache (`:97`). A leaf whose local path is a **directory** fails
  this way (Java `FileInputStream` on a directory throws), aborting the plan (quirk kept, Q9).
- B20. Cancellation: `cancel: &CancellationToken` is bridged to the `AtomicBool` that
  `hash_files` checks per file: set the flag from `on_done` when `cancel.is_cancelled()`, and
  check the token before hashing and after it. Any `io::ErrorKind::Interrupted` result or a
  cancelled token → `PlanError::Cancelled` (DV-P3; Java silently skips the remaining files and
  marks them "updated", `:134, 185-187`). Latency is bounded by the largest file each worker is
  hashing.

### New/updated (`plan::mark_updated`)

- B21. For every non-root directory: `updated = !local_path.exists()` (`:516-523`; a regular
  file with that name counts as existing).
- B22. For every leaf: `updated = !local_path.exists() || local_sha1.is_none() ||
  local_sha1 != sha1` (`:524-536`). A `None` remote `sha1` is therefore always updated. Empty
  files compare `"0" == "0"`.

### Hidden folders (`plan::mark_hidden`)

- B23. For every non-root directory, `hidden` is recomputed (set **and** cleared) (`:542-571`).
- B24. Match rule: for each entry `h` of `options.hidden_folder_paths`, replace `\` by `/`
  (`:557, 575-589`); the directory is hidden iff its relative path **starts with** `h` as a plain
  string prefix, case-sensitive (`:558-563`). Quirks kept: `"@a"` also hides `"@abc"`; `""`
  hides everything; subfolders of a hidden folder are hidden too.
- B25. Java builds the relative path by climbing parents and skipping **every** ancestor named
  `racine` (`:548-553`); Rust uses the structural relative path (DV-P1, same as WP07 DV9).

### Extra local files (`plan::add_extra_local_files`)

- B26. Recursive from the root, **after** B21-B25 (`:607-659`). A hidden directory is skipped
  entirely, including its subtree (`:613`).
- B27. Listing: for a non-root directory, list `local_path` (`:615-617`). For the root, list
  `options.destination` **only if** `exact_match` (`:618-620`). A missing folder, a file, or a
  read error gives no listing (Java `listFiles()` returns `null`), silently.
  Consequence kept (Java quirk, local-only): directories **below** the root are always scanned,
  whatever `exact_match` says, so extra files inside a remote addon folder are always offered
  for deletion. With an event filter, every local entry inside a synthesized folder that is not
  in the event is also flagged (Q5).
- B28. Names present remotely: the directory's children names **before** this step's additions,
  lowercased (`str::to_lowercase`) (`:625-628`). An entry is extra when its lowercased name is not
  in that set (`:629-630`).
- B29. Extra directory (`Path::is_dir`, follows symlinks) → new `PlanDirectory` with `deleted =
  true`, all other flags default (`:631-634`). Extra non-directory → new `PlanLeaf` with
  `deleted = true`, `sha1 = None`, sizes 0, **unless** its name **contains** `".part"` or
  `".pbo.zip"` anywhere (`:640-641`; `dao/DataAccessConstants.java:22, 26`). Quirk kept:
  `my.particles.pbo` contains `.part` and is never offered for deletion.
- B30. Destination of an added node: the scanned directory's `destination_path.join(name)` when
  it has one, else `options.destination` (root case) (`:635-639, 645-649`).
- B31. After the listing, recurse into **every** child directory, including the ones just added
  (`:654-656`): the full content of an extra directory is therefore enumerated as deleted nodes
  (its remote child set is empty). Node insertion uses `add_child` (WP07 B29 order), so listing
  order does not matter.

### Summary (`plan::summary`, port of `FilesSynchronizationManager`)

- B32. `PlanSummary::compute(&PlanTree)` walks **including the root** in pre-order
  (`service/synchronization/FilesSynchronizationManager.java:31-90`). Per node:
  - `files_updated += 1` if `updated`, **else if** `deleted` → `files_deleted += 1` (`:50-54,
    70-74`) — directories count too;
  - `files_selected += 1` if `selected` (the root counts if it is selected, `:75-77`);
  - `selected && updated` → push to `download_tasks` (via WP07 `DownloadTask::from_node`), and for
    leaves add `download_size()` (WP07 B31) to `total_download_size` (`:58-63, 78-80`);
  - else `selected && deleted` → push a `DeleteTask { relative_path, local_path, is_directory }`
    (`:64-67, 81-84`).
  Task order = pre-order (a directory before its content). A selected updated node without a
  destination (impossible after `plan_repository`) is skipped with `tracing::warn!`.
- B33. `userconfig_dir`: the first `download_tasks` entry (in order) whose relative path's
  **first segment**, lowercased, is `"userconfig"` **and** that segment is a directory, i.e. the
  task path has ≥ 2 segments, or the task is that directory itself → `Some(first segment as
  written)`; else `None` (`:138-169`; Java climbs to the ancestor whose parent is named `racine`,
  structural here, DV-P1). A root-level **leaf** named `userconfig` does not count.
- B34. `resumed_tasks(tasks)` = tasks whose `status != Done`, in order (`:171-181`).
  `resumed_size(tasks)` = Σ `download_size()` of **file** tasks with `status == Done` (`:183-196`).
  `downloaded_compressed(tasks)` = file tasks with `compressed && status == Done` (`:198-211`).
- B35. `ReportTotals::compute(tasks)` over file tasks only (`:105-134`): `disk_files_size += size`
  for every file; if `complete != 0.0` → `uncomplete_files += 1`, `uncomplete_expected_size +=
  download_size()`, `uncomplete_disk_size += size`; **else if** `compressed` →
  `compressed_files += 1`, `compressed_files_size += compressed_size`,
  `uncompressed_files_size += size`.
- B36. `PlanTree` CLI selection helper `select_all_except_root(&mut PlanTree)`: every non-root
  node `selected = true`, root unchanged (`console/CommandGeneral.java:430-441`). (The GUI
  "select all" also selects the root; that is WP26's business via WP07
  `set_selected_recursive`.)

### Completion (`completion`)

- B37. `classify_leaves(tree, server_info, partial_supported) -> Vec<String>`
  (`service/ConnectionService.java:300-323`), every leaf in pre-order (deleted leaves included):
  - `updated` and `server_info.compressed_pbo_files_only` → `complete = 0.0`;
  - else `updated` and `!partial_supported` → `0.0`;
  - else `updated` and the local file does not exist → `0.0`;
  - else `updated` → returned for checking (`complete` untouched until B40);
  - not `updated` → `complete = 100.0`.
- B38. `partial_supported` (`:285-298`): start with `!server_info.no_partial_file_transfer`. If
  true, probe with WP07 `RemoteConnection::probe_partial_transfer` (HTTP `Range: bytes=0-1` on
  `.a3s/sync`): `Supported` → true, `Unsupported` → false, `NotApplicable` (FTP/SFTP/WebDAV) →
  see B39, `Err` → `CompletionError::Remote` (the whole completion fails, `:292-294`). The probe
  runs before classification, even if nothing needs checking.
- B39. Non-HTTP transports: Java opens K FTP/SFTP/WebDAV connections whose `getFileCompletion`
  returns `0` (`dao/connection/ftp/FtpDAO.java:733-735`, `sftp/SftpDAO.java:351-353`,
  `webdav/WebdavDAO.java:415-417`). Rust produces the same values without any network access:
  classify with `partial_supported = false` (DV-P4).
- B40. Per checked leaf (`dao/connection/http/HttpDAO.java:449-490`):
  - local file length 0 → `complete = 0.0`, no request (`:455`);
  - else log `tracing::info!("Determining file completion: {abs}")` (`:457`), fetch the remote
    `RemoteFile { filename: name + ".zsync", parent_relative_path: parent_relative_path(path) }`
    (`:459-462`) via `transport_path()`; parse with `a3s_zsync::ControlFile::parse`; run
    `a3s_zsync::match_blocks(&control, File::open(local)?, Some(&flag))` in
    `spawn_blocking`; `complete = completion_percent(&matches, control.header.hash_lengths.seq_matches)`
    (B41); log `tracing::info!("File completion: {pct}% {abs}")` with
    `pct = a3s_format::java_double_to_string(((100.0 * complete) as i64) as f64 / 100.0)` (`:484-485`).
  - fetch error → `CompletionError::Remote(RemoteError::Fetch { .. })` whose message follows
    WP07 B13 (HTTP core `"Failed to connect to the HTTP server on url: {host_url}{relative_file_path}"`,
    `HttpDAO.java:176, 206-213`), see Q1;
  - parse / match / local read error → `CompletionError::Zsync` with message
    `"Failed to read zsync file: {relative_file_path}\n{error}"` (`:472-477`), kind
    `InvalidData` for `a3s_zsync::Error::InvalidControlFile`, `ErrorKind::from_io` for
    `a3s_zsync::Error::Io`.
- B41. `completion_percent(matches, seq_matches) -> f64` (`jazsync/FileMaker.java:495-525`): on a
  copy of `matches.local_offsets`, when `seq_matches == 2` and `n ≥ 2`, clear (set `None`) every
  matched block whose neighbours are both unmatched (interior), the first block if block 1 is
  unmatched, and the last block if block `n-2` is unmatched — evaluated left to right on the
  **mutating** copy exactly like Java's single loop. Result `(n - missing) as f64 / n as f64 *
  100.0`, or `0.0` when `n == 0`. (Java crashes for `seq_matches == 2, n == 1`, which jazsync never
  produces; Rust skips the clearing for `n < 2`.)
- B42. Concurrency (`service/synchronization/FilesCompletionProcessor.java:37-53`):
  `completion_connections(server_info) = clamp(server_info.number_of_connections, 1, cpus)` where
  `cpus = std::thread::available_parallelism()` (Java: `0 → 1`, then `min(n, availableProcessors)`;
  negative values clamp to 1, DV-P11). The client's own connection setting is **not** used
  (quirk kept). Rust: `min(K, candidates)` workers, each owning one `RemoteConnection` (WP07),
  popping paths from a shared stack (Java `Stack`, LIFO, `ConnectionCompletionProcessor.java:27-28,
  129-136`). Java's per-worker `checkConnection` pre-flight (`:44`) is dropped (DV-P5).
- B43. Errors (`ConnectionCompletionProcessor.java:71-123`): after the first error every worker
  stops taking new files; in-flight files finish or fail; the **first** error (by completion time)
  is returned (Java collects all that raced and the UI shows `errors.get(0)`,
  `ui/repository/workers/AddonsChecker.java:60-64`; DV-P6). Results already computed are written
  to the tree even on error; callers must treat the tree's `complete` values as unreliable after
  `Err`.
- B44. Progress: `SyncEvent::Phase(Phase::DeterminingCompletion)` once at start, then
  `PercentCounter::new(candidates)` incremented per **successful** leaf (cancelled leaves not
  counted), emitting `Progress { phase: DeterminingCompletion, percent }` on change
  (`:138-143`; Java emits on every file, DV-P8). Zero candidates → no `Progress`.
- B45. Cancellation: `ctx.cancel` (WP07 `TransferCtx`) aborts fetches; a watcher task sets the
  `AtomicBool` given to `match_blocks`. Result `Err(CompletionError::Cancelled)` within 1 s
  (DV-P3; Java ends normally on cancel, `:71, 78-84`).
- B46. Return `Ok(CompletionStats { checked, partial })` where `checked` = candidates processed and
  `partial` = leaves with `0.0 < complete`. The WP09 download uses `complete == 0.0` → full
  download, else zsync patch (`dao/connection/AbstractConnexionDAO.java:262-264`).

### Java quirks to preserve (wire-visible)

- None written to a repository. Server-visible requests: the probe `GET .a3s/sync` with
  `Range: bytes=0-1` (WP07) happens before classification unless `no_partial_file_transfer`; one
  `GET <parent>/<name>.zsync` per checked leaf (B40); nothing for compressed-only repositories
  except the probe; no request at all for non-HTTP transports (B39, DV-P4).

### Java quirks preserved for user-visible parity (local-only; kept by default)

- Last duplicate event wins in the filter (B4); empty synthesized folder from `seek` (B8).
- Addon/userconfig name matching is case-sensitive; userconfig folder lookup is
  case-insensitive (B6, B7).
- Auto-discover at any depth, only for `mark_as_addon` folders (B13).
- Whole-cache pruning (B15); hash error on a local directory aborts the plan (B19).
- Hidden-path string-prefix matching (B24).
- Extra-file scanning of every non-root remote folder regardless of `exact_match`; `.part` /
  `.pbo.zip` substring exclusion; case-insensitive name comparison while `exists()` is
  case-sensitive on Linux (B27-B29).
- Summary counts the root when selected; `updated` wins over `deleted` in the counts (B32).
- Completion ignores the client connection setting (B42); compressed-only repositories never use
  zsync (B37).

### Java quirks that may be dropped (local-only; needs an approved deviation)

- DV-P1. Structural relative paths: Java skips every directory named `racine` in
  `getDeepSearchNodesList` (`SyncTreeNodeMethods.java:36`) and in the hidden-path and
  userconfig climbs (`RepositoryService.java:549`, `FilesSynchronizationManager.java:155-156`), so a
  nested `racine` folder gets no destination/flags. Rust treats only the tree root specially
  (consistent with WP07 DV9).
- DV-P2. No mutation of the decoded `SyncTreeDirectory` (B3).
- DV-P3. Cancellation returns `Err(Cancelled)` from planning and completion.
- DV-P4. Non-HTTP completion without connections (B39).
- DV-P5. No per-worker `checkConnection` pre-flight request in completion (B42).
- DV-P6. Completion returns the first error only (B43).
- DV-P7. Completion percentage comes from `a3s_zsync::match_blocks` (pair-wise sequential
  matching) instead of jazsync's `mapMatcher` scan (`FileMaker.java:263-430`, single-block hits with
  a `lastMatch + blocksize` skip). Values can differ slightly on edge cases; they only steer
  zsync-vs-full download and size estimates.
- DV-P8. Completion progress deduplicated through `PercentCounter`.
- DV-P9. (Q2) Unknown event name → `PlanError::EventNotFound` instead of an empty plan.
- DV-P10. (Q3) Duplicate synthesized directory names merged.
- DV-P11. Negative server connection count clamps to 1 (B42).

### Errors, cancellation, progress

- No retries anywhere (Java has none for check/completion).
- `PlanError` (`thiserror`, `Send + Sync + 'static`, implements `a3s_error::UserFacing`):
  `SyncMissing` / `EventsMissing` → `NotFound`; `Options(SyncOptionsError)` → its kind;
  `EventNotFound` → `NotFound` (message `"Event not found: {name}"`, Rust-only text);
  `Hash { path, source }` → `ErrorKind::from_io`; `Cancelled` → `Cancelled`.
- `CompletionError`: `Remote(RemoteError)` → `RemoteError::kind()` (WP07 B14);
  `Zsync { relative_path, message, source: a3s_zsync::Error }` → B40; `Cancelled`.
  `is_connection_lost()` delegates to `RemoteError::is_connection_lost` (false otherwise).
  `EventError::from` conversions are not required (callers use `UserFacing`).
- Events (WP07 `SyncEvent`): planning emits `Phase(CheckingFiles)` then
  `Progress{CheckingFiles, …}`; completion emits `Phase(DeterminingCompletion)` then
  `Progress{DeterminingCompletion, …}`. No `Finished` (callers get the `Result`).
- Read-dir errors during extra-file scanning are swallowed (Java `listFiles() == null`), logged at
  `tracing::debug!`.

### Concurrency

- Planning: blocking; SHA-1 through `a3s_hash::hash_files` (≤ `min(8, cpus)` rayon threads,
  `RepositorySHA1Processor.java:39, 83-85`). Everything else single-threaded.
- Completion: async (`Send` future), K = `completion_connections` workers (B42), each owning one
  `RemoteConnection`; `match_blocks` in `spawn_blocking`. Memory per worker: one `.zsync` body
  (≈ 1 MB for a 1 GB file) plus `match_blocks` buffers (≈ 4 MB).
