## Scope

- `local`: the Rust client's own store, in the directories that `a3s_paths::AppDirs` returns
  (`…/arma3sync-rs/…`). It holds configuration, preferences, profiles, repositories, per-repository
  SHA-1 caches and the Workshop metadata cache, as versioned TOML files written atomically.
- `local` load semantics ported from the Java DAOs: Java's error collection and messages, the
  duplicate-repository rule, and the default profile that is always present.
- `local` file naming: Java's `RepositoryDAO` preferred scheme, `sanitize(name) + "__" + 12 hex digits
  of SHA-1(name)`, used for both profiles and repositories.
- `legacy`: read-only decoding of the Java client's files: gzip + Java serialization with Java's
  class allowlist (`a3s.cfg`, `a3s.prefs`, `*.a3s.profile`), and
  `GZIP(ObjectOutputStream(SealedObject(AES-128/ECB/PKCS5(ObjectOutputStream(Repository)))))`
  (`*.a3s.repository`). Also `java.util.Properties` parsing for `known-workshop-mods.properties`.
- `legacy::import`: an idempotent, one-time importer from the locations `a3s_paths` discovers. It
  never touches Java's files, never overwrites Rust data, applies Java's deprecated-configuration
  migration (search paths and launcher options into the active profile), and writes an import
  marker plus a report.
- Port `T/dao/A3SFilesAccessorTest` and `T/dao/PreferencesDAOTest`.

## Behaviour contract

### Directory layout of the Rust store (`local`)

- B1. `LocalStore::new(&a3s_paths::AppDirs)` uses:
  - `config = AppDirs::config_dir()`;
  - `profiles = AppDirs::profiles_dir()` (`config/profiles`);
  - `repositories = AppDirs::repositories_dir()` (`data/repositories`);
  - `sha1_cache = AppDirs::data_dir()/sha1_cache` (see Q3).

  `LocalStore::with_dirs(LocalDirs)` takes explicit directories for tests. The store creates a
  directory only when it first writes into it (`create_dir_all`). Java creates its folder in every
  `write` (`dao/PreferencesDAO.java:35-38`, `dao/repository/RepositoryDAO.java:221-224`). Reads of a
  missing directory or file are not errors.
- B2. File names, all fixed constants:
  - `config/configuration.toml`
  - `config/preferences.toml`
  - `config/workshop_mods.toml`
  - `config/legacy_import.toml` (the import marker)
  - `profiles/<stem>.toml`
  - `repositories/<stem>.toml`
  - `sha1_cache/<stem>.sync.toml` and `sha1_cache/<stem>.build.toml`

  `<stem> = file_stem(name)` (B4).
- B3. Every TOML file has a top-level integer `format = 1` and puts its payload in one table whose
  key is fixed per kind: `configuration`, `preferences`, `profile`, `repository`, `cache`,
  `workshop`, `import`. A missing `format` is read as 1. `format > 1` is rejected with
  `Error::UnsupportedFormat { path, found, supported: 1 }`. Unknown keys are ignored. Missing keys
  take the WP03 serde defaults (Java initializer values, WP03 B49).

### File naming (`dao/repository/RepositoryDAO.java:313-363`)

- B4. `file_stem(name) = sanitize(name) + "__" + name_hash(name)`, where:
  - `name_hash(name)` is the lowercase hex of the first **6 bytes** of `SHA-1(UTF-8(name))`, which is
    **12** hex characters (`HASH_PREFIX_BYTES = 6`, `:41, 344-359`). It hashes the untrimmed name.
  - `sanitize(name)` (`:330-342`):
    1. Java `String.trim()`: strip leading and trailing chars `<= U+0020`.
    2. Replace each run of Java `\s` (`[ \t\n\x0B\f\r]`, ASCII only) with one `_`.
    3. Replace each of `\ / : * ? " < > |` with `_`.
    4. An empty result becomes `"repository"`.

  Examples: `"WOG"` → `WOG__fe52247a11ac`. `"My Repo"` → `My_Repo__339879ebfb9b`.
  `"  a/b:c*?  "` → `a_b_c____b3a64f4e4ad1`. `"Default"` → `Default__808d7dca8a74`.

  Rust additions (local-only, Q5): after step 3, every remaining char `< U+0020` or `U+007F` also
  becomes `_`. The sanitized part is truncated to at most 64 bytes on a char boundary. The hash is
  never truncated.
- B5. `legacy::naming` also exposes Java's own names, for diagnostics and tests:
  - `java_preferred_repository_file_name(Some(name)) = file_stem_java(name) + ".a3s.repository"`. This
    is the same as B4 without the Rust additions. A `None` name gives `"repository__000000.a3s.repository"`
    (`:332-334, 346-348`).
  - `java_legacy_repository_file_name(name)` = the name with every U+0020 removed
    (`replaceAll(" ", "")`), plus `".a3s.repository"`. A `None` name gives
    `"repository.a3s.repository"` (`:322-328`).
  - `java_profile_file_name(name) = name + ".a3s.profile"` (`dao/ProfileDAO.java:72`).

### Atomic writes (`dao/A3SFilesAccessor.java:144-201`)

- B6. Every store write serializes to a string first. It then calls the existing
  `crate::a3s_file::write_atomic(path, bytes)`, which creates a temp file in the same directory,
  writes it, fsyncs it, and renames it over the target (`tempfile::NamedTempFile::persist`). This
  matches Java's temp file plus `ATOMIC_MOVE` with a `REPLACE_EXISTING` fallback (`:188-201`).
  - If serialization or any I/O step fails, the target is left unchanged and the temp file is
    removed (`:156-161`).
  - On Unix, `tempfile` creates the file with mode `0600`, and the rename keeps that mode. This is
    relied on for the credential-bearing files (Q1). A test asserts it.
  - Leftover temp files (`.tmp*`) never end in `.toml`, so listings ignore them.
- B7. Writes from one `LocalStore` are serialized by a `parking_lot::Mutex<()>`, the counterpart of
  Java `REPOSITORY_WRITE_LOCK` (`dao/repository/RepositoryDAO.java:37, 200-207`). One lock covers
  every kind of write. `LocalStore` is `Send + Sync`. Reads take no lock: the atomic rename makes
  them see either the old file or the new one.
- B8. Java's `.backup` rename dance in `ProfileDAO.write` (`dao/ProfileDAO.java:74-97`) is not
  reproduced; atomic replace gives the same guarantee. `.backup` files are not created.

### Configuration and preferences (`dao/ConfigurationDAO.java:24-54`, `dao/PreferencesDAO.java:15-45`)

- B9. `read_configuration()`:
  - missing file → `Ok(Configuration::default())`, as Java keeps its static default
    (`ConfigurationDAO.java:28`);
  - unreadable or unparsable file → `Err(Error::Read{..} | Error::Parse{..})`, whose `user_message()`
    is `"Failed to read file: <path>"` (`:35`). The caller (WP14) logs it and continues with the
    defaults (`ui/main/MainPanel.java:460-464`).

  `read_preferences()` is identical, with `Preferences::default()` (`PreferencesDAO.java:15-28`).
- B10. `write_configuration(&Configuration)` and `write_preferences(&Preferences)` create
  `config/` if needed and write atomically. On failure the user message is
  `"Failed to write file: <path>"` (`ConfigurationDAO.java:51`, `PreferencesDAO.java:42`).
  `<path>` is the canonical path when it can be computed (Java `getCanonicalPath`), otherwise the
  path as given.

### Profiles (`dao/ProfileDAO.java`)

- B11. `load_profiles() -> ProfilesLoad` reads every regular file in `profiles/` whose name ends with
  `.toml`, in file-name order. The profile's identity is its `name` field, never the file name.
  - Each failure is recorded under the **file name** in a `BTreeMap` (Java `TreeMap`, `:28, 37-39`).
  - Two files with the same profile name: the newer mtime wins, and on a tie the first in file-name
    order wins. A warning is added in the B15 format. Java's last-listed-wins is non-deterministic
    (`:35`).
- B12. After loading, if no profile is named `"Default"`, `Profile::new("Default")` is inserted in
  memory only, not written (`:44-48`, `constant/DefaultProfileName.java:5`). This is the "default
  profile always present" rule.
- B13. `ProfilesLoad::error_message()` returns `None` when there are no failures. Otherwise it
  returns `"Failed to load profiles:"` followed, for each failure in key order, by
  `"\n - <file>: <message>"` (or `"\n - <file>"` when the message is empty) (`:50-63`).
- B14. `write_profile(&Profile)` writes `profiles/<file_stem(name)>.toml` (B6). On failure the
  message is `"Failed to write file: <path>\n<detail>"` (`:90-92`). `delete_profile(name) -> bool`
  removes that file and returns whether a file was removed (`:100-108`; Java ignores the result).

### Repositories (`dao/repository/RepositoryDAO.java`)

- B15. `load_repositories() -> RepositoriesLoad` mirrors `readAll` (`:103-167`):
  - Candidates are the regular files in `repositories/` whose name ends with `.toml` (Java
    `endsWith(REPOSITORY_EXTENSION)`, `:116`), in file-name order.
  - A file that fails to read or parse is recorded under its file name (`:128-130`).
  - A repository whose `name.trim()` is empty is recorded with the message
    `"Repository name is missing."` (`:121-124`).
  - Duplicate names (`registerRepository`, `:169-190`): the candidate replaces the kept one only
    if its mtime is **strictly greater**. A missing previous file counts as `i64::MIN`. Each
    duplicate adds one warning, with the exact text:
    - replaced: `"<name>: replaced \"<old file>\" with \"<new file>\" because it is newer."`
    - ignored: `"<name>: ignored \"<new file>\" because \"<old file>\" is newer."`
  - If there are any warnings, they are logged with `tracing::warn!`, preceded by
    `"Detected duplicate repository definitions during load:"`, one line each with the prefix
    `" - "` (`:145-150`).
  - A directory read error other than `NotFound` → `Err`, with the message
    `"Failed to read repository files\n<detail>"` (`:134-142`).
- B16. `RepositoriesLoad` keeps every successfully loaded repository **even when there are
  failures**. Java populates `mapRepositories` before it throws, and callers only print the
  exception (`ui/main/MainPanel.java:472-476`). `error_message()` returns
  `"Failed to read repository files:"` followed by `"\n - <file>: <message>"` lines (`:152-164`).
  `RepositoriesLoad` also records each repository's source file (used by B17).
- B17. `write_repository(&Repository)` writes `repositories/<file_stem(name)>.toml` atomically,
  under the write lock (`:196-239`). The message on failure is `"Failed to write file: <path>"`
  (`:236`).

  `write_repository_replacing(&Repository, previous: Option<&Path>)` additionally deletes
  `previous` after a successful write when it differs from the target file. This is the counterpart
  of Java's legacy-file migration (`:209-232`), for renames and stray copies. The deletion is
  best-effort: on failure it logs and still returns `Ok`.
- B18. `remove_repository(name) -> bool` deletes `repositories/<stem>.toml` and both cache files.
  It returns `true` when at least one file was deleted (`:52-91`; the `.backup` variants do not
  exist in the Rust store).

### SHA-1 caches (`Repository.mapFilesForSync` / `mapFilesForBuild`)

- B19. Kept out of the repository TOML (WP03 Q4). Two kinds:
  - `CacheKind::Sync` = `mapFilesForSync`, the client's local hashes;
  - `CacheKind::Build` = `mapFilesForBuild`, the admin build hashes.

  On disk, `[cache.entries]` maps the absolute path string to `{ sha1, last_modified }`, where
  `last_modified` is in ms (`dao/repository/RepositorySHA1Processor.java:112-114, 145`).
  The in-memory type is `a3s_hash::Sha1Cache`:
  - entries are written as a `BTreeMap<String, _>` (deterministic output);
  - non-UTF-8 paths are skipped on write, with a `tracing::warn!`.
- B20. `read_sha1_cache(name, kind)`: a missing file gives an empty cache. A corrupt file gives an
  empty cache plus a `tracing::warn!`, never an error, because a cache can always be rebuilt.
  `write_sha1_cache(name, kind, &Sha1Cache)` writes atomically and creates `sha1_cache/` if needed.

### Workshop metadata (`service/WorkshopMetadataStore.java`; see Q2)

- B21. `config/workshop_mods.toml` holds a table `workshop.mods`, keyed by addon key, with values
  `{ published_id, name }`.
  - `find(key)`: `None` for a blank key, or when the stored id or name is blank. Otherwise it returns
    the trimmed values (`:42-53`).
  - `save(key, id, name)` validates in Java's order, with Java's exact messages:
    1. a blank key → `"Addon key must not be empty."`;
    2. an id that does not match `^[1-9][0-9]*$` (untrimmed, Java `matches`) →
       `"Workshop ID must be a positive number."`;
    3. a blank name → `"Workshop name must not be empty."` (`:55-64`).

    It then re-reads the file, sets the trimmed values, and writes atomically under the store lock
    (`:66-99`). An unreadable existing file is treated as empty (`:76-78`).
  - Java's `.lock` file guards against other processes. The Rust single-instance guard (WP15)
    takes its place.

### Legacy decoding (`legacy`)

- B22. `legacy::read_object_file(path) -> Result<a3s_jserial::Graph>`, used for `a3s.cfg`,
  `a3s.prefs` and `*.a3s.profile` (`dao/A3SFilesAccessor.java:55-83`):
  1. Gunzip with a cap of `MAX_DECOMPRESSED_SIZE` (256 MiB, Java `streamBytes`, `:28`).
  2. `a3s_jserial::read`, with the generous default limits (WP03 B35).
  3. `check_java_allowlist(&graph)` (B24).
- B23. Error texts. `<file>` is the file **name** only (`:70, 101`):
  - an I/O or gzip error → `"Failed to read file: <file>\n<detail>"`; if the cause is a gzip or
    truncated-input (EOF) error, `"\nThe file seems to be corrupted."` is appended (`:26, 65-74`);
  - a serialization or allowlist error → `"Failed to deserialize file: <file>"`, with the detail kept
    as `source` (`:75-76`);
  - a decryption error (B26) → `"Failed to decrypt serialized file: <file>"` (`:106-107`).
- B24. `check_java_allowlist(graph) -> Result<(), Rejected { class }>` checks **every** class
  descriptor node in the graph, superclass descriptors included, because Java's filter sees each
  descriptor it resolves (`:27-53, 116-142`). A descriptor name is allowed when:
  - it starts with `fr.soe.a3s.`; or
  - it is one of `java.lang.{String, Enum, Boolean, Byte, Character, Double, Float, Integer, Long, Short}`,
    `java.util.{ArrayList, HashMap, HashSet, LinkedHashMap, LinkedHashSet, Properties, TreeMap, TreeSet, Date, Map$Entry}`
    or `javax.crypto.SealedObject`; or
  - it is an array (`[…`) whose component is a single primitive code (`[B`, `[I`, …),
    `Ljava/lang/Object;`, or `L<allowed name>;`. A nested array component (`[[B`) is **rejected**,
    as in Java (`:43-47`).

  Quirk: `java.lang.Integer` is allowed but its serializable superclass `java.lang.Number` is
  not, so Java rejects any stream containing a boxed `Integer`. Mirror this.
- B25. `legacy::read_repository_file(path) -> Result<LegacyFile<LegacyRepository>>` (`:85-114`):
  1. B22 steps 1-3 on the outer stream.
  2. The root object must have `javax.crypto.SealedObject` in its class hierarchy. Otherwise:
     `Error::UnexpectedClass`.
  3. Read the field `encryptedContent` by name (`Graph::opt_field`). It must be a byte array
     (`Node::Array` with `ArrayData::Byte`). Any UID is accepted. `encodedParams`, `paramsAlg` and
     `sealAlg` are read only to produce warnings: a non-null `encodedParams`, or a `sealAlg` that is
     not `"AES"` (ASCII case-insensitive) or absent, adds a warning but does not abort.
  4. Decrypt with B26.
  5. Decode the plaintext, which is an uncompressed Java stream, with
     `a3s_types::local::decode_legacy_stream::<LegacyRepository>`. No allowlist check is applied:
     Java's `SealedObject.getObject` uses its own unfiltered `ObjectInputStream`.
- B26. `legacy::crypto` (`dao/EncryptionProvider.java:13-31`):
  - `JAVA_AES_KEY: [u8; 16] = [0x01,0x72,0x43,0x3E,0x1C,0x7A,0x55,0x00,0x01,0x72,0x43,0x3E,0x1C,0x7A,0x55,0x4F]`.
  - The cipher is `Cipher.getInstance("AES")`, which SunJCE resolves to `AES/ECB/PKCS5Padding`
    (`:19, 27`). ECB means each 16-byte block is processed independently, with no IV.
  - `decrypt(ct)`:
    - `ct.len()` must be a non-zero multiple of 16;
    - after decryption, PKCS#7 padding is validated: the last byte `n` is in `1..=16` and the last
      `n` bytes all equal `n`;
    - otherwise `CryptoError::{BadLength, BadPadding}`.
  - `encrypt(pt)` always appends 1 to 16 padding bytes, so 16 bytes of input give 32 bytes of
    output.
  - Test vectors: `encrypt(b"hello") = 722efc9890ba35cbe048931ba220cca1`.
    `encrypt(b"0123456789abcdef")` gives 32 bytes, starting `9133552568478c0cf574c481b6b2fd28`
    (computed with `openssl enc -aes-128-ecb`).
- B27. `legacy::sealed::seal(inner_stream: &[u8]) -> Result<Vec<u8>>` produces
  `GZIP(stream(SealedObject{encodedParams: null, encryptedContent: encrypt(inner), paramsAlg: null, sealAlg: "AES"}))`.
  It uses the SealedObject descriptor from Wire-compat notes. It exists for tests and for the WP01
  "Java reads it" cross-check. Production code never writes Java files.
- B28. `legacy::read_configuration_file`, `read_preferences_file` and `read_profile_file` combine
  B22 with WP03's `decode_legacy_stream` for `LegacyConfiguration`, `Preferences` and `Profile`.
  They return `LegacyFile<T> { value, warnings }`. Each warning is prefixed with the file name.
- B29. `legacy::properties::parse(bytes) -> Result<Vec<(String, String)>, PropertiesError>` follows
  Java `Properties.load(InputStream)`:
  - bytes are ISO-8859-1;
  - logical lines may continue with an odd number of trailing backslashes, and the leading
    whitespace of each continuation line is skipped;
  - comment lines start with `#` or `!` after leading whitespace (` `, `\t`, `\f`); blank lines are
    skipped;
  - the key ends at the first unescaped `=`, `:` or whitespace; whitespace and one `=` or `:` after
    it are skipped;
  - escapes are `\t \n \r \f \uXXXX`, and `\x` gives `x`;
  - a malformed `\u` is an error (Java `IllegalArgumentException`);
  - when a key repeats, the last value wins.
- B30. `legacy::read_workshop_file(path)` (`WorkshopMetadataStore.java:106-123`):
  - parses B29; a parse or I/O error gives an empty result plus one warning, since Java clears the
    cache;
  - for every key `mod.<seg>.publishedid` that has a matching `mod.<seg>.name`, the addon key is
    `base64url_nopad_decode(seg)` as UTF-8 (`:119-123`); if `seg` does not decode, it falls back to
    the `mod.<seg>.key` value, and the entry is skipped with a warning if that is absent;
  - entries kept follow `find` (B21): non-blank, trimmed.

### One-time import (`legacy::import`)

- B31. `legacy::import(store: &LocalStore, sources: &[a3s_paths::legacy::LegacyJavaData], options: &ImportOptions) -> Result<ImportReport, ImportError>`.
  - Sources come from `a3s_paths::legacy::discover_legacy_java` or `inspect_java_installation`
    (WP02 L4, L6). They are processed in the given order.
  - It never creates, modifies, renames or deletes anything inside a source (WP02 L5).
  - It never overwrites data that already exists in the Rust store.
  - `ImportError` covers only failures to **write the Rust store**. Every problem with a legacy
    file is recorded in the report.
- B32. Order per source:
  1. profiles;
  2. repositories (with caches);
  3. configuration (with the B36 migration);
  4. preferences;
  5. workshop.

  Profiles come first so that the configuration migration can target the imported active profile.
- B33. Profiles. The candidates are the regular files in `profiles_dir` whose name **contains**
  `.a3s.profile` (`dao/ProfileDAO.java:31`), so Java also picks up `X.a3s.profile.backup`.
  - Each is read with B28.
  - When two candidates have the same profile name, a file whose name ends with `.a3s.profile`
    beats any other file, and after that the newer mtime wins (Q6).
  - If the Rust store already holds a profile with that name, or an earlier source imported one,
    the result is `SkippedExisting`.
  - Otherwise the profile is written with `write_profile`. The name check covers every file in
    `profiles/`, including the B12 in-memory default.
- B34. Repositories. The candidates are the regular files in `repositories_dir` whose name **ends
  with** `.a3s.repository` (`RepositoryDAO.java:116`). Pre-modern `.a3s.repository.backup` files
  are ignored, as in current Java.
  - Each is read with B25.
  - A blank name gives the failure `"Repository name is missing."`.
  - Duplicates follow the B15 rule (newer mtime wins) and produce the same warning texts.
  - An existing Rust repository with the same name gives `SkippedExisting`.
  - Otherwise `write_repository(repository)` is called. Then each non-empty `files_for_sync` or
    `files_for_build` is written with `write_sha1_cache`. Java ms mtimes and absolute-path keys are
    kept as they are.
  - The raw values stay raw (WP03 Q5). For example, `parallel_upload_connections = 0` stays 0.
- B35. Configuration and preferences: a source's `configuration_file` (`a3s.cfg`) is imported only
  if `config/configuration.toml` does not exist yet and no earlier source has imported one. The
  same rule applies to `preferences_file` (`a3s.prefs`) and `config/preferences.toml`. A decode
  failure gives `Failed(message)`, and the next source may still provide the file.
- B36. Deprecated-field migration (`ui/main/MainPanel.java:538-569`, WP03 B25). After the
  configuration is decoded, let `active = configuration.profile_name`.
  - The target profile is the one imported in this run under `active`. If none was imported and

    (`dao/ProfileDAO.java:44-48`, `service/ProfileService.java:197-209`).
  - In every other case (the profile was skipped because it already exists, or it doesn't exist)

  - If `addon_search_directory_paths` is `Some(v)`, `v` is appended in order to

- B37. Workshop: entries from `workshop_metadata_file` are merged into `workshop_mods.toml` only for

- B38. Marker. When every source has been processed and no `ImportError` occurred, write

  - `imported_at_ms`;
  - the configuration dirs of the sources;

### Java quirks to preserve (wire-visible)

- The AES key bytes (B26). Note the `0x00` at index 7. `Cipher.getInstance("AES")` means
  ECB/PKCS5.
- The `.a3s.repository` envelope is `GZIP` → stream → `SealedObject` → the encrypted **inner Java
  stream**. The inner stream is not gzipped.
- The name hash is 6 bytes, which is 12 hex chars. Earlier notes that say `sha1[0..6]` mean bytes,
  not chars.
- The legacy repository name only removes U+0020, not every kind of whitespace.
- The profile filter uses `contains(".a3s.profile")`, while the repository filter uses
  `endsWith(".a3s.repository")`. Pre-modern Java used `contains` for both (161a067 RepositoryDAO:79).
- The SHA-1 cache keys are Java `File.getAbsolutePath()` strings, and the mtimes are ms.
- The allowlist quirks: nested arrays and `java.lang.Number` are rejected (B24).

### Java quirks that may be dropped (local-only; needs an approved deviation)

- The `.backup` files of `ProfileDAO.write` (B8). Atomic replace is used instead.
- Java names profile files `<name>.a3s.profile` without sanitizing them, so names that contain `/`
  fail to save. Rust uses the B4 stem for profiles too.
- Control characters and the 64-byte truncation in `sanitize` (B4, Q5).
- Non-deterministic `listFiles` order. Rust sorts by file name and resolves profile duplicates by
  mtime (B11, B33).
- Java's `.lock` file for the Workshop cache (B21).
- An unknown `sealAlg` or a non-null `encodedParams` only produce a warning (B25.3). Java ignores
  them as well when a `Cipher` is passed to `getObject`, so this is effectively the same behaviour.
- Plain legacy files are read with generous depth and reference limits rather than Java's
  100 / 250 000. The class allowlist **is** enforced (Q8).

### Errors, cancellation, progress

- `local::Error` (`thiserror`) has these variants:
  - `Read { path, source: io::Error }`
  - `Parse { path, message }`
  - `UnsupportedFormat { path, found, supported }`
  - `Write { path, source: io::Error }`
  - `Serialize { path, message }`
  - `CreateDir { path, source }`
  - `InvalidWorkshopEntry(&'static str)`

  It implements `a3s_error::UserFacing`. `kind()` maps `Read`, `Write` and `CreateDir` through
  `ErrorKind::from_io`, `Parse` and `UnsupportedFormat` to `InvalidData`, and `Write` failures to
  `WriteFailed`. `user_message()` returns the Java texts of B9, B10, B14 and B17.
- `legacy::Error` has these variants:
  - `Io { file, source }`
  - `Corrupted { file, source }`, for gzip and EOF errors
  - `Deserialize { file, source }`, for jserial, types and allowlist errors
  - `Decrypt { file, source: CryptoError }`
  - `UnexpectedClass { file, found }`

  Its `Display` follows B23.
- Load functions collect per-file failures and never abort on one bad file (B11, B15). Only an
  unreadable directory aborts.
- Import: there is no cancellation. Inputs are small, apart from repository caches, which are
  bounded by 256 MiB. There are no progress events. The UI shows the report.

### Concurrency

There are no threads. `LocalStore` is `Send + Sync` and has one internal write mutex (B7). Java's
static in-memory maps (`RepositoryDAO.java:35-36`, `ProfileDAO.java:18`) are **not** reproduced:
the store has no state apart from its directories. In-memory state belongs to WP14's services.

## Wire-compat notes

- Classes read:
  - Outer stream of `*.a3s.repository`: `javax.crypto.SealedObject`.
    - serialVersionUID `4482838265551344752`, from JDK source. It is **unverified here**, and the
      reader accepts any UID.
    - Flags: `SC_SERIALIZABLE` (0x02). The class has a private `readObject` but no `writeObject`.
    - Fields in wire order: `L encodedParams [B`, `L encryptedContent [B`,
      `L paramsAlg Ljava/lang/String;`, `L sealAlg Ljava/lang/String;`. There are no primitives.
    - No serializable superclass.
    - Array class `[B`: UID `-5984413125824719648`, flags `0x02`, no fields.
    - Java writes `encodedParams = null` and `paramsAlg = null` (ECB has no parameters), and
      `sealAlg = "AES"` (`cipher.getAlgorithm()` of `Cipher.getInstance("AES")`).
  - Inner and plain streams: every class of the WP03 wire table (`Repository`, `FileAttributes`,
    `Configuration` and its option classes, `Preferences`, `Profile`, `TreeDirectory`, `TreeLeaf`,
    the enums, the protocols, `FavoriteServer`). WP03 decodes them leniently by field name. WP04
    adds only the gzip, SealedObject and AES layers, plus the allowlist.
- Byte identity is required for nothing. WP04 writes TOML only. `legacy::sealed::seal` (B27) has
  to be **semantically** readable by Java. That is a deferred WP01 check.
- Fixtures used: none on disk. Tests build Java-like streams with `a3s_jserial::jdk::Builder`, using
  the exact WP03 descriptors and the SealedObject descriptor above, then gzip and encrypt them in
  the test.
  - `Builder` has no byte-array helper. Tests call `Builder::finish(Value::Null)` and then use the
    public `Graph::push`:
    - `Node::ClassDesc` for `[B`;
    - `Node::Array { data: ArrayData::Byte }`;
    - `Node::String` for `"AES"`;
    - `Node::Object` for the SealedObject;
    - set `graph.roots`.

    The writer assigns handles in emission order, so the push order does not matter.
  - Because `tests/*.rs` files cannot share a helper module inside the owned globs, the Java-like
    graph builders for `Repository`, `Profile`, `Configuration` and `Preferences` live in
    `tests/legacy_import.rs`. The other legacy test files only need small graphs.
- Fixtures still needed from the JDK harness (WP01). Each becomes a `#[test]` once present; until
  then the item is **DEFERRED**:
  - real Java-written `a3s.cfg`, `a3s.prefs`, a profile, and encrypted `*.a3s.repository` for HTTP,
    FTP and SFTP (with non-empty caches), plus a tree in Java's per-user layout and in the portable
    layout;
  - a dump of the `SealedObject` class descriptor (to confirm the UID and flags);
  - the Java side reading `legacy::sealed::seal` output.

## Open questions

- Q1 Credentials (repository login and password, proxy and favorite-server passwords) end up in
  plain-text TOML. Java encrypted only `*.a3s.repository`, with a hard-coded key, which is
  obfuscation rather than protection. `a3s.cfg`, which holds the proxy and favorite-server
  passwords, was never encrypted. Proposed default: plain TOML, with files created `0600` on Unix
  through `tempfile`. On Windows the per-user AppData ACLs apply. An OS keyring is a possible later
  follow-up. Decision:
- Q2 Who owns the Workshop metadata store? WP18 lists `WorkshopMetadataStore` as an anchor, and
  WP04 must import its file. Proposed default: WP04 owns the storage (`local::workshop`: file
  format, `find`, `save`, validation messages). WP18 consumes it, so WP18 gains a dependency on
  WP04 (wave order is unaffected: WP04 is Wave 1, WP18 Wave 2). Decision:
- Q3 Location and format of the SHA-1 caches. Proposed default: TOML at
  `data/sha1_cache/<stem>.{sync,build}.toml`. The caches go in the data dir, not the cache dir,
  because losing them forces a re-hash of whole repositories. A cache of 50 000 entries is about
  5 MB of TOML, which is acceptable. Alternative: `serde_json`, which is faster. Decision:
- Q4 Conflicts between sources (per-user layout and installation dirs). Proposed default: the first
  source in discovery order wins for configuration and preferences, and each profile or repository
  name is imported once. Existing Rust data is never overwritten. Decision:
- Q5 File-name stem additions: control chars become `_`, and the sanitized part is truncated to
  64 bytes, which avoids `ENAMETOOLONG` on 255-byte file systems. Java does neither. These are Rust
  file names only, so the change is local-only. Proposed default: approve. Decision:
- Q6 Profile candidates follow Java's `contains(".a3s.profile")` rule, so `.backup` files are
  included. A primary `*.a3s.profile` file always beats a `.backup` copy, and after that the newer
  mtime wins. Proposed default: as described. Decision:
- Q7 `SealedObject` UID `4482838265551344752` and its flags were taken from JDK knowledge, not from a
  JDK run. Proposed default: the reader is lenient (any UID, field by name). `seal` uses this UID,
  and A17 confirms it later. Decision:
- Q8 Enforcing Java's class allowlist on `a3s.cfg`, `a3s.prefs` and profiles. Rust decoding is safe,
  but a file the current Java client rejects is unusable there too. Proposed default: enforce the
  allowlist, mirroring Java and keeping the ported A15 test meaningful. Do **not** enforce Java's
  depth and reference limits. Decision:
