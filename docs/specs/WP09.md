## Scope

- `download::download(request, tasks, zips, cancel, events)`: runs a list of WP07 `DownloadTask`s
  over **K** parallel connections. K = `SyncOptions::download_connections(server_info)` =
  min(client setting, `ServerInfo.numberOfConnections`), each 0 → 1. Each worker owns one
  `a3s_transport::Transport`.
- Full-file downloads: `.pbo.zip` selection for compressed leaves, a `.part` file then rename,
  resume within a session (`Running` status + partial file), bounded resume retries on
  incomplete transfers, and the size check.
- zsync partial downloads (HTTP only, `complete > 0`): fetch `<file>.zsync`, `a3s_zsync::match_blocks`,
  `Plan`, range requests of ≤ 100 blocks, `assemble` into `<file>.part`, verify, rename. Falls back
  to a full download when partial transfer cannot be used.
- Run-level policy: max-error abort (10), connection lost, cancellation within 1 s, a global
  speed limit (shared `Throttle`), and final per-task statuses.
- A progress monitor that emits WP07 `SyncEvent`s: transfer progress, speed, active connections,
  disk usage (free-space delta) and connection waiting (seconds without progress).
- Hand-off to WP10: every finished `.zip` goes to a `ZipSink` (WP10's unzip pool) as soon as it is
  complete, and is also listed in the returned `DownloadReport`. WP10 turns the report into the
  final `Outcome`.

## Behaviour contract

Terms:
- **file task**: a `DownloadTask` with `kind = File{..}`.
- **pending task**: a task with `status != Done`.
- **download size** of a file task: WP07 `DownloadTask::download_size()`, i.e. Java
  `determineDownloadSize` (`service/synchronization/FilesSynchronizationManager.java:92-103`).
- **final path** of a file task: `destination_dir/name`.

### Inputs and setup

- B1. **Input.** `tasks` is the list WP08 builds (Java `listFilesToUpdate`, in pre-order:
  `FilesSynchronizationManager.java:46-90`). Tasks with `status == Done` are skipped and never
  touched (`getResumedFiles`, `:171-181`). Their download sizes count as already transferred
  (`getResumedFilesSize`, `:183-196`; see B30). The caller owns `tasks`. On return every task's
  `status` is up to date (B28).
- B2. **Connections.** `request.connections` is used as given, clamped to ≥ 1. The caller computes
  it with `SyncOptions::download_connections(server_info)` (WP07 B35, mirroring
  `service/synchronization/FilesSynchronizationProcessor.java:65-80` and
  `service/ConnectionService.java:59-64`). `DownloadRequest::new` does this. The number of
  workers is `min(connections, pending file tasks)`. Java starts a thread only while the stack
  is non-empty (`service/connection/ConnectionDownloadProcessor.java:49-50`). With zero pending
  file tasks, no worker and no connection is created.
- B3. **Start.** In this order:
  1. `Phase(Phase::Downloading)`. Java sets the `"Downloading..."` label when the download
     starts (WP07 B37). WP10 must not emit it again.
  2. `TransferTotal { bytes, files }`. `bytes` = Σ download size over **all** file tasks,
     including `Done` ones. Java emits `getTotalFilesSize()` before `synchronize`
     (`FilesSynchronizationProcessor.java:188-189`; `FilesSynchronizationManager.java:58-63`).
     `files` = the number of file tasks.
  3. A first `Transfer` snapshot (B30).

  Log `tracing::info!("Downloading from repository: {name} on url: {host_url}")`
  (`service/ConnectionService.java:339-340`).
- B4. **Nothing to do.** If no task is pending, return `DownloadEnd::Completed` right away (after
  B3 and a final `Transfer`), with no connection (`ConnectionDownloadProcessor.java:46-47, 139-180`).
- B5. **Directory tasks.** Java pushes directories through the same worker loop
  (`dao/connection/AbstractConnexionDAO.java:339-347`). Rust handles every pending directory task
  **before** the workers start, sequentially and in input order (deviation DV6). It does
  `create_dir_all(destination_dir/name)`, then sets `status = Done` and emits
  `FileStarted` + `FileDone`. A failure becomes a file error (B15, message
  `a3s_error::messages::cannot_create_directory(path)`, `exception/CreateDirectoryException.java:12-21`)
  that counts toward `max_errors` (B23). Directory tasks are never sent to the network.
- B6. **File order.** Java copies the list into a `Stack` and `pop()`s, so the **last** task goes
  first (`ConnectionDownloadProcessor.java:34-35, 202-209`). Rust keeps this LIFO order: workers
  take the pending file task with the highest index that has not been taken yet. The order
  can be observed in logs and events, which keeps tests deterministic with K = 1.

### One file task, full download (`complete == 0`)

- B7. **Destination.** `create_dir_all(destination_dir)` before anything else. On failure: file
  error `cannot_create_directory` (`AbstractConnexionDAO.java:243-248`).
- B8. **Remote and local names** (`AbstractConnexionDAO.java:264-280`):
  - `compressed == true`: remote `"{relative_path}.zip"`, local target `destination_dir/"{name}.zip"`,
    expected size `compressed_size`.
  - otherwise: remote `relative_path`, local target `destination_dir/name`, expected size `size`.

  Rust writes into `"{local target}.part"` (Java `PART_EXTENSION`, `dao/DataAccessConstants.java:22`)
  and renames at the end (DV3). Java writes straight into the target, after deleting it.
- B9. **Resume decision** (`AbstractConnexionDAO.java:282-293`). Resume from offset
  `len(part)` iff `task.status == Running` **and** the `.part` exists **and**
  `0 < len(part) < expected`. Otherwise delete any existing `.part` and start at offset 0.
  Log `tracing::info!("Resuming file: {part abs path} at offset: {offset}")` or
  `tracing::info!("Downloading file: {part abs path}")` (`:287-288, 292`). `Running` only comes from
  an earlier attempt in the **same** process: a pause, a cancel, a retry or an error. After a
  restart WP08 produces `Pending` tasks, so a leftover `.part` is discarded. This is Java's
  behaviour: `DownloadStatus` is not persisted.
- B10. **Status.** Set `status = Running` before the transfer (`:295`). Set `Done` only when the
  file has been finalized (B13) and the run is not cancelled (`:302-306`).
- B11. **Transfer.** `transport.download_file(remote, part, offset, &worker_ctx)`. The transport
  implements the per-protocol resume:
  - HTTP sends `Range: bytes={offset}-` when `offset > 0` (`dao/connection/http/HttpDAO.java:163-169`,
    `DataRange.java:48-54`). A `200` reply restarts from 0.
  - FTP sends `REST offset` (`dao/connection/ftp/FtpDAO.java:159`; fixed by WP06).
  - SFTP seeks to the offset (`dao/connection/sftp/SftpDAO.java:166, 229-232, 477-489`).
  - WebDAV always restarts from 0 (`dao/connection/webdav/WebdavDAO.java:188`).

  `worker_ctx` = `TransferCtx { cancel: run token (B25), progress: per-attempt counter, throttle: Some(request.throttle) }`.
- B12. **Completeness.**
  - HTTP and WebDAV: the transport compares with `Content-Length` (+ offset) and returns
    `Error::Incomplete` (`HttpDAO.java:360-370`).
  - FTP(S) and SFTP: Java's FTP compares the local length with the server's `MLST` size
    (`FtpDAO.java:383-403`). Rust compares the returned final length with the task's expected
    size from B8. If it is smaller, treat the attempt as `Incomplete { expected, actual }` (DV13).
    If it is larger, accept the file and `tracing::warn!`.
  - Empty files: a 0-byte remote file must leave a 0-byte final file (`HttpDAO.java:366-369`,
    `FtpDAO.java:398-400`). Create the `.part` even if the transport wrote nothing.
- B13. **Finalize.** `fsync`, then rename `.part` → local target, replacing any existing file. A
  rename failure is a file error (`LocalIo`, kind from `ErrorKind::from_io`; DV12). Then
  `status = Done` and `FileDone`. If the task is compressed, build a `DownloadedZip`
  (relative path, zip path, target path `destination_dir/name`, `sha1`, `size`), call
  `zips.submit(zip.clone())` **immediately**, and add it to `report.downloaded_zips`. This
  happens for every compressed leaf. Java only hands names that contain `".pbo.zip"`
  (lower-cased) to the unzipper (`ConnectionDownloadProcessor.java:98-104`), which leaves
  downloaded `.ebo.zip` files unextracted (DV9).
- B14. **Resume retries.** On `Incomplete`, Java logs `"WARNING: " + message`, disconnects and
  calls itself recursively. The status is `Running`, so the next attempt resumes. There is no
  bound (`AbstractConnexionDAO.java:308-311`). Rust (DV4) retries an attempt that failed in
  one of these ways:
  - (a) `Incomplete` (transport or B12) after this attempt received ≥ 1 byte: retry on the
    same transport.
  - (b) A connection-class error (B15) after this attempt received ≥ 1 byte: reconnect the
    worker's transport first.
  - (c) A connection-class error with 0 bytes on a transport that had already completed at
    least one file: reconnect and retry, **once per task**. Java opened a fresh connection
    per file (`AbstractConnexionDAO.java:299-307`), so an idle-closed connection never
    surfaced there.

  Each retry logs `tracing::warn!("WARNING: {message}")` and goes back to B9. B9 then resumes,
  because the status is `Running`. At most `MAX_RESUME_RETRIES = 3` retries per task. When
  they are exhausted, or when the case is not retryable:
  - `Incomplete` becomes a file error. Message `a3s_error::messages::incomplete_transfer(abs local target, actual, expected)`
    (`exception/IncompleteFileTransferException.java:9-15`, typo `"Incompete"` kept). Kind
    `IncompleteTransfer`.
  - A connection-class error becomes **connection lost** (B24).

  If reconnecting fails, that is connection lost.
- B15. **Error classification** (`ConnectionDownloadProcessor.java:106-121`,
  `exception/ConnectionExceptionFactory.java:23-60`), applied after B14:
  - The run token is cancelled, or the error is `Cancelled`: **cancelled**. No error is
    recorded and the status stays `Running` (`ConnectionDownloadProcessor.java:115`,
    `AbstractConnexionDAO.java:312-317, 332-336`).
  - **Connection-class**: the transport error has `is_connection_lost() == true` and is not
    `Incomplete` and is not a local I/O error. Local I/O means `Error::Io(e)` with
    `e.kind()` in {`StorageFull`, `ReadOnlyFilesystem`, `QuotaExceeded`, `FileTooLarge`,
    `IsADirectory`, `NotADirectory`, `InvalidFilename`, `PermissionDenied`, `NotFound`,
    `AlreadyExists`, `DirectoryNotEmpty`, `CrossesDevices`, `ResourceBusy`,
    `ExecutableFileBusy`}. Java: `SocketException`/`SocketTimeoutException` set
    `downloadConnectionError` and are **not** added to the error list (`:116-117`).
  - Everything else is a **file error**. It is appended to `report.errors`, emitted as
    `FileFailed`, and the worker continues with the next task (`:118-120`).

  The message of a transport error follows WP07 B13 "Fetch" rules, with the B8 remote path
  (`.zip` included) as `relative`. HTTP/WebDAV:
  `"Failed to connect to the HTTP server on url: {host_url}/{relative}"` (`HttpDAO.java:206-212`,
  `WebdavDAO.java:211-216`). FTP/SFTP `NotFound`: FTP/SFTP connect core
  (`FtpDAO.java:190-207`). Other FTP/SFTP errors: `"Failed to retrieve file: /{relative}"`
  (`FtpDAO.java:406-411`, `SftpDAO.java:242-246`). The detail and the
  `a3s_error::messages::connection` composition are also as in WP07 B13. Kinds follow WP07 B14.
- B16. **Retry state.** Each attempt starts from a fresh per-attempt progress counter. The bytes
  already on disk (the resume offset) count toward progress (B30) but not toward "received in
  this attempt".

### One file task, zsync partial download (`complete > 0`)

- B17. **Trigger.** `kind.complete > 0.0` and the worker's transport is HTTP(S)
  (`AbstractConnexionDAO.java:264, 319-338`). Only `HttpDAO.getFileCompletion` can produce
  `complete > 0`. FTP, SFTP and WebDAV return 0 and their `downloadPartialFile` is unsupported
  (`FtpDAO.java:426-428, 733-735`, `WebdavDAO.java:245-247, 415-417`, `SftpDAO.java:351-353`).
  With any other transport, fall back to a full download (B22). The local file is the
  **uncompressed** `destination_dir/name`, even for compressed leaves, and no `.zip` is
  involved (`HttpDAO.java:495-502`). Set `status = Running` (`AbstractConnexionDAO.java:323`).
- B18. **Control file.** `transport.fetch("{relative_path}.zsync", &control_ctx)`
  (`HttpDAO.java:497-500, 526-538`). `control_ctx` has no throttle and its own throw-away
  progress counter. Java fetches with `doRecordProgress = false, doControlSpeed = false`.
  Parse with `a3s_zsync::ControlFile::parse`.
- B19. **Match and plan** (`HttpDAO.java:508-511`). Run `match_blocks(&control, File(local), cancel_flag)`
  in `spawn_blocking`. `cancel_flag` is an `AtomicBool` set when the run token is cancelled.
  Then `Plan::new(&control, &matches, Plan::MAX_BLOCKS_PER_RANGE)`. The 100-block limit comes
  from `jazsync/MetaFileReader.java:71, 442-444` and `jazsync/FileMaker.java:220-236`.
- B20. **Range requests** (`FileMaker.java:131-154`). Each range is fetched in ascending order
  with `transport.fetch_range(relative_path, range, &worker_ctx)`, throttled and counted.
  Java sends `Range: bytes={first*bs}-{(last+1)*bs}`, which asks for one byte too many (its
  `DataRange` end is exclusive but HTTP's is inclusive). Rust sends the exact
  `bytes={start}-{end-1}` produced by the transport from the clipped `Plan` range (DV10).
  Log `tracing::info!("Downloading partial file: {part abs} at range [{start}-{end-1}]")`
  (`FileMaker.java:139-141`).
- B21. **Assemble** (`FileMaker.java:96-197`). In `spawn_blocking`, run
  `assemble(&control, &matches, File(local), ChannelReader, File(part))`. `part` =
  `"{destination_dir/name}.part"` (`FileMaker.java:99-100`). The remote bytes flow through a
  bounded `tokio::sync::mpsc` channel (capacity 4 range bodies). The blocking side reads with
  `blocking_recv`. When the async side drops the sender after an error or a cancel, the reader
  returns an I/O error. `assemble` verifies the control file's SHA-1. Java does not (DV10).
  On success, fsync and rename `part` → `destination_dir/name`. Java deletes the target and
  then calls `renameTo`, ignoring its result (`FileMaker.java:183-186`; DV12). Then
  `status = Done` and `FileDone`. Nothing goes to the zip sink. The `.part` is deleted on
  every failure and on cancel, as Java's `finally` does (`FileMaker.java:194`). Partial zsync
  output is never resumed.
- B22. **Partial-transfer fallback** (DV10). The task falls back to the full-download path
  (B7–B14, with `complete` treated as 0: compressed leaves fetch `.zip`) when any of these
  happens:
  - the `.zsync` fetch returns `NotFound`;
  - `ControlFile::parse` fails;
  - `control.header.length != task size`;
  - the local file is missing or unreadable;
  - `fetch_range` returns `Error::Unsupported`, i.e. the server ignored `Range`;
  - `assemble` returns `ChecksumMismatch`;
  - the transport is not HTTP (B17).

  Log `tracing::warn!("Partial transfer failed for {relative_path}: {reason}; downloading the whole file")`
  and fall back once per task. Other errors are classified as in B15. Java wraps them with
  core `"Failed to retrieve file: /{relative_path}.zsync"` (`HttpDAO.java:513-518`), and Rust
  uses that core for zsync-phase errors that are not transport errors (`DownloadError::Zsync`).
  Connection-class errors with 0 bytes on a reused transport follow B14 (c).

### Run-level policy

- B23. **Max errors** (`ConnectionDownloadProcessor.java:122-126, 145-151, 225-227`). After each
  task the worker checks `errors.len() >= max_errors`. `max_errors` comes from
  `request.max_errors`, clamped to ≥ 1, and is `SyncOptions::max_errors = 10`. When the limit
  is reached the run ends with `DownloadEnd::TooManyErrors { limit: max_errors }`, and all
  in-flight transfers are cancelled through the run token (B25). Java's worker finishes its
  current file, but the UI cancels everything at once on the error callback
  (`ui/repository/workers/AddonsDownloader.java:312-336`). Errors that in-flight tasks raise
  after the stop are **not** recorded (cancelled). With K = 1 the report holds exactly
  `max_errors` errors.
- B24. **Connection lost** (`ConnectionDownloadProcessor.java:116-117, 123-125, 142-144`;
  `AddonsDownloader.java:338-362`). The first connection-lost condition (B14/B15/B27) stops the
  run: cancel the run token and emit `SyncEvent::ConnectionLost` **exactly once**. The result
  is `DownloadEnd::ConnectionLost { error }`, carrying the first connection error. The
  connection error is not added to `report.errors`. Errors collected earlier stay there.
  `.part` files of interrupted tasks are kept, and their status stays `Running`.
- B25. **Cancellation** (`service/ConnectionService.java:551-556`,
  `FilesSynchronizationProcessor.java:340-347`, `AddonsDownloader.java:389-416`). `cancel` is
  the caller's token (pause and cancel are the same thing for the executor). Internally, use a
  child **run token**. B23 and B24 cancel the run token, never the caller's token. When the
  caller's token fires:
  - `download` returns `DownloadEnd::Cancelled` within **1 s**, even during a stalled read, a
    connect, `match_blocks` or `assemble`;
  - in-flight full-download tasks keep `status = Running` and their `.part` files, so a later
    call resumes them (B9);
  - zsync `.part` files are deleted (B21);
  - no `FileFailed` is emitted after the cancel.
- B26. **End precedence.** Caller cancelled > `ConnectionLost` > `Failed` (B27) >
  `TooManyErrors` > `Completed`. Java checks the connection error before too-many-errors
  (`ConnectionDownloadProcessor.java:141-151`). `Completed` covers "finished, possibly with
  file errors". Java's "end" versus "end with errors" split happens after unzip
  (`:162-180`) and is WP10's job.
- B27. **Worker connect.** Each worker runs `Transport::connect(protocol, options)`, raced against
  the run token. Java calls `checkConnection` per DAO (a `.a3s/sync` request) before starting
  its thread. A failure there marks the DAO inactive and reports connection lost when no
  other DAO is downloading (`ConnectionDownloadProcessor.java:49-73`, `AbstractConnexionDAO.java:136-142`).
  Rust: no probe request (DV2). If some workers connect, the run goes on with those, and the
  failure is logged with `tracing::warn!`. If **no** worker connects, the run ends with
  `ConnectionLost` when the first error is connection-class, and with
  `DownloadEnd::Failed { error }` otherwise (for example `Unauthorized`, `InvalidProtocol` or
  `InsecureTlsRefused`; DV11).
- B28. **Final state.** Before returning:
  - every task's `status` is `Done` (finalized), `Running` (attempted, not finalized) or
    `Pending` (never taken);
  - all worker transports are closed with `Transport::close`;
  - the monitor has stopped;
  - a final `Transfer` snapshot and `ActiveConnections { active: 0 }` have been emitted.

  `report.files_done` counts tasks finalized in this call.

### Progress, speed, throttling, monitor

- B29. **Active connections** (`ConnectionDownloadProcessor.java:90-96`,
  `FilesSynchronizationProcessor.java:274-298`). A worker is active from `FileStarted` until its
  task finalizes or fails. Emit `ActiveConnections { active }` whenever the count changes.
  `report.max_active_connections` is the maximum seen (Java's report value,
  `FilesSynchronizationProcessor.java:294-297`).
- B30. **Transfer progress** (`FilesSynchronizationProcessor.java:205-231`,
  `AbstractConnexionDAO.java:609-635, 669-743`). `TransferProgress` fields:
  - `total` = the `TransferTotal.bytes` value.
  - `transferred` = Σ download size of `Done` file tasks (including those `Done` before the
    call) + Σ over in-flight file tasks of `min(offset + attempt_bytes, download_size)`. Java
    counts only the in-flight bytes of the semaphore holder. Rust counts every worker (DV7).
  - `current_file` = the relative path of the reporter's task (B31). `None` if there is none.
  - `current_file_percent`:
    - full download: `(offset + attempt_bytes) * 100 / expected` (`AbstractConnexionDAO.java:627-634`,
      with `complete = 0`);
    - zsync: `attempt_bytes * 100 / plan.download_size()`. Java always reports 0 here,
      because `expectedFileSize` stays 0 in the zsync branch (DV7);
    - 0 if the denominator is 0; clamped to 100.
  - `remaining`: Java uses `(total - resumed - value) * elapsed / (resumed + value)`
    (`:211-222`). Rust uses `(total - transferred) * elapsed / run_bytes`, where `run_bytes`
    is the bytes received in this call and `elapsed` runs from the B3 start. It is `None`
    while `run_bytes == 0` (DV7).

  `Transfer` events are emitted by the monitor every `TRANSFER_EVENT_INTERVAL = 100 ms`, only
  when the snapshot changed (WP07 `RateLimiter` ≤ 10 Hz), plus at start (B3) and at the end (B28).
- B31. **Reporter slot** (Java semaphore: `ConnectionDownloadProcessor.java:80-82, 108-112, 130-133, 182-188`,
  `AbstractConnexionDAO.java:355-357, 699-702`). At most one worker is the reporter. A worker
  that starts a task takes the slot if it is free. It keeps the slot across successful tasks
  and releases it on a task failure or when it exits. On release, the slot goes to the
  lowest-numbered active worker, if any.
- B32. **Speed.** Every `SPEED_INTERVAL = 500 ms` the monitor emits
  `Speed { bytes_per_second = Δrun_bytes / Δt }`. This includes 0 during stalls. Java samples
  per-DAO speeds and only when progress callbacks fire (`FilesSynchronizationProcessor.java:247-262`,
  `AbstractConnexionDAO.java:695-697`). Average for the report (Java quirk, kept): if
  `speed > 0`, then `avg = if avg == 0 { speed } else { (avg + speed) / 2 }`
  (`FilesSynchronizationProcessor.java:263-270`), giving `report.average_speed`.
- B33. **Throttle.** Java divides `maximumClientDownloadSpeed` by the number of active connections
  and makes each connection sleep `speed / limit * 125 ms` per 4 KiB once it exceeds its share
  (`FilesSynchronizationProcessor.java:283-288`, `ConnectionService.java:543-547`,
  `AbstractConnexionDAO.java:792-812`). Rust passes one shared `Arc<Throttle>` (a global limit
  in bytes/s, 0 = unlimited) in every worker context (DV5). The caller may call
  `request.throttle.set_limit(..)` during a run. Java re-reads the setting at each change in
  active connections. Control files are never throttled (B18). Range fetches are throttled
  (`FileMaker.java:145-146`, `doControlSpeed = true`).
- B34. **Disk usage** (`service/synchronization/FilesSynchronizationDiskUsageListerner.java:32-71`).
  Only when `request.disk_usage_path` is `Some`, as Java requires a destination and an observer
  (`:34-36`). Every `DISK_USAGE_INTERVAL = 500 ms` the monitor reads the free space of that
  path with `fs4::free_space` in `spawn_blocking` (Java `File.getFreeSpace`) and emits
  `DiskUsage { bytes_per_second = disk_usage_rate(free_before, free_after, Δt) }`. An increase
  in free space (files being deleted) counts as 0 (`:53-61`). A failed read emits nothing and
  logs at debug level.
- B35. **Connection waiting** (`FilesSynchronizationDiskUsageListerner.java:73-110`; the separate
  `FileSynchronizationConnectionWaitingListener` is dead code, `FilesSynchronizationProcessor.java:177-179`).
  Every `WAITING_TICK = 1 s`, emit `ConnectionWaiting { seconds }`, where `seconds =
  WaitingCounter::tick(any_active, unzip_idle = zips.is_idle(), disk_usage = last DiskUsage
  value or 0, bytes_advanced = run_bytes changed since the previous tick)`. The counter:
  - becomes 0 when there is no active worker (`:91-92`);
  - else becomes 0 when unzip is busy (`:94-95`);
  - else becomes 0 when `disk_usage > 0` (`:96-97`);
  - else becomes 0 when `bytes_advanced` (Rust addition, DV8: free space lags on some file
    systems);
  - else adds 1 (`:98-99`).

  The UI's 15 s threshold is WP07's `WAITING_FOR_SERVER_THRESHOLD`
  (`AddonsDownloader.java:373-387`).
- B36. **Per-file events.** For each task taken (including directories, B5), emit
  `FileStarted { relative_path }` once, not once per retry. Then exactly one of
  `FileDone { relative_path }` or `FileFailed { relative_path, error: EventError }`, or neither
  if the task was interrupted by cancel or connection lost. `EventError` = `{ kind, message,
  relative_path: Some(task.relative_path) }`.
- B37. **No `Finished`.** WP09 never emits `SyncEvent::Finished`. Java's end callbacks fire after
  unzip (`ConnectionDownloadProcessor.java:162-180`), and that is WP10's job. WP10 builds the
  `Outcome` with `DownloadReport::outcome(extra_errors)`, where `extra_errors` are the unzip
  errors (Java appends them, `:166`), and emits `Finished`. After `ConnectionLost`,
  `outcome()` returns `None`: `ConnectionLost` is the terminal event, as in Java
  (`FilesSynchronizationProcessor.java:334-338`).
- B38. **Plan write-back.** `apply_statuses(tree, tasks)` sets `download_status` on the
  `PlanTree` node at each task's `relative_path` (missing nodes are ignored). WP10 and WP26 use
  it so the tree view shows `Done`/`Running`. Java mutates the DTO nodes directly
  (`AbstractConnexionDAO.java:295, 303, 323, 328, 345`).

### Java quirks to preserve (wire-visible)

These are request-level details a repository server sees. Nothing is written to a repository.
- Remote paths: `relative_path` for uncompressed files, `"{relative_path}.zip"` for compressed
  ones, `"{relative_path}.zsync"` for control files (`AbstractConnexionDAO.java:272-279`,
  `HttpDAO.java:497-498`).
- Resume over HTTP uses an open-ended `Range: bytes={offset}-` (`DataRange.java:48-54`).
- zsync range requests cover at most 100 blocks each, one request per group of consecutive
  missing blocks, in ascending order (`FileMaker.java:131-154, 220-236`). Only the inclusive
  end changes (DV10).
- Headers (`User-Agent: ArmA3Sync`, `Accept-Encoding: identity`, no-cache, Basic auth) come from
  `a3s_transport` unchanged.

### Java quirks preserved for user-visible parity (local-only; kept by default)

- `MAX_DOWNLOAD_ERRORS = 10` and the "at least {limit}" message (WP07 B39).
- Connection errors are not listed as file errors. Errors after a cancel are dropped (B15).
- Resume works only within a session (status `Running`, not persisted). Otherwise the partial
  file is discarded (B9).
- LIFO task order (B6).
- The "transferred" total counts the download size of `Done` tasks, not the bytes actually
  received (B30).
- Average speed is a running mean `(avg + sample) / 2` (B32).
- A disk-usage increase in free space counts as 0, and the waiting counter resets while unzip
  runs (B34, B35).
- Texts: `"Incompete file size transfer: …"`, `"Cannot create directory …\nPlease checkout file access permissions."`,
  the log lines in B3, B9, B14 and B20.

### Java quirks that may be dropped (local-only; needs an approved deviation)

- DV1. One `Transport` per worker, reused across files. Java connects, and for FTP logs in
  again, for every file (`AbstractConnexionDAO.java:299-307`). The reconnect-once rule (B14 c)
  covers idle-closed connections.
- DV2. No per-connection `checkConnection` probe of `.a3s/sync` before the workers start
  (`ConnectionDownloadProcessor.java:52`).
- DV3. Full downloads go to `<target>.part`, followed by an atomic rename. Java deletes the old
  file and writes the target in place (`AbstractConnexionDAO.java:290, 301`). The old file
  stays valid until the new one is complete.
- DV4. Bounded resume retries (3, and only while bytes arrive) instead of unbounded recursion on
  `Incomplete` (`AbstractConnexionDAO.java:308-311`). A mid-body connection drop is resumed
  instead of being treated as connection lost.
- DV5. A global token-window `Throttle` instead of per-connection sleeps.
- DV6. Directory tasks are created first and sequentially, not interleaved with files.
- DV7. Progress counts every worker's in-flight bytes, zsync files report a real percent, the
  remaining time uses bytes received in this run, and speed is emitted every 500 ms even
  during a stall.
- DV8. The waiting counter also resets when network bytes arrived during the last second.
- DV9. Every compressed leaf's `.zip` is handed to the unzipper, `.ebo.zip` included. Java only
  matches `".pbo.zip"`.
- DV10. zsync: exact range ends (Java asks for one extra byte per group), SHA-1 verification of
  the assembled file, and a fallback to a full download (B22). Java leaves a corrupt file or
  reports an error.
- DV11. If no worker can connect, a non-connection error is reported as `Failed { error }`
  instead of "connection lost". A partial connect failure doesn't emit a spurious
  `ConnectionLost` (Java's check at `ConnectionDownloadProcessor.java:61-71` races thread
  start-up).
- DV12. A failed rename is an error. Java ignores `renameTo`'s result after deleting the target,
  so the file is lost silently (`FileMaker.java:183-186`).
- DV13. FTP(S) and SFTP final length is checked against the task's expected size. Java uses
  `MLST` for FTP and has no check for SFTP.

### Errors, cancellation, progress

- Retries: only B14. Nothing else is retried. Run-level retries after `ConnectionLost` are the
  UI's business (WP26 `ConnectionLostDialog`).
- Collected errors: file errors (B15), directory creation (B5, B7), rename (B13), exhausted
  `Incomplete` (B14), zsync-phase errors that don't fall back (B22).
- Abort conditions: `max_errors` reached (B23), connection lost (B24), no worker connected (B27),
  caller cancel (B25).
- Cancel latency: `download` returns within 1 s of `cancel.cancel()` (A10).
- Events emitted (WP07 `SyncEvent`): `Phase(Downloading)`, `TransferTotal`, `Transfer`, `Speed`,
  `DiskUsage`, `ActiveConnections`, `ConnectionWaiting`, `FileStarted`, `FileDone`,
  `FileFailed`, `ConnectionLost`. Never `Finished`, `Progress` or `MetadataFetched`.

### Concurrency

- Java runs K download threads (one per DAO, `ConnectionDownloadProcessor.java:53-59`), two
  listener threads (`FilesSynchronizationDiskUsageListerner.java:38-110`) and an unzip pool of
  `availableProcessors()` threads (`UnZipFlowProcessor.java:24-29`, WP10).
- Rust runs K worker futures, each owning a `Transport`, plus one monitor future, either in a
  `tokio::task::JoinSet` or joined in place. Dropping the `download` future must abort all of
  them (`JoinSet` aborts on drop). `match_blocks`, `assemble` and `fs4::free_space` run on the
  blocking pool. The shared state (task queue, statuses, errors, reporter slot, counters) is
  behind one `parking_lot::Mutex` plus atomics. No lock is held across an `.await`.
- At most K transfers are in flight at once. That includes zsync range fetches and control
  files, because each worker does one thing at a time.
- Memory per zsync task stays bounded: at most 4 range bodies of ≤ 100 × 8 KiB in the channel.
- The future returned by `download` is `Send`. `ZipSink` is `Send + Sync` and `submit` must
  not block.

## Wire-compat notes

- Classes read or written: none. Tasks come from WP07/WP08 types. `.zsync` files are parsed with
  the existing `a3s_zsync::ControlFile::parse`.
- Byte identity is required only for the downloaded content: a full download stores exactly the
  server's bytes (`.pbo.zip` included). A zsync download must reproduce the server file
  byte-for-byte (SHA-1 verified, B21). Semantic compatibility of `.pbo.zip` (Java can
  extract it) is WP10's concern. WP09 stores the zip verbatim.
- Fixtures: none from the JDK harness. Tests build `.zsync` files with
  `a3s_zsync::ControlFile::generate`, which is already golden-tested against Java in `a3s_zsync`.
