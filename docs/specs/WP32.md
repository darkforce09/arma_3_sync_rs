## Scope

- **Update session** (`apply`): the rest of Java `Service` (cached manifest, `isUpdateAvailable`,
  `getSize`, `download`, `install`, `clean`, `cancel`) as an async `UpdateSession` with `check` and
  `apply`. It emits progress events that the CLI (WP19) and the GUI dialog (WP29/WP22) render.
- **Self-replace of the running executable** (`apply::replace`): a `FileReplacer` for WP31's
  `install_staged`. On Unix it renames over the target. On Windows it falls back to
  rename-away + rename-in when the target is locked (the running `.exe`). Leftover cleanup runs at
  startup.
- **Release layout checks** (`apply::install`): before anything is written, check that the archive
  contains the platform binary at its root and no portable user data. Force the exec bit on Unix.
  Detect installs that cannot be self-updated (AppImage, macOS `.app`, a Java installation dir, a
  cargo `target/` dir).
- **Elevation** (`elevation`): permission-failure classification, the install-dir write probe, the
  `requires_elevation` rule (Windows only), and the PowerShell `Start-Process -Verb RunAs` launcher
  (Java mechanism, no `unsafe`). Also the parent ↔ elevated-child protocol: a hidden subcommand,
  a startup marker, a result file and the exit code. The elevated child only **installs an
  already downloaded and SHA-256-verified archive**. The non-elevated parent waits for it, then
  relaunches the app without elevation (design change, Q1).
- **Console flows** (`apply::console`): ports of `Console.execute` (exit 0/1/2), `Console.checkOnly`
  (exit 0/1/2), the main app's legacy `-update` (`CommandGeneral.checkForUpdates`), and the Java
  updater flag grammar (`-dev -console -check -github -manifest`). All printing goes to injected
  writers.
- **Relaunch** (`apply::relaunch`): after a GUI update, release the single-instance lock (WP15
  `InstanceGuard`), then start the installed binary (`-dev` when in dev mode). Port of
  `Updater.launchApplication`.
- **Strings for the GUI** (`apply::text`): every user-visible string of `Updater.java` and
  `MainPanel.checkForUpdates`, plus the mapping from `ApplyError` to dialog title and body. WP29
  and WP22 only render them.

## Behaviour contract

### Context and session (`apply`)

- B1. `UpdateContext` carries the inputs that Java read from system properties:
  `exe_path` (Java `installationPath()/Arma3Sync.exe`), `install_dir` (Java
  `a3s.updater.installationPath`, `U/dao/DataAccessConstants.java:25-30`), `current_version` (Java
  `a3s.updater.currentVersion` = `Version.getVersion()`, `service/UpdaterProcess.java:55`), `dev`,
  `source`, `overrides` (Java `-Da3s.updater.*`), `elevated`, `os`, `target`, `appimage_env`, `diag`.
  `UpdateContext::for_current_process(current_version, dev, source, user_config_dir, diag)`:
  - `exe_path` = `std::env::current_exe()`, resolved **once, at construction**. On Unix it is
    canonicalized, so a symlink such as `/usr/local/bin/arma3sync` resolves to the real file. On
    Windows it is not canonicalized (no `\\?\` prefix). Reason: after a rename-over on Linux,
    `/proc/self/exe` reads `… (deleted)`, so relaunch must use the path captured before the install.
  - `install_dir` = `exe_path.parent()`.
  - `overrides` = WP31 `ConfigOverrides::from_env()`. `user_config_dir` is set to the caller's value
    (`AppDirs::config_dir()`) unless the env var already set it. Java always passed the main app's
    configuration folder (`service/UpdaterProcess.java:54`).
  - `target` = WP31 `host_target()`. `os` = `a3s_paths::PlatformEnv::current()?.os()`.
    `elevated = false`. `appimage_env` = env `APPIMAGE`.
  `UpdateContext::new(exe_path, install_dir, current_version, os)` builds one for tests, with every
  other field at its default (`dev=false`, `source=Configured`, `elevated=false`, `target=host_target()`,
  `diag=DiagnosticLog::disabled()`, overrides default).
- B2. `source_for_preference(prefer_github: bool) -> UpdateSource`: `true` → `GitHub`, `false` →
  `Manifest`. The main app never used `CONFIGURED` (`service/UpdaterProcess.java:58,65-67`). A missing
  preference means `true` (`domain/Preferences.java:81-83`, WP03 already defaults it).
- B3. `UpdateSession::new(ctx)` never fails. `check(&self, cancel)`:
  1. If `ctx.target` is `None` → `ApplyError::NoTarget`.
  2. Load the config lazily and cache it (`UpdateConfig::load(install_dir, overrides)`). Build
     `HttpClient::new(&config)`. Any error from here up to step 3 → `ApplyError::Metadata(e)`.
     Java maps config errors to the same "Can't read update metadata." (`U/service/Service.java:52,64-66`).
  3. `resolve_release(config, http, ResolveRequest{install_dir, dev, preference: source, target}, diag, cancel)`.
     WP31 already logs the metadata lines. Errors → `Metadata(e)`, but `UpdateError::Cancelled` →
     `ApplyError::Cancelled`.
  4. `available = is_newer(release.version, current_version)`. Diag info
     `Update comparison: current=<c>, target=<v>, available=<b>` (`U/service/Service.java:75-82`).
  5. Return `CheckOutcome::Available{release, current}` or `UpToDate{latest: release, current}`.
  The resolved release is cached in the session, keyed by `dev`. Java cached it the same way
  (`U/service/Service.java:48-49`). A second `check` returns the cached value without network I/O.
- B4. `apply(&self, release, on_event, cancel) -> Result<ApplyOutcome, ApplyError>` runs, in order.
  The Java sequence is `getSize → setDownload → download → install → clean`
  (`U/console/Console.java:43-53`, `U/ui/Updater.java:83-93`):
  1. Busy guard. A second concurrent `apply` on the same session → `ApplyError::Busy`.
  2. **Preflight** (B5). On error, return it before any network request.
  3. `on_event(Preparing)`. Total size = `release.size` if `> 0`. Otherwise
     `http.content_length(download_url)`. An error there → `ApplyError::SizeUnknown(Some(e))`.
     `Ok(None)` → proceed with `total = None` (local-only deviation D1; Java aborted with
     `Can't find update file on repository.`, `U/service/Service.java:103-107`). Diag info
     `Preparing update download: file=<f>, transport=HTTP` (`:129-130`).
  4. `StagingDir::new()`. Then `download_release(...)` with the progress callback mapped to
     `on_event(Downloading{bytes, total})` and `allow_unverified = false` (WP31 Q2). Diag info
     `Downloading update: file=<f>, size=<size>, transport=HTTP` before, and
     `Update download completed: file=<f>` after (`:139-150`). Errors → `ApplyError::Download(e)`.
     `UpdateError::Cancelled` → `ApplyError::Cancelled`.
  5. If `cancel` is cancelled now → `Cancelled`. Java checked `isCancelled()` after the download
     (`U/ui/Updater.java:88`). From here on nothing can be cancelled.
  6. If the preflight said `NeedsElevation` → elevated install (B20). Otherwise
     `on_event(Installing)`, then the in-process install (B10) in `spawn_blocking`.
  7. If the in-process install fails with `is_permission_failure` (B15): when
     `os == Windows && !elevated` → diag info
     `Install failed with a permission error; requesting UAC.`, then elevated install of the
     **same verified archive** (B20). When `os != Windows && !elevated` →
     `ApplyError::ElevationUnavailable`. When `elevated` → diag error
     `Elevated updater still cannot write to the installation; not retrying UAC.` and return the
     install error (`U/console/Console.java:54-76`, `U/ui/Updater.java:130-155`).
  8. Drop the `StagingDir` on every path, success or error (Java `service.clean()`, `Console.java:77-79`).
  9. Success → `ApplyOutcome{version, install_dir, elevated: bool, report: Option<InstallReport>,
     relaunch: RelaunchPlan::for_context(ctx)}`, and `on_event(Done)`.
- B5. **Preflight** `preflight(ctx, release) -> Result<Preflight, ApplyError>`:
  1. `ctx.target` is `None` → `NoTarget`.
  2. `detect_install_kind` (B12) ≠ `Directory` → `Unsupported{kind}`.
  3. `release.sha256.is_none()` → `Unverified{version}` (WP31 Q2: refuse; XML-only releases can be
     checked but not applied).
  4. `can_write_installation(install_dir)` (B16) → `Preflight::InProcess`.
  5. Else if `requires_elevation(os, elevated, install_dir)` (B17) → `Preflight::NeedsElevation`.
     Diag info `Preflight requires elevation; UAC will be requested after the download.`
  6. Else if `os != Windows && !elevated` → `ElevationUnavailable`. Java downloaded first and failed
     at install time with the same final message (`ElevationSupport.java:73`); Rust fails before the
     download (local-only deviation D2).
  7. Else (elevated and still not writable) → `Preflight::InProcess`. The install then fails and B4.7
     applies.
- B6. `UpdateEvent` (non-exhaustive), in emission order: `Preparing`, `Downloading{bytes: u64,
  total: Option<u64>}` (one per WP31 progress callback), then either `Installing`, or
  `WaitingForElevation` → `ElevatedInstallStarted` (zero or one, see B21) → `Installing`.
  `Done` comes last on success. The fallback path in B4.7 emits `Installing` first, then
  `WaitingForElevation` …. `on_event` is `&(dyn Fn(UpdateEvent) + Send + Sync)`. It is called
  from the task or a blocking thread, never while a lock is held.
- B7. `ApplyError` `Display` (user-facing, used as `<msg>` in B26/B29). Every Java message is
  reproduced:
  - `Metadata(e)` → `Can't read update metadata. {e}`. Java printed only `Can't read update metadata.`
    (`U/service/Service.java:66`); the cause is a local-only addition.
  - `SizeUnknown(_)` → `Can't find update file on repository.` (`U/service/Service.java:106,111`).
  - `Download(e)` → `{e}` (WP31 messages, e.g. `SHA-256 verification failed for the update archive.`).
  - `Install{dir, source}` → `Can't write files to the installation directory '{dir}'. {source}`
    (`U/service/Service.java:167-173`; Java put the exception class simple name before the
    message, local-only).
  - `ElevationUnavailable` → `UAC elevation is only available on Windows.` (`ElevationSupport.java:73`).
  - `ElevationNotGranted(m)` / `ElevatedInstallFailed(m)` → `{m}` (B22).
  - New (Rust-only) texts: `NoTarget` → `Automatic updates are not available for this platform.`;
    `Unsupported{kind}` → `This installation cannot be updated automatically ({kind}). Download the
    new version manually.` (kind names: `AppImage`, `macOS app bundle`, `Java ArmA3Sync installation`,
    `development build`); `Unverified{version}` → `Update {version} has no SHA-256 checksum and
    cannot be installed automatically.`; `Layout(m)` → `{m}`; `Cancelled` → `Update cancelled.`;
    `Busy` → `An update is already running.`
  - `ApplyError::needs_admin()` is true for `ElevationUnavailable` and `ElevationNotGranted`.
    `ApplyError::is_permission_failure()` = B15 applied to `self`.

### Installing a verified archive (`apply::install`)

- B10. `install_verified_archive(archive, install_dir, os, replacer, diag) -> Result<InstallReport, ApplyError>`.
  The same function serves the in-process path and the elevated child. Order (WP31 B35 split open
  so that B11 can run between staging and copy):
  1. `cleanup_leftovers(install_dir)` (B14), best-effort.
  2. Diag info `Installing update into <install_dir>` (`U/service/Service.java:160`).
  3. WP31 `validate_archive(archive)`. Error → `UpdateError::Stage{stage: "archive validation", …}`.
  4. Extraction dir = new temp dir with prefix `arma3sync-update-extracted-` in `std::env::temp_dir()`.
     It is always removed on return. WP31 `stage_archive(archive, dir)`. Error →
     `Stage{"archive extraction", …}`.
  5. `check_release_layout(&mut entries, os)` (B11). Error → `ApplyError::Layout(msg)`. Nothing has
     been written to `install_dir` yet.
  6. WP31 `install_staged(install_dir, &entries, replacer)`. Error → `Stage{"installation copy", …}`.
  7. Steps 3, 4 and 6 failing → `ApplyError::Install{dir: install_dir, source}` plus diag error
     `Update installation copy failed.`. Success → diag info `Update installation copy completed.`
     (`U/service/Service.java:158-175`).
- B11. `check_release_layout(entries, os)`:
  - `RELEASE_BINARY_NAME` = `arma3sync.exe` on Windows, `arma3sync` elsewhere (the WP19 binary name).
  - Exactly one entry must have `relative` equal to `RELEASE_BINARY_NAME`. The comparison ignores ASCII
    case on Windows and is exact elsewhere. No such entry → `Update archive does not contain
    <name>.` This guards against archives for another target, or archives with a top-level folder.
  - No entry may equal `a3s_paths::PORTABLE_MARKER` (`arma3sync-rs.portable`), and no entry may be
    `PORTABLE_DATA_DIR` (`arma3sync-rs-data`) or lie under `PORTABLE_DATA_DIR/` (ASCII-case-insensitive).
    Otherwise → `Update archive contains user data path: <relative>`.
  - Unix: if the binary entry's `unix_mode` is `None` or lacks `0o100`, set it to `0o755`.
    Otherwise keep it, masked `& 0o777`. Zips built on Windows have no mode, and WP31 Q8 would
    default them to `0o644`, which would leave a non-executable app.
- B12. `detect_install_kind(exe_path, os, appimage_env) -> InstallKind`. The first matching rule wins:
  1. `os == Linux` and `appimage_env` is non-blank → `AppImage`.
  2. `exe_path.parent()` is named `MacOS`, its parent is named `Contents`, and that one's parent name
     ends with `.app` (ASCII-case-insensitive) → `MacBundle`.
  3. `<install_dir>/ArmA3Sync-Updater.jar` is a regular file → `JavaInstallation`. The Java updater's
     `.a3s-updater-files` there lists Java files. WP31 B31 cleanup would delete them, because the
     Rust archive does not contain them (Q3).
  4. `<install_dir>/.cargo-lock` is a regular file → `Development` (cargo `target/{debug,release}`).
  5. Otherwise → `Directory`. This is the only kind that `apply` accepts. `check` works for every kind.
- B13. `SelfReplacer` (implements WP31 `FileReplacer`; WP31 B36 semantics plus the Windows fallback):
  1. `new_tmp` = sibling of `target` named `.a3s-new-<pid>-<n>-<target file name>`, where `n` is a
     per-replacer `AtomicU32`. `fs::copy(source, new_tmp)`. On Unix set permissions
     `unix_mode.unwrap_or(0o644) & 0o777`.
  2. `fs::rename(new_tmp, target)`. On success, done. On Unix this is the whole algorithm: it is
     atomic and does not hit `ETXTBSY` on a running binary.
  3. Windows only. If step 2 fails, `target` exists, and the error is `PermissionDenied` or
     `raw_os_error() ∈ {5, 32}` (access denied, sharing violation: running image or read-only file),
     then:
     a. `old` = sibling `.a3s-old-<pid>-<n>-<target file name>`.
     b. `fs::rename(target, old)`. On failure, remove `new_tmp` and return the **original** error,
        so B15 can still classify it as a permission failure.
     c. `fs::rename(new_tmp, target)`. On failure, best-effort `fs::rename(old, target)` (rollback),
        remove `new_tmp`, and return this error.
     d. Best-effort `fs::remove_file(old)`. It fails for the running image, which is fine. The file
        stays until B14 removes it.
  4. Any other error: remove `new_tmp` and return the error unchanged.
  The rename-away fallback is written against a small internal `FsOps` trait (copy, rename,
  remove_file, set_mode), so tests can inject Windows error codes on every OS (A10).
- B14. `cleanup_leftovers(install_dir) -> usize` removes regular files whose name starts with
  `.a3s-old-` or `.a3s-new-`. It walks `install_dir` recursively, at most 4 levels deep, does not
  follow symlinks, and skips `PORTABLE_DATA_DIR`. Every error is swallowed and logged at `debug`.
  It returns the number of files removed. Callers: `install_verified_archive` (B10.1), the elevated
  child (B23), and the app at startup (B30). Because B10.1 runs before every install, at most one
  generation of leftovers survives, even in an install dir that is only writable when elevated.

### Elevation (`elevation`)

- B15. `is_permission_failure(err: &(dyn Error + 'static)) -> bool`. Walk `err` and its `source()`
  chain. For each element that downcasts to `std::io::Error`:
  - `kind() == PermissionDenied` → `true` (Java `AccessDeniedException`, `ElevationSupport.java:54`).
  - On Windows, `raw_os_error() ∈ {32, 33}` (sharing or lock violation) → **`false` for this
    element**. A locked file is not a permission problem (port of test
    `doesNotTreatFileLocksAsPermissionFailures`).
  - Otherwise, its `Display` lowercased contains `access denied`, `permission denied` or
    `zugriff verweigert` → `true` (`:55-56,442-448`).
  Elements that are not `io::Error` are only traversed, never text-matched. Java text-matched only
  `IOException`/`FileSystemException`. `NotFound`, `ReadOnlyFilesystem` and WP31 `MissingSource` →
  `false`. `ApplyError::is_permission_failure` forwards to this function on its inner error.
- B16. `can_write_installation(dir, diag) -> bool`. `false` if `dir` is not a directory. Otherwise
  create a temp file in `dir` with prefix `.a3s-write-probe-` and suffix `.tmp`
  (`tempfile::Builder`), then delete it. Success → `true`. A create error → diag info
  `Installation write probe failed: path=<dir>, reason=<io::ErrorKind:?>` and `false`. A delete
  error → diag info `Installation write probe cleanup failed: <probe>`, and the result stays `true`
  (`ElevationSupport.java:199-217`).
- B17. `requires_elevation(os, elevated, install_dir, diag) -> bool` =
  `os == Os::Windows && !elevated && install_dir.is_dir() && !can_write_installation(install_dir)`
  (`ElevationSupport.java:219-225`). `is_windows(os)` = `os == Os::Windows` (Java `os.name` contains
  `win`, `:45-49`).
- B18. Elevation is explicit. `ctx.elevated` is `true` only in the process started through the
  hidden subcommand (B23). Running the app "as administrator" by hand does not count (Java
  `isElevatedProcess` reads the property only, `:184-191`).
- B19. Launching elevated (port of `restart`, `:62-182`):
  - `ElevatedLaunch { program: PathBuf, args: Vec<String>, working_dir: PathBuf }`.
    `parameters()` = `a3s_platform::shortcut::windows_args(&args)` (WP15 K3, MSVCRT quoting). This
    replaces Java `windowsArgumentQuote`, which writes `4n+2` backslashes before an embedded `"`
    (`:425`, `"\\\\".repeat(2n+1)`). That bug is not reproduced.
  - `powershell_command(&self) -> String`, exactly (with `q(x)` = `'` + `x` with `'` doubled + `'`,
    `:413-415`):
    `$ErrorActionPreference='Stop'; try { $p=Start-Process -FilePath q(program) -ArgumentList q(parameters) -WorkingDirectory q(working_dir) -WindowStyle Hidden -Verb RunAs -PassThru } catch { [Console]::Error.WriteLine($_.Exception.Message); exit 1223 }; $null=$p.Handle; $p.WaitForExit(); exit $p.ExitCode`.
    Java's outer command returned immediately (`; exit 0`, `:335-355`), and a second `.ps1` script
    waited for the parent PID (`:357-411`). In Rust the parent waits for the child instead, and the
    child never waits for the parent, so no deadlock and no script file are possible (Q1).
  - `trait ElevatedLauncher: Send + Sync { fn run(&self, launch: &ElevatedLaunch, timeout: Duration) -> io::Result<LaunchExit>; }`
    with `enum LaunchExit { Exited(i32), NotStarted { detail: String }, TimedOut }`.
  - `PowerShellLauncher` (the default; Windows only, other OSes return `NotStarted{"UAC elevation is
    only available on Windows."}`):
    - Spawn `powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -EncodedCommand <b64>`.
      `<b64>` = standard base64 of the UTF-16LE bytes of `powershell_command()`. This avoids
      `CommandLineToArgvW` re-quoting of `"`. Java used `-Command` (`:146-148`).
    - Working dir = `working_dir`, `stdin` null, `stdout`/`stderr` piped, creation flags
      `CREATE_NO_WINDOW` (`0x0800_0000`, via `std::os::windows::process::CommandExt`).
    - Poll `try_wait` every 100 ms up to `timeout`. On timeout, kill the PowerShell process (the
      elevated child keeps running) and return `TimedOut`.
    - Exit `1223` → `NotStarted{detail: stderr trimmed (lossy UTF-8, ≤ 4 KiB)}`. Any other code →
      `Exited(code)`. A spawn error → `Err(io)`.
  - `ELEVATED_INSTALL_TIMEOUT = 10 min`. It covers the time to answer the UAC prompt plus the install.
    Java's 30 s (`:153`) only covered the hand-off.
- B20. Parent side, `elevated_install(ctx, release, archive, staging, launcher, on_event)`:
  1. `ctx.os != Windows` → `ElevationUnavailable`, and the launcher is never called (port of
     `doesNotRequestWindowsElevationOnLinux`). `!ctx.exe_path.is_file()` →
     `ElevationNotGranted("The Arma3Sync executable was not found: <exe>.")`. Java checked the
     updater jar (`:75-78`).
  2. `marker` = `<staging>/elevated.startup` and `result` = `<staging>/elevated.result`, as absolute
     paths that do not exist yet. Java put the marker in the diagnostic log dir (`:100-113`).
  3. `args` = `ElevatedInstallArgs{archive, sha256: release.sha256, version, marker, result,
     debug_log: diag.is_enabled().then(diag.path())}.to_args()`. Diag info
     `UAC restart requested: exe=<exe>, installation=<dir>` (`:81-82`).
  4. `on_event(WaitingForElevation)`. Run `launcher.run(&ElevatedLaunch{program: exe_path, args,
     working_dir: install_dir}, ELEVATED_INSTALL_TIMEOUT)` on a blocking thread. Meanwhile poll every
     100 ms for `marker`. The first time it exists, emit `ElevatedInstallStarted` and then
     `Installing`, once each.

  `Update check failed: <msg>`, `Updating ArmA3Sync to version <v>...`, `\rDownloading: <p>%`,
  `Processing update...`, `ArmA3Sync has been successfully updated to version <v>.`,

  `Administrator rights are required to update this installation.`, `An error occurred: <msg>`,

  `ArmA3Sync-Updater - command not found.`
- Error texts `Can't read update metadata.`, `Can't find update file on repository.`,

### Java quirks that may be dropped (local-only; needs an approved deviation)

- D1. Unknown archive size (`size = 0` and no `Content-Length` on HEAD) aborts the Java update
  (`U/service/Service.java:105-106`). Rust continues with an indeterminate progress bar. A HEAD
  *error* still aborts with Java's message.
- D2. On Linux and macOS, Java downloads first and only fails at install time with the
  admin-required message. Rust fails before the download (B5.6).
- D3. The interactive console `UPDATE` command terminates the whole console with `System.exit(0)`
  (`CommandGeneral.java:586-588`). WP19 returns to the prompt.
- D4. Unknown updater flags exit `0` and are ignored in `-console`/`-check` mode
  (`U/main/ArmA3SyncUpdater.java:47-55`). Rust rejects them with exit `1`.
- D5. Java `windowsArgumentQuote` emits `4n+2` backslashes before an embedded quote
  (`ElevationSupport.java:425`). Rust uses the correct MSVCRT rule (WP15 K3).
- D6. The elevated child does the whole update (re-resolve, download, install), waits for the
  parent PID, and relaunches the app **elevated** (`U/ui/Updater.java:126`, `ElevationSupport.java:366-371`).
  Rust: the parent downloads and verifies, the child only installs, and the parent waits and
  relaunches without elevation (Q1).
- D7. Java stages a copy of the JRE and the updater jar into `%TEMP%\arma3sync-update-runner-*`,
  checks at least 10 copied files plus `release`/`conf`/`lib`/`bin/server/jvm.dll`, and resolves
  `java.exe`/`javaw.exe` (`ElevationSupport.java:227-333`). None of this applies to a single native
  binary. Rust renames the running exe away instead (B13).
- D8. Java forwards 17 `a3s.updater.*` properties to the elevated JVM (`:24-41,95-121`). Rust forwards
  only the B23 arguments.
- D9. Progress printing on every callback, and Java's double-counted bytes (WP31 quirk list). Rust
  prints once per percent change.
- D10. The Java GUI updater re-checks and fails with `No new update is available.` when it was
  started without an update (`U/ui/Updater.java:64-66`). The Rust dialog always receives a resolved
  release.
- D11. `Install` error detail: Java prints `<ExceptionSimpleName>: <message>`. Rust prints the
  WP31 error `Display`. `Metadata` errors append the cause (B7).
- D12. Java's write probe logs the exception class name. Rust logs `io::ErrorKind`.

### Errors, cancellation, progress

- No retries anywhere (Java has none). The only fallback is the one-time
  in-process → elevated retry after a permission failure (B4.7).
- Validation order: preflight (no network) → download + SHA-256 → archive validation → staging →
  layout check → first write to the install dir. A failure after the first write leaves a partially
  updated install (Java does the same, Q4). Each file replace is atomic, and the binary is never
  left half-written.
- Cancellation works during `check` and download (< 1 s, WP31 B26) and is checked once more before
  installing. Install, the elevated wait and the relaunch cannot be cancelled. WP29 disables
  `Cancel` on `Installing`/`WaitingForElevation`.
- Progress: `Downloading{bytes, total}` per chunk. The elevated install shows indeterminate progress.

### Concurrency

- Java: one `SwingWorker` or the console thread; `cancel()` from the EDT; the elevated JVM is a
  separate process (`U/ui/Updater.java:54-163`).
- Rust: `UpdateSession` is `Send + Sync`. `check`/`apply` are `async` on the caller's tokio runtime.
  Archive and install work runs in `tokio::task::spawn_blocking`. The elevated wait runs in
  `spawn_blocking`, with marker polling on the async side (`tokio::time::sleep(100 ms)`). One
  `apply` at a time per session (`AtomicBool`, `Busy`). There is no cross-process lock: two app
  instances cannot update at once, because single-instance covers the GUI, and a CLI `update`
  racing the GUI is accepted.

## Wire-compat notes

- No Java-serialized classes are read or written. No `.a3s/*`, `.zsync` or `.pbo.zip` output.
- Byte identity required for: nothing. Semantic compatibility: `.a3s-updater-files` is written by
  WP31 `install_staged` and stays Java-readable. Release archive layout (B11) is a new contract
  with WP33: a ZIP per target, with `arma3sync[.exe]` at the archive root.
- Fixtures: none. Tests build zips with the `zip` crate and serve them from axum (`127.0.0.1:0`,

## Open questions

- Q1 Elevated hand-off design. Java hands the **whole** update to an elevated copy of the updater,
  exits, and the elevated process relaunches the app (elevated). Proposed default (this spec): the
  non-elevated app downloads and verifies the archive, then starts
  `arma3sync.exe __a3s-elevated-install …` with `RunAs`. That child only re-verifies the SHA-256 and
  installs, while the parent waits (≤ 10 min) and relaunches the app without elevation. Benefits:
  one download with visible progress, no forwarded network config (so the over-the-shoulder
  admin's different config dir does not matter), and no elevated app afterwards. Cost: if the user
  declines UAC, the download was wasted. Alternative: Java parity (the child does the full flow).
  Decision:
- Q2 Elevation mechanism. Proposed default: PowerShell `Start-Process -Verb RunAs` with
  `-EncodedCommand` (the Java mechanism, no `unsafe`, no new deps; `unsafe_code = "deny"` in the
  workspace). Alternative: `windows-sys 0.61.2` `ShellExecuteExW` + `WaitForSingleObject` in one
  `#[allow(unsafe_code)]` module. That is faster, does not depend on PowerShell policy, and can
  parent the UAC prompt to the app window, but it needs an approved `unsafe` exception. Decision:
- Q3 Unsupported install kinds. Proposed default: `apply` refuses AppImage, macOS `.app` bundles, Java
  installation dirs (an `ArmA3Sync-Updater.jar` sibling) and cargo `target/` dirs, with
  `Unsupported`. `check` still works, so the GUI can say "download manually". If WP33 ships an
  AppImage or a `.app`, a follow-up WP adds those formats. Decision:
- Q4 Rollback. Java has none. Proposed default: no transactional rollback. Each file replace is
  atomic and the binary is validated before the copy. A later failure leaves new and old files mixed,
  and the next update repairs it. Decision:
- Q5 Legacy `-update` exit code. Java always exits 0. Proposed default: keep 0 for the legacy flag
  (scripts may rely on it). The new `update` subcommand uses 0/1/2. Decision:
- Q6 Should the Java updater flag grammar (`-check`, `-console`, `-dev`, `-github`, `-manifest`) be
  exposed? Proposed default: yes. WP19 maps `arma3sync update <flags>` through `parse_updater_flags`
  (`Gui` mode = open the viewer with the updater dialog, or console when there is no display). Unknown
  flags → exit 1 (D4). Decision:
- Q7 Approve the local-only deviations D1-D12. Proposed default: approve all. Decision:
