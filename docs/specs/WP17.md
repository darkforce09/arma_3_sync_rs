## Scope

- `a3s_tools::bikey`: validate the source and target directories using the Java messages, walk the
  source tree for `*.bikey` (case-insensitive), copy the keys flat into the target, count them, support
  cancellation, and produce the Java outcome messages. The GUI wizard (WP30) and CLI `-extract` (WP19)
  both use it.
- `a3s_tools::rpt`: a pollable `LogTailer` that handles appends, truncation and rotation, plus a
  named background thread (`RptTail`) that can actually be stopped, preloading of existing content,
  and the viewer title strings.
- `a3s_tools::radio`: TeamSpeak 3 helpers (`ts3client_win64/32.exe` detection, `changelog.txt`
  version parsing), the system-spec labels, the TFAR and ACRE 2 first-page validation (identical
  messages, Java last-wins precedence), the second-page copy steps and their result messages, and the
  UI string constants WP30 renders.
- Shared crate internals: `CancelToken`, a Java-`copyDirectory`-equivalent recursive copy, and a
  writability probe.
- No Swing/egui. No registry, process listing or config persistence. Those come in through plain
  inputs or the `Ts3ProcessProbe` trait.

## Behaviour contract

### Bikey (`a3s_tools::bikey`)

- B1. Validation takes the raw text-field strings (the GUI does not trim them; the CLI trims its args
  first, `main/ArmA3Sync.java:149`) and checks them in this order, returning the first failure
  (if/else chain):
  `source.is_empty()` → `Source directory is empty!`; `!exists(source)` →
  `Source directory does not exists!`; `target.is_empty()` → `Target directory is empty!`;
  `!exists(target)` → `Target directory does not exists!`; `!is_writable(target)` →
  `Can't write on target directory!` (`ui/tools/bikey/BiKeyExtractorDialog.java:233-246`,
  identical in `console/CommandGeneral.java:536-549`). The strings must be byte-identical, including
  "does not exists".
- B2. A file is a bikey when its name has a `.` and the substring from the **last** `.` equals
  `.bikey` ignoring ASCII case. So `a.BIKEY` matches, `.bikey` (index 0) matches, `a.bikey.bak` does
  not, and `bikey` does not (`dao/CommonDAO.java:92-97`, `dao/DataAccessConstants.java:27`). Compare
  on the file name's lossy UTF-8 form.
- B3. The walk is recursive. A directory's children are visited, and a directory whose listing
  fails is silently skipped (`listFiles()` returns null). A non-directory is tested with B2. The
  source itself may be a file: it passes `exists()` in B1 and is then tested with B2
  (`dao/CommonDAO.java:81-101`). Java's `File.isDirectory` follows symlinks.
- B4. The walk finishes before any copying. Each found file is then copied to
  `target.join(file_name)`. The layout is flattened: names that clash across mods overwrite one
  another, and the last one copied wins. An existing target file is truncated and overwritten
  (`dao/CommonDAO.java:70-74`, `dao/FileAccessMethods.java:64-72`).
- B5. The returned count is the number of **found** files, duplicates included, not the number of
  distinct target files. `0` is returned without touching the target when nothing was found
  (`dao/CommonDAO.java:67-77`).
- B6. The first copy error aborts the remaining copies. Files already copied stay, and the error goes
  to the caller (`dao/CommonDAO.java:70-74`, `ui/tools/bikey/ExtractProgressDialog.java:43-47`).
- B7. Outcome messages, all shown under the title `Bikey extractor wizard`
  (`ui/tools/bikey/ExtractProgressDialog.java:30-47`):
  cancelled → `Extraction canceled!` (info);
  count ≠ 0 → `"{n} have been copied to target directory."` (info; the noun "bikeys" is missing in
  Java, keep it that way);
  count = 0 → `"0 have been found."` (warning);
  I/O error → the error's message (error).
  The progress dialog title is `Extracting *.bikey files...` (`ExtractProgressDialog.java:17`).
- B8. CLI strings (used by WP19): `Extracting *.bikey files...` is printed first, then either the
  validation message, or `Extraction done.` / `Extraction failed.` followed by the error message
  (`console/CommandGeneral.java:534-562`).
- B9. Cancel stops the walk: every recursive call checks the flag first
  (`dao/CommonDAO.java:83`, `111-113`).
- B10. The UI labels are `Bikey extractor wizard` (title), `Extract *.bikey files` (description),
  `Source directory to search for *.bikey files` and `Target directory to copy *.bikey files`
  (`BiKeyExtractorDialog.java:51,73,108,128`). Export them as constants for WP30.

### RPT tail (`a3s_tools::rpt`)

- R1. Preload: if the file exists, read it whole and decode it with the JVM default charset (UTF-8 on
  JDK 25, malformed input → U+FFFD, so Rust uses `String::from_utf8_lossy`). If non-empty, append it
  to the view, and append `\n` if it does not end with `\n` (`ui/tools/rpt/Tail.java:44-76`). A
  missing file means no preload.
- R2. Tailing starts at the file's length **at thread start**. The 3-arg constructor never assigns
  `startAtBeginning`, so it is always false (`ui/tools/rpt/LogFileTailer.java:34, 67-71, 96-100`).
- R3. The poll interval is 1000 ms (`Tail.java:25`). The 5000 ms default (`LogFileTailer.java:22`)
  is unused.
- R4. On each poll, if `length < pointer` the file is treated as rotated/truncated: reopen it and
  reset the pointer to 0 (`LogFileTailer.java:110-115`).
- R5. If `length > pointer`, seek and read lines until EOF, then set pointer = file position
  (`LogFileTailer.java:117-126`). `RandomAccessFile.readLine` ends a line at `\n`, `\r` or `\r\n`,
  maps each byte to one char (Latin-1), and **returns a trailing unterminated fragment as a line**.
- R6. Each line goes to every listener. `Tail` appends `line + "\n"` and scrolls to the end
  (`Tail.java:36-42`, `LogFileTailer.java:44`, `LogFileTailerListener.java:13`).
- R7. Exceptions inside the loop are swallowed (`LogFileTailer.java:130-131`). If opening the file at
  start fails (missing file), the thread ends with only a stack trace (`LogFileTailer.java:105,
  136-138`).
- R8. Viewer: the window title is `RPT Viewer`, and after a file is chosen it becomes
  `RPT Viewer - Reading {file_name}`. The chosen path is persisted with `setRptPath`
  (`RptViewerPanel.java:39, 111-117`). The default folder is the stored RPT path, or else
  `determineRptPath` (WP15) (`ConfigurationService.java:249-259`, `ConfigurationDAO.java:161-172`).

### Radio: TS3 helpers (`a3s_tools::radio`)

- T1. `is_ts3_64bit(dir)` is true iff `dir/ts3client_win64.exe` exists. `is_ts3_32bit(dir)` is the
  same for `ts3client_win32.exe`. A missing (null) dir gives false
  (`service/ConfigurationService.java:271-293`). Java joins with `"\\"`; Rust uses `Path::join`, and
  an empty dir string gives false (see the local-only quirks).
- T2. `ts3_version(dir)`: read `dir/changelog.txt`. A missing file → `None`. Decode as UTF-8 (lossy)
  and split lines on `\r\n|\r|\n`. Take the **first** line whose lowercase form contains
  `client release` **and** that has ≥ 4 space-separated tokens. Tokens come from `StringTokenizer(line,
  " ")`: only U+0020 delimits, runs of spaces collapse, and tabs are not delimiters. Return the 4th
  token. A matching line with < 4 tokens is skipped and the search continues. Any read error → `None`
  (`dao/ConfigurationDAO.java:87-120`). Examples:
  `=== Client Release 3.1.10 ===` → `3.1.10`; `## Client Release 3.6.2 - 10 Jun 2024` → `3.6.2`;
  `Client Release 3.5.6` → skipped.
- T3. Stored-or-detected TS3 dir: if the stored option is `Some` (even `""`), return it. Otherwise
  return the detector result (registry `HKCU\Software\TeamSpeak 3 Client` default value, owned by
  WP15) (`ConfigurationService.java:188-198, 214-224`). The UI fills the field only if the path
  `exists()` (`FirstPageTFARInstallerPanel.java:283-291`, `FirstPageACRE2InstallerDialog.java:185-193`).
- T4. OS label: `"{os_name} - 64 bit"` or `"{os_name} - 32 bit"`. The value counts as 64-bit when, on
  Windows, env var `ProgramFiles(x86)` is set, and elsewhere when `os.arch` contains `64`
  (`ui/tools/WizardDialog.java:134-149`).
- T5. TS3 label (`WizardDialog.java:151-178`): if the TS3 field is empty → `Unknown`. Otherwise
  `version = ts3_version(dir).unwrap_or("Unknown")`. Check 64-bit **before** 32-bit:
  64 → `"{version} - 64 bit"`, else 32 → `"{version} - 32 bit"`, else `Unknown`. So
  `Unknown - 64 bit` is possible and is **not** treated as unknown by V-checks.
- T6. TFAR plugin label (`FirstPageTFARInstallerPanel.java:346-361`): if the plugin field or the TS3
  field is empty → `Unknown`; else if 64-bit → `task_force_radio_win64.dll`; **otherwise**
  `task_force_radio_win32.dll`. There is no 32-bit check, so TFAR never gives `Unknown` here.
- T7. ACRE 2 plugin label (`FirstPageACRE2InstallerDialog.java:222-243`): if either field is empty →
  `Unknown`; else 64 → `acre2_win64.dll`, 32 → `acre2_win32.dll`, else `Unknown`.
- T8. TFAR initial field values (`FirstPageTFARInstallerPanel.java:270-336`): Arma 3 dir = parent of
  the profile's `arma3ExePath` when that is non-null (no exists check). TS3 per T3. Plugin dir =
  stored `tfarPluginPath` if it exists. Userconfig dir = stored `tfarUserconfigPath` if it exists.
  The fallback via `@task_force_radio/plugins` / `/userconfig` is dead code (its source is hard-coded
  `null`), so do not port it. ACRE 2 (`FirstPageACRE2InstallerDialog.java:182-214`): TS3 per T3;
  plugin dir = stored `acre2PluginPath` if it exists (the `@ACRE2/plugin` fallback is likewise dead).

### Radio: first-page validation

Java does **not** stop at the first failure. It runs an if/else chain and then a series of
independent `if`s, each of which **overwrites** `message`. The last failing check wins. Rust must
return exactly the message Java would show.

- V1. TFAR (`FirstPageTFARInstallerPanel.java:461-519`), checks in evaluation order:
  1. Not Windows (`os.name` lacks `Windows`) → `This feature is not supported for your system`,
     returned **immediately**, with title `TFAR installer`.
  2. if/else chain: Arma 3 field empty → `ArmA 3 installation directory is missing.`; TS3 field empty
     → `TS3 installation directory is missing.`; plugin field empty → `TFAR plugin directory is
     missing.`; userconfig field empty → `TFAR userconfig directory is missing.`; TS3 label (T5) ==
     `Unknown` → `Can't determine between TS3 32/64 bit.`
  3. `!exists(ts3 + "/plugins")` → `TS3 installation directory is missing \plugins folder` (a single
     backslash; the Java literal is `"\\plugins"`).
  4. `!exists(plugin_dir + "/" + plugin_label)`: if the label is `Unknown` → `TFAR plugin is missing.`,
     else `TFAR plugin {label} is missing.`
  5. `!exists(userconfig + "/task_force_radio/radio_settings.hpp")` → `TFAR userconfig file
     radio_settings.hpp not found`
  6. TS3 running (`ts3client_win32.exe` **or** `ts3client_win64.exe` in the process list,
     `LaunchService.java:120-127`) → `TS3 is running and must be close to proceed.`

  Warning title: `TFAR installer`.
- V2. ACRE 2 (`FirstPageACRE2InstallerDialog.java:283-331`):
  1. Not Windows → `This feature is not supported for your system`, with title **`ACRE installer`**
     (sic), returned immediately.
  2. if/else chain: TS3 field empty → `TS3 installation directory is missing.`; plugin field empty →
     `ACRE 2 plugin directory is missing.`; TS3 label == `Unknown` → `Can't determine between TS3 32/64
     bit.`
  3. `!exists(ts3 + "/plugins")` → `TS3 installation directory is missing \plugins folder`
  4. `!exists(plugin_dir + "/" + label)`: `Unknown` → `ACRE 2 plugin is missing.`, else `ACRE 2 plugin
     {label} is missing.`
  5. TS3 running → `TS3 is running and must be close to proceed.`

  Warning title: **`ACRE 2 installer`**.
- V3. Empty fields in Java produce paths like `"/plugins"` and `"/Unknown"`, which are resolved
  against the filesystem root. Rust treats an empty field as "path does not exist" for checks 3–5,
  and treats a `Unknown` label as "plugin missing" without probing a file literally named `Unknown`.
  This matches Java except when such root-level paths actually exist.
- V4. On success the validated plan carries: TFAR (arma3_dir, ts3_dir, userconfig_dir, plugin_dir);
  ACRE 2 (ts3_dir, plugin **file** = `plugin_dir/label`) (`FirstPageTFARInstallerPanel.java:524-528`,
  `FirstPageACRE2InstallerDialog.java:310-311, 336-337`).
- V5. The process probe is called only after the not-Windows early return (order as above).

### Radio: second-page install steps

- I1. TFAR (`SecondPageTFARInstallerPanel.java:156-247`) runs two steps **independently**: a failed
  first step does not skip the second.
  - Userconfig step: if `!is_writable(arma3_dir)` → fail with `"Can't to write on: {arma3_dir}\nCheck
    files permissions."`. Otherwise `mkdirs(arma3_dir/userconfig)`, then copy-directory
    `userconfig_dir` → `arma3_dir/userconfig` (merge/overwrite). On an I/O error → `"Failed to write
    on: {arma3_dir}\n{error}"`.
  - Plugin step: if `!is_writable(ts3_dir)` → `"Can't to write on: {ts3_dir}\nCheck files
    permissions."`. Otherwise copy-directory the **whole** `plugin_dir` → `ts3_dir/plugins` (the
    TFAR copy is the directory, not just the chosen dll). On error → `"Failed to write on:
    {ts3_dir}\n{error}"`.
  - Each failure is a separate error dialog with title `Error`, userconfig first and then plugin.
  - The per-step status label is `OK` / `Fail`. When both are OK, show message 1 `You can now run
    your game with @task_force_radio.` and message 2 `Don't forget to run TS3 with administrator
    priviledges.` (keep the misspelling).
- I2. ACRE 2 (`SecondPageACRE2InstallerDialog.java:124-173`): if `!is_writable(ts3_dir)` → `"Can't to
  write on: {ts3_dir}\nCheck files permissions."`. Otherwise copy the single plugin file →
  `ts3_dir/plugins/{file_name}` (overwrite). On error → `"Failed to write on: {ts3_dir}\n{error}"`.
  Status `OK`/`Fail`. On success show message 1 `You can now run your game with @ACRE2.` (there is no
  message 2).
- I3. Copy-directory semantics (`dao/FileAccessMethods.java:26-45`): if the source is a directory,
  create the target with a single-level `mkdir` (the result is ignored) when it is absent, then recurse
  into each child. If the source is not a directory (including a **missing** source), copy it as a
  file, so a missing source is an I/O error. Existing files are overwritten. The first error aborts,
  and partial results stay.
- I4. UI strings for WP30, exported as constants: wizard titles `TFAR installer wizard` / `ACRE 2
  installer wizard`; descriptions `Install or update TFAR for ArmA 3 and TS3` / `Install or update
  ACRE 2 for ArmA 3 and TS3`; buttons `Proceed`/`Cancel` (page 1), `Back`/`Close` (page 2), `Select`,
  `View`; group titles `Installation directories`, `System specifications`; field labels `ArmA 3`,
  `TS3`, `@task_force_radio\plugins`, `@task_force_radio\userconfig`, `@ACRE2\plugin`; spec labels
  `OS: `, `TS3: `, `TFAR plugins: `, `ACRE 2 plugin: `; page-2 lines `The following operations have
  been performed:`, `  - TFAR plugin copied into TS3\plugins directory. ` (note the trailing space),
  `  - TFAR userconfig copied into ArmA 3 directory.`, `  - ACRE 2 plugin copied into TS3\plugins
  directory. `; `View` opens `ts3_dir/plugins` or `arma3_dir/userconfig`
  (`SecondPageTFARInstallerPanel.java:265-289`). Line refs: TFAR page 1 `:41-46,58,68,95,121,149,178,
  186,196,206`; TFAR page 2 `:63-64,77,86,93,102,109`; ACRE page 1 `:30-34,81,116,126,136`; ACRE
  page 2 `:51-52,65,74,81`.

### Java quirks that may be dropped (local-only; needs an approved deviation)

Each item lists the proposed Rust behaviour, which is also listed under Open questions.

- L1 Bikey cancel flag (`CommonService.java:33` static DAO + `CommonDAO.java:18,111-113`): it is set
  once and never reset, so every later extraction in the process silently finds 0. → Rust uses a
  per-call `CancelToken`.
- L2 Bikey cancel still copies the files found so far, then reports "canceled"
  (`CommonDAO.java:66-74`). → Rust also checks the token before each copy and returns
  `Cancelled { found, copied }`.
- L3 Copying a bikey onto itself (the target dir is inside the source tree) truncates the file to 0
  bytes: the `FileOutputStream` truncates before `transferFrom`. `std::fs::copy` has the same hazard.
  → Rust skips a copy when the canonical source == the canonical target, and still counts it.
- L4 Walk order: `File.listFiles` order is unspecified. → Rust sorts entries by file name (byte
  order), so the winner among duplicates is deterministic (the last in sorted walk order).
- L5 Symlink cycles: Java recurses until `StackOverflowError`. → Rust follows directory symlinks but
  keeps a set of visited canonical directories.
- L6 `ExtractProgressDialog.java:27` sleeps 1 s before starting. → Dropped.
- L7 The RPT stop path calls `Thread.interrupt()`, but the `InterruptedException` from `sleep` is
  swallowed inside the loop, so the tailer **never stops** and leaks a thread plus an open file
  (`Tail.java:82-84`, `LogFileTailer.java:129-131`). In addition, selecting a second RPT does not stop
  the first tail (`RptViewerPanel.java:115`). → `RptTail::stop()` joins the thread, and `Drop` stops
  it.
- L8 Race between preload and tail: preload (SwingWorker) and the tailer start independently, so lines
  written in between are duplicated or lost (`Tail.java:24-25`). → Rust preloads, then starts tailing
  at the exact byte offset where the preload ended.
- L9 A partial last line is emitted as a line and its continuation becomes a separate line (R5). →
  Rust buffers an unterminated fragment. It is emitted when a terminator arrives, or on the first poll
  that sees no growth (so a crashed game's last fragment still shows).
- L10 Tailed lines are decoded as Latin-1 while the preload is UTF-8. → Rust decodes each complete
  line as lossy UTF-8.
- L11 A missing file at start kills the tailer silently (R7). → Rust keeps polling. When the file
  appears, tailing starts at offset 0.
- L12 Rotation is detected only by shrinkage (R4). → Rust also resets when the file identity changes
  (unix `dev`+`ino`; elsewhere `Metadata::created()` when available) and reopens the path on every
  poll instead of holding a handle.
- L13 TS3 exe/changelog paths use `"\\"` concatenation, and an empty/relative dir resolves against the
  drive root (T1, V3). → `Path::join`, and an empty string means absent.
- L14 The TFAR initial Arma 3 dir throws an NPE when `arma3ExePath` has no parent
  (`FirstPageTFARInstallerPanel.java:275-277`). → `None`.
- L15 Error text for I/O failures uses `IOException.getMessage()` (e.g. `C:\x (Access is denied)`). →
  Rust uses `std::io::Error` Display, prefixed by the path where useful. The text cannot be identical.

### Errors, cancellation, progress

- Bikey: there are no retries. The first copy error aborts (B6). Unreadable directories are skipped
  silently (B3). Cancellation is cooperative through `CancelToken`, checked at every walk step and
  before each copy (L2). Java's only progress is an indeterminate bar, so no progress events.
  Optionally, `extract_with_progress` may report `found` during the walk; leave it out unless it is
  trivial.
- RPT: there are no retries beyond polling. I/O errors during a poll are reported through
  `RptEvent::Error(String)` **once per distinct error kind/message in a row** (no flood), and polling
  continues (Java swallows all errors; R7, L11).
- Radio: validation returns the single winning `InstallerIssue`. The install steps never abort each
  other (I1), and each returns `Result<(), InstallStepError>`.

### Concurrency

- Java runs bikey extraction on one unnamed worker thread (`ExtractProgressDialog.java:23`), and RPT
  tailing on one `Thread` per tail plus a SwingWorker for the preload.
- Rust: bikey extraction is a blocking fn; the caller picks the thread (WP30/WP19). RPT uses one
  thread per `RptTail`, named `rpt-tail` (`std::thread::Builder`), parked with
  `park_timeout(interval)` and woken by `stop()`. The preload runs on that same thread before the
  first poll. Use `parking_lot` if any lock is needed, though atomics should be enough.

pub mod rpt;

// cancel.rs
