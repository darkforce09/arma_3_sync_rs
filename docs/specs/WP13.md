## Scope

- **Discovery** (`scan`): walk the profile's addon search directories, detect Arma 3 mods (a
  directory with an `addons` sub-directory that contains a `.pbo`/`.ebo` name), skip the Arma 3
  system folders, collapse overlapping search directories, build the "available addons" tree
  (tree view and flat list view), register CDLCs found in the Arma 3 root.
- **Registry** (`AddonRegistry`): the Java static `AddonDAO` map: symbolic keys with the `*`
  suffix for duplicates, case-insensitive lookup, duplicate detection by name.
- **Priorities**: sync `Profile::addon_names_by_priority` with the registry; top/up/down/reset;
  up/down for `Profile::addon_search_directories` ("directory priority").
- **Modsets**: build an addon group from a repository's `.a3s/sync` tree
  (`getGroupFromRepository`/`extractAddons`/`markRecursively`/`cleanTree`), from an `Event`, and
  refresh existing modset groups after a sync, preserving the user's selection.
- **Checks on the addon-group tree** (`Profile::tree`): resolve modset leaves against download
  locations, missing addons (by workshop id via `meta.cpp`, by DLC app id, by name), missing
  selected addons, duplicates and duplicated selection.
- DLC data comes from `a3s_types::constants::{GameDlc, GAME_SYSTEM_FOLDERS}` (WP03). WP13 must not
  redefine either.

## Behaviour contract

Notation: "Windows mode" = Java's `os.name` contains `Windows`. In Rust this is a
`case_insensitive_paths: bool` parameter (default `cfg!(windows)`) so both modes are testable.
"`lower`" = `str::to_lowercase`. "Ignore-case compare" = `a3s_types::java_string::compare_ignore_case`.

### Addon registry (`dao/AddonDAO.java`)

- B1. The registry maps `lower(key)` → `Addon`. In Java it is one **static** `HashMap` shared by
  every `AddonService`, `RepositoryService` and `LaunchService` instance (`dao/AddonDAO.java:14`).
  Rust: an owned `AddonRegistry` value that the caller (WP21 app state) keeps; no global. Iteration
  order is **insertion order** (see Q2).
- B2. `determine_new_key(name)`: if `lower(name)` is a key, retry with `name + "*"`, recursively;
  return the first free candidate **with the original case** (`dao/AddonDAO.java:20-28`). The
  second `@ace` becomes `@ace*`, the third `@ace**`; an `@ACE` after `@ace` becomes `@ACE*`.
- B3. `get(key)` looks up `lower(key)` (`service/AddonService.java:195-200`); `None` for an
  unknown key. `addons()` returns every `Addon` (`:206-208`).
- B4. `duplicates(key)`: if `get(key)` is `None` → empty. Else every map key (lowercase) whose
  addon's `name` **equals exactly (case-sensitive)** the found addon's `name`, in registry order;
  the list includes `lower(key)` itself (`dao/AddonDAO.java:40-53`).
  `has_duplicate(key)` = `duplicates(key).len() > 1` (`:30-38`). Quirk (local-only, preserve):
  `@ace` and `@ACE*` are **not** duplicates of each other.

### Arma 3 root and system folders

- B5. `arma3_directory(exe)`: `None` if the profile's `launcher_options.arma3_exe_path` is `None`
  or empty; otherwise the parent of that path; `None` if there is no parent (Java
  `getParentFile() == null`; in Rust treat an empty parent, e.g. for `"arma3.exe"`, as `None`)
  (`service/AddonService.java:52-62`, `:239-247`).
- B6. Excluded paths: for each of the 21 `GAME_SYSTEM_FOLDERS` names in order,
  `absolute(arma3_dir.join(name))`, lowercased in Windows mode (`:64-75`). Only when B5 gives a
  directory. Java's `init()` clears the registry and the exclusion list first (`:49-50`).

### Effective search directories (`:80-149`)

- B7. Input: `profile.addon_search_directories` in profile order (`:82-91`). That order matters:
  it decides which duplicate gets the plain key (B2), which is why "directory priority"
  (B27) exists.
- B8. For each path `i` in order: skip it if it does not exist, or if it has no parent, or its
  parent does not exist (`:99-115`). **Quirk:** a filesystem root (`/`, `C:\`) is therefore
  never scanned. `path_to_keep = i`. For every `j` (all paths, including `i`): skip `j` if it does
  not exist or has no existing parent (`:120-135`); if `absolute(parent(i)) != absolute(parent(j))`
  (**case-sensitive** string compare even in Windows mode, `:137`) and `cmp(i)` **contains**
  `cmp(j)` as a substring or vice versa (`cmp` = lowercased in Windows mode, `:104-106`,
  `:124-127`), and `len(j) < len(path_to_keep)` (UTF-16 length), then `path_to_keep = j`
  (`:138-142`). Append `path_to_keep` if not already in the result (exact string compare,
  `:146-148`). Result keeps the original spelling.
- B9. Quirks to preserve (local-only): containment is a **substring** test, not a path-prefix
  test (`/b/a/mods` is replaced by `/a/mods` when both are listed); siblings (same parent) are
  never collapsed; `"/x/mods"` and `"/x/mods2"` are siblings so both stay.

### Scanning (`generateTree`, `:292-348`)

- B10. Raw tree: root `"racine1"`. For each effective directory that exists, add a directory
  node named `file_name(path)` under the root, then call `scan_entry` on each entry of the
  directory (`:151-165`). Unreadable directories (Java `listFiles() == null`) are treated as empty.
- B11. `scan_entry(entry, parent)`: ignored unless `entry` is a directory (`File.isDirectory`,
  follows symlinks). Ignored if `absolute(entry)` (lowercased in Windows mode) is in the
  exclusion list (B6) (`:294-302`). Otherwise a node named `file_name(entry)` is added to
  `parent` (`:304-305`).
- B12. Mod detection (`:307-323`): the entry is a mod if **any** child whose
  `lower(name) == "addons"` is a readable directory containing at least one child (file **or**
  directory) whose name **contains** `".pbo"` or `".ebo"` (`String.contains`, not `ends_with`,
  case-sensitive; so `x.pbo.zip` counts, `X.PBO` does not). All `addons`-named children are
  examined (on Linux `Addons` and `addons` may both exist).
- B13. If it is a mod (`:325-339`): `key = registry.determine_new_key(name)`; insert
  `Addon { key, name, path: absolute(parent_dir_of_entry), at_arma3_install_root: false }` under
  `lower(key)`; **rename the node to `key`**; mark the node and every ancestor up to the root
  (`markRecursively`, `:350-357`). Its sub-directories are **not** scanned (a mod inside a mod is
  never found). Otherwise recurse into each child entry (`:341-345`).
- B14. Entry order: Java uses `File.listFiles()` order (filesystem dependent). Rust sorts the
  entries of each directory with ignore-case compare, ties broken by byte order of the name
  (approved-deviation candidate, Q1). Non-UTF-8 names are converted with `to_string_lossy` and a
  `tracing::warn!`. Symlink loops: see Q3.

### Available addons tree and list

- B15. `cleanTree(dir, out)` (`:359-372`): if `dir` is marked and has children, add a new
  directory `dir.name` to `out` and recurse into each child; if marked and childless, add a
  **leaf** `dir.name` to `out`; unmarked directories are dropped. All produced nodes have
  `selected/marked/optional/updated = false`, no workshop/DLC id. Insertion uses
  `TreeDirectory::add_child` (directories first, ignore-case stable sort).
- B16. Result root `"racine1"` (`:168`). If the raw root has **exactly one** child (one effective
  search directory present), clean each child **of that child** into the result, i.e. the search
  directory level is hidden; otherwise clean each child of the raw root, so each search directory
  that contains mods appears as a directory named by its basename (`:170-181`).
- B17. Sibling dedupe (`ObjectDTOtransformer.java:137-166`, used by `getAvailableAddonsTree`,
  `:210-219`): when the tree is copied for display, a child whose name **exactly equals** an
  earlier sibling's name is dropped with its subtree. Effect to preserve: with two search
  directories with the same basename, the second one's subtree is not shown (its addons stay in
  the registry). Rust: `normalize_group_tree` (B36) applied to the result.
- B18. Flat list (`getAvailableAddonsList`, `:221-228`, `generateTreeList` `:271-290`): new root
  `"racine1"`; visit the (deduped) tree depth-first in child order; every leaf whose name is not
  already present (exact compare) is added with `add_child`. Result: all leaves, ignore-case
  stable sorted, first DFS occurrence wins.

### DLCs (`getAvailableDLCList`, `:230-269`)

- B19. Only when B5 gives a directory: for each `GameDlc` in `GameDlc::ALL` order, if
  `arma3_dir.join(dlc.java_name())` exists (file or directory, case-sensitive on Linux), add the
  DLC to the result list (Java: leaf named `java_name()` with description `description()`, root
  `"racineDLC"`), and register `Addon { key: determine_new_key(java_name), name: java_name, path:
  absolute(arma3_dir) }` (`:249-266`).
- B20. Registration happens **after** the mod scan (`AddonsPanel.java:663-669`: `init()` then
  `loadAvailableAddons` then `loadAvailableDLC`), so a mod folder named `GM` keeps the plain key
  and the DLC becomes `GM*`. Java re-registers on every `getAvailableDLCList()` call (a second
  call would create `GM*`); Rust's `scan` does mods then DLCs once per call on a cleared registry,
  which is what the only caller does.
- B21. The static event-editor DLC list (`EventsPanel.java:725-738`) is simply all of
  `GameDlc::ALL`; no function needed beyond `GameDlc::ALL`.

### Priorities (`getAddonsByPriorityList`, `:374-417`; `ProfileService.java:290-401`)

- B22. `sync_addon_priorities(list, registry)`: `available` = every registry key (lowercase)
  sorted by `lower(a)` vs `lower(b)` compared as UTF-16 code units (`SortIgnoreCase`, `:410-417`).
  If `available` is empty, clear `list`. Otherwise append each available key not already in `list`
  (exact compare), in sorted order, then remove every entry of `list` not in `available`
  (`:386-404`). The list therefore holds **lowercase keys**, DLC keys included. Java mutates the
  in-memory profile without saving (`:405`); Rust returns whether the list changed so the caller
  may persist.
- B23. `reset_addon_priority`: clear the list (`ProfileService.java:290-302`).
- B24. `top(list, i)`: if `i != 0 && i <= len-1`, move element `i` to index 0 (`:304-321`).
- B25. `up(list, i)`: if `i != 0 && i <= len-1`, swap `i` and `i-1` (`:323-341`).
- B26. `down(list, i)`: if `i < len-1` (Java `!(index >= size-1)`), swap `i` and `i+1`
  (`:343-361`). Java throws on an empty list with index 0 (`0 >= -1` is false → `get(0)`);
  Rust: no-op when `len == 0`.
- B27. Directory priority: `up`/`down` with the same rules on `addon_search_directories`
  (`:363-401`).
- B28. Every move returns `true` only when the list changed; Java writes the profile only then
  and swallows `WritingException` (persistence is the caller's job, WP14).

### Modsets from a repository (`RepositoryService.java:1069-1153`)

- B29. `group_from_repository(sync, with_userconfig)`: raw root named `sync.name`;
  `extractAddons` (`:1127-1144`): for each **directory** child of a sync directory (leaves are
  ignored; `deleted`/`hidden` flags are **not** checked): add a directory with the same name; if
  `mark_as_addon` mark it and all its ancestors and do not descend, else descend.
- B30. Clean each raw top-level child into a new root `"racine"` with B15 (`:1080-1086`). Every
  `markAsAddon` directory becomes a leaf named exactly like the folder; non-addon folders on the
  way become directories.
- B31. If `with_userconfig` (`:1088-1100`): for each top-level sync child whose
  `lower(name) == "userconfig"` and that is a directory, add a directory with its original name
  and, under it, one **leaf per child** (files and directories alike), named like the child.
- B32. The result goes through sibling dedupe (B17/B36), so if the cleaned tree already contains a
  same-named `userconfig` directory, the userconfig-leaves directory is dropped. Java returns
  `null` when the repository is unknown or its sync tree is not loaded (`:1072-1075`); Rust takes
  `&SyncTreeDirectory`, so the caller handles `None`.
- B33. `add_groups_from_repository(root, repos, updated)` (`AddonsPanel.java:1810-1835`), per
  `(repository_name, Option<&SyncTreeDirectory>)`: skip when the sync tree is `None`. Otherwise
  find the **last** top-level child of `root` whose name equals `repository_name` (any kind);
  if present, record its selected paths (B37) and remove it. Build `group_from_repository(sync,
  false)`, rename it to `repository_name`, set `modset_type = Repository`,
  `modset_repository_name = repository_name`, `updated`, insert with `add_child`, then apply the
  recorded selected paths (B37).
- B34. `add_groups_from_events(root, events, updated)` (`AddonsPanel.java:1846-1883`), per
  `(repository_name, &Event)`: remove the last same-named top-level child as in B33 (recording its
  selection); create directory `event.name` with `modset_type = Event`,
  `modset_repository_name = repository_name`, `updated`; add one leaf per entry of
  `addon_names` ∪ `dlc_names` (a key in both takes the `dlc_names` value), `optional` = map value,
  no workshop/DLC id; insert; apply the recorded selection. `userconfig_folder_names` are **not**
  added.
- B35. `update_group_modsets(root, repository_name, sync, events)` (`AddonsPanel.java:1885-1936`):
  if any top-level directory has `modset_type == Repository` and `modset_repository_name ==
  repository_name`, run B33 for that repository with `updated = true`. Then, for each top-level
  directory with `modset_type == Event` and that repository name, in tree order, take the
  **first** event of `events` with that name (Java `getEvents` drops later same-named events,
  `RepositoryService.java:878-887`) and run B34 for all of them with `updated = true`. Caller then
  runs the resolution and checks (B38-B44) and persists.

### Group tree helpers

- B36. `normalize_group_tree(dir)` mirrors the DTO round trip (`ObjectDTOtransformer.java:137-215`
  and `ProfileService.java:251-288`): recursively, keep only the first child of each exact name
  (later same-named siblings and their subtrees are dropped, leaves and directories alike), and
  re-sort with `add_child` order. Leaf fields kept: `name, selected, optional, missing,
  workshop_id, dlc_app_id`; directory fields kept: `name, modset_type, modset_repository_name,
  selected, updated`. **`marked` is reset to `false`** (not copied by the transformer).
  `getAddonGroups` also replaces a null profile name with `"Default"` (`:255-258`): WP14's concern.
- B37. Selected paths (`AddonsPanel.java:1473-1515`): a node's path is the `/`-joined names from
  the tree root down to the node. Rust: the path is relative to `root` and built by the caller
  from the root's children, which is equivalent because the same root is used for capture and
  apply. `selected_paths(node)` collects the path of every selected node in the subtree (node
  included, directories included). `apply_selected_paths(node, paths)` sets `selected =
  paths.contains(path)` for every node in the subtree (node included), i.e. deselects anything
  not listed.
- B38. `set_selected_recursive(dir, value)` (`AddonsPanel.java:887-907`): set `dir.selected` and
  every descendant's `selected`.

### Resolution and checks on the group tree

The Java call order on a refresh (`AddonsPanel.java:731-738`) is: `resolveAddonGroups`, save,
`checkMissingAddons`, save, `checkDuplicateAddons(racine2, racine1)`,
`checkDuplicateAddonsSelection`. `refresh_group_status` performs exactly this sequence (without
saving).

- B39. `resolve_addon_groups(root, registry, repositories, status)` (`:419-456`): only **direct**
  children of `root` that are directories with a `modset_type`; the repository is looked up by
  `modset_repository_name` (exact; unknown → skip). `Repository` → location =
  `repository.default_download_location`. `Event` → if `events_download_location` contains the
  directory's `name`, location = that value; otherwise location = `default_download_location`. No
  location → skip.
- B40. `resolve_addon_group(dir, location)` (`:463-515`), for every leaf in the subtree:
  - if `registry.has_duplicate(leaf.name)`: for each key in `registry.duplicates(leaf.name)` (in
    registry order, see Q2), if `same_path(addon.path, location)` or
    `within_path(addon.path, location)`, rename the leaf to `addon.key` and stop (`found`);
  - else `found` = `get(leaf.name)` exists and its path is the same as or within `location`.
  - if `found`: `missing = false`, `source_file_path = None`. Otherwise: if `get(leaf.name)` exists,
    `missing = false`, `source_file_path = None`; else `missing = true`,
    `source_file_path = Some(location)`.
  - `same_path`/`within_path` (`:517-529`): both sides `std::path::absolute` + lexical
    normalisation (`.`/`..` removed, like `Path.normalize()`, no symlink resolution), then equality
    / component-wise `starts_with`. In Windows mode compare lowercased (Java's `WindowsPath` is
    case-insensitive). Either side `None` → false.
- B41. `check_missing_addons(root, registry, newly_missing, status)` (`:531-569`), every leaf:
  - `was_missing = leaf.missing`;
  - if `workshop_id` is non-blank: `resolved = find_addon_by_workshop_id(id)`; if found, rename the
    leaf to `addon.key`. **No fallback** to the name when not found (quirk, preserve);
  - else if `dlc_app_id` is non-blank: `dlc = GameDlc::from_steam_app_id(id)` (exact string match);
    `resolved` = first registry addon whose `name` equals `dlc.java_name()` ignoring case; if found,
    rename the leaf to `dlc.java_name()` (not the addon key);
  - else `resolved = get(leaf.name)`;
  - `resolved` none → `missing = true`, and push `leaf.name` to `newly_missing` only if it was not
    already missing; else `missing = false`, `source_file_path = None`.
- B42. `find_addon_by_workshop_id(registry, id)` (`:571-590`): for each addon in registry order,
  skip if `<path>/<name>/meta.cpp` is not a regular file (follows symlinks). Read it as **strict
  UTF-8** (invalid UTF-8 or I/O error → skip that addon silently). Take the **first** match of the
  Java regex `(?m)^\s*publishedid\s*=\s*([1-9][0-9]*)\s*;` (`:37-38`); the addon matches if the
  captured digits equal `id` exactly. A later `publishedid` line is never consulted. Implement
  without a regex crate (`parse_published_id(text) -> Option<&str>`):
  - Java `\s` here is `[ \t\n\x0B\x0C\r]` (ASCII only); `[0-9]` is ASCII;
  - `^` matches at offset 0 or after `\n`, `\r`, `\u{85}`, `\u{2028}`, `\u{2029}`;
  - `publishedid` is case-sensitive;
  - `\s` may span newlines (`publishedid =\n 123\n;` matches);
  - scanning continues past non-matching candidates (`publishedid = 0;` on line 1 and
    `publishedid = 5;` on line 2 → `5`).
- B43. `check_missing_selected_addons(root, registry) -> Vec<String>` (`:605-624`): every leaf: if
  not `missing` and `get(name)` is `None`, set `missing = true`; then if `missing && selected`,
  push `name`. LaunchPanel blocks the launch when the list is non-empty ("Some selected addons are
  missing.", `LaunchPanel.java:278-282`). Java runs it on a fresh DTO copy of the profile tree, so
  the extra `missing = true` does not reach the profile; the Rust caller should pass a clone if it
  cares.
- B44. `check_duplicate_addons(root, registry, available_tree, status)` (`:626-643`): every leaf:
  `status.duplicate = registry.has_duplicate(name)`; if duplicate,
  `status.source_relative_path` = path of the **last** leaf in `available_tree` (the tree view,
  B16-B17, even when the UI shows the list view) whose name equals the leaf name ignoring case,
  built from the names of its ancestor directories excluding any name that **contains**
  `"racine"`, `/`-joined, or `None` when it sits at the root (`:645-670`); else `None`.
- B45. `check_duplicate_addons_selection(root, status) -> Vec<String>` (`:672-730`): collect the
  names of all selected leaves in DFS order; for each occurrence of a name that appears more than
  once (exact compare), push it (so a name selected twice appears **twice** in the list); then for
  every leaf `status.duplicated_selection = list.contains(name)`. LaunchPanel blocks on a
  non-empty list ("Duplicate addons selection.", `LaunchPanel.java:283-287`).
- B46. Only `missing` (on `TreeLeaf`) and `duplicated_selection` are displayed by Java
  (`ui/main/tree/CheckTreeCellRenderer.java:43`). `duplicate`, `source_relative_path` and
  `source_file_path` are written but never read; they are kept in `LeafStatus` for the UI tooltip
  (WP23) at negligible cost.

### Java quirks to preserve (wire-visible)

- Leaf names written into profiles are registry **keys**, including the `*` suffixes (B2, B13,
  B40, B41). Profiles imported from Java (WP04) contain such names, so key allocation, scan
  order across search directories (B7) and the `*` rule must match Java for those names to
  resolve. Persisted as data, not as a Java stream.
- `addon_names_by_priority` holds **lowercase** keys (B22).
- DLC leaves and event `dlcNames` keys use `GameDlc::java_name()` (`vn` lowercase), via WP03.

### Java quirks that may be dropped (local-only; needs an approved deviation)

- Directory listing order (B14, Q1).
- `HashMap` iteration order for `duplicates`, `find_addon_by_workshop_id`, DLC addon lookup and
  the priority source list (Q2): Rust uses insertion order.
- Symlink loops recurse forever in Java (Q3).
- `source_relative_path` skips any ancestor whose name **contains** `racine` (B44). Proposed:
  keep it (never displayed).
- Kept as Java (no deviation proposed): substring overlap test (B9), root search directory
  ignored (B8), second same-basename search directory hidden (B17), case-sensitive duplicate
  names (B4), no name fallback for an unresolved workshop id (B41), duplicate names repeated in
  the duplicate-selection list (B45).

### Errors, cancellation, progress

- No function returns an error. I/O failures are swallowed like Java (`listFiles() == null` →
  empty, `meta.cpp` unreadable → skipped) with `tracing::debug!`.
- No retries, no cancellation, no progress events. A scan of a large `!Workshop` folder is a
  blocking filesystem walk; callers run it off the UI thread (`spawn_blocking`).

### Concurrency

- Java runs everything on the Swing thread against a static map. Rust: plain synchronous
  functions over owned values; `AddonRegistry` is `Send + Sync` (no interior mutability). No
  threads.

## Open questions

- Q1 Directory listing order. Java uses `File.listFiles()` order: NTFS gives ignore-case
  alphabetical, ext4 gives hash order. That order decides which of two same-named mods in
  different sub-folders of one search directory gets the plain key. Proposed default: sort the
  entries of each directory with `compare_ignore_case`, ties broken by byte order. This matches
  Windows Java for practically all names and is deterministic on Linux. Approve it as a local-only
  deviation. Decision:
- Q2 `HashMap` iteration order (`duplicates`, workshop-id lookup, DLC-name lookup). Java's order
  depends on `String.hashCode` buckets. Proposed default: registry insertion (scan) order, as a
  local-only deviation. It only matters when two addons both match a location, or two `meta.cpp`
  files share a workshop id. Decision:
- Q3 Symlink or junction loops: Java follows directory symlinks and would recurse until
  `StackOverflowError`. Proposed default: follow symlinks like Java, but skip a directory whose
  canonical path is already on the current recursion stack, with a `tracing::warn!`. Approve as a
  local-only deviation. Decision:

  WP23 must not re-implement it. Decision:
