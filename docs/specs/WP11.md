## Scope

- `build_repository(&Repository, &mut Sha1Cache, …)`: scan a local folder into a `SyncTreeDirectory`
  exactly like Java (exclusions, `.a3s` skip, addon detection, ordering, pruning).
- SHA-1 stage through `a3s_hash` with the mtime cache (`mapFilesForBuild`), tracking which files
  were re-hashed.
- Content fingerprint, revision rule, `ServerInfo` (counts, sizes, flags, hidden folders),
  `AutoConfig`.
- `Changelogs` (≤ 10, new/updated/deleted addons) and `Events` carried over with the DLC filter.
  These two are emitted at graph level so that Java's `String`/`Boolean`/`Date` instance sharing
  and `HashMap` layout are reproduced (B44–B58).
- `.zsync` generation for HTTP(S) repositories and `.pbo.zip`/`.ebo.zip` compression or deletion,
  run in parallel with progress events and cancellation.
- Write the five `.a3s` files in Java's order, each atomically.

## Behaviour contract

`J` below means `dao/repository/RepositoryBuildProcessor.java`.

### Preconditions and inputs

- B1. Inputs come from the local `Repository` (WP03): `name`, `protocol`, `path`,
  `excluded_files_from_build`, `excluded_folders_from_sync`, `compressed`,
  `no_partial_file_transfer`, `number_of_connections` (raw, WP03 B7),
  `favorite_servers_set_to_autoconfig`. The SHA-1 cache (`mapFilesForBuild`) is passed separately
  as `&mut a3s_hash::Sha1Cache`. The caller persists the cache and the repository afterwards
  (`service/administration/RepositoryBuildProcessor.java:44-45`).
- B2. `path` `None` or `""` fails with `PathNotSet`. Java's message is
  `"Repository <name> main folder location is empty!"` (`service/RepositoryService.java:396-398`).
  A path that does not exist fails with `"Repository path does not exist."` (`J:78-81`).
- B3. Old metadata is read **before** scanning, from `<path>/.a3s/{sync,serverinfo,changelogs,events}`
  (`J:83-109`). A missing file means "none". A file that exists but cannot be decoded aborts the
  build and nothing is written. `.a3s/autoconfig` is never read.

### Scan (`generateSync`, `J:113-124`, `J:468-497`)

- B4. The root is `SyncTreeDirectory("racine")`. Java iterates the direct children of the
  repository folder, and for each one calls `generateSync` (`J:114-121`). The root itself is never
  `markAsAddon`.
- B5. Directory (`File.isDirectory()`, which follows symlinks): skip it (and its subtree) if its
  name `equalsIgnoreCase(".a3s")`, at **any** depth. Otherwise add a `SyncTreeDirectory(name)` and
  recurse into its children. While iterating the children, set `mark_as_addon = true` if
  **any** child (file or directory) has a name whose `toLowerCase()` equals `"addons"`
  (`J:470-484`).
- B6. File: skip it if the name *contains* `".zsync"`, `".pbo.zip"` or `".a3s"` (case-sensitive
  `contains`), or if its absolute path string is in `excluded_files_from_build` (exact,
  case-sensitive string compare, `J:487-489`). Otherwise add a `SyncTreeLeaf(name)` with
  `size = file length` (`J:491-495`). Reuse `a3s_repo_files::layout::is_builder_ignored_file`.
  The absolute path is `File.getAbsolutePath()` of `<path>/<…>/<name>`: the repository path made
  absolute **without** canonicalisation (no symlink resolution, `..` kept), joined with the
  platform separator. Use `std::path::absolute(path).join(...)` and compare
  `to_string_lossy()` (Q12).
- B7. `excluded_files_from_build` entries that name a directory have no effect. Only files are
  checked (`J:487-489`).
- B8. Children order mirrors `SyncTreeDirectory.addTreeNode` (`domain/repository/SyncTreeDirectory.java:31-49`):
  all directories, then all leaves, each group stably sorted by `compareToIgnoreCase` of the name
  (`:96-101`, `SyncTreeLeaf.java:97-101`). Pushing all children and calling
  `SyncTreeDirectory::sort_children()` once gives the same result as Java's re-sort on every
  insert. Ties (names that differ only in case) keep directory-listing order in Java, which is
  OS-dependent. Rust sorts each `read_dir` listing by name bytes first (Q7).
- B9. An unreadable directory (`listFiles()` returns `null`) contributes no children and raises no
  error (`J:475-476`). Rust logs a `tracing::warn!` and continues. A leaf whose file has
  disappeared or is a broken symlink fails the build, because commons-io 2.15.1
  `FileUtils.sizeOf` throws `IllegalArgumentException` (`J:494`). Rust returns `BuildError::Scan`.
- B10. `pruneMissingNodes` (`J:423-457`) runs after the scan, depth-first:
  - a leaf whose `<root>/<relative path>` no longer exists is removed, with warning
    `"Warning: Removing missing file from metadata: <relpath>"`;
  - a directory is pruned recursively first, then removed if its child list is empty, with
    warning `"Warning: Removing empty directory from metadata: <relpath>"`.
  Consequence (wire-visible): empty directories, and directories that contain only skipped or
  excluded files (recursively), do not appear in `.a3s/sync`. A pruned `addons` folder does not
  clear its parent's `mark_as_addon`. Emit each warning as `BuildEvent::Warning` and
  `tracing::warn!`.
- B11. Relative path (`SyncTreeNodeMethods.java:11-24`): names below `racine` joined with `/`.
  For a top-level node it is the node's own name (same `String` instance, which matters for B50).
- B12. "Deep leaf list" order (`SyncTreeNodeMethods.java:48-65`) is a DFS over each list in
  order. A directory's subdirectories come first (with their whole subtrees), then its own leaves.
  `SyncTreeDirectory::walk` yields this order. It is used by B13, B16, B19, B24 and B35.
- B13. `numberOfFiles` = number of leaves after pruning (`J:127-130`).

### Total size (`J:133`, `J:499-519`)

- B14. `totalFilesSize` = sum of `Files.size` over every regular file (`Files.isRegularFile`
  follows symlinks) under the root, found by `Files.walk`, which does **not** descend into
  symlinked directories. Only paths whose first relative component `equalsIgnoreCase(".a3s")` are
  excluded. Wire-visible consequences, all to preserve:
  - `.zsync`, `.zip`, excluded files, files whose names contain `.a3s`, and nested `.a3s`
    folders **are** counted;
  - it is computed **before** the zsync and zip stages, so it includes the `.zsync`/`.zip` files of
    the previous build (including orphans) and excludes those created by this build. A second
    build without content change therefore reports a different (larger) `totalFilesSize`.
- B15. An I/O error during the walk aborts the build (`J:516-518`).

### SHA-1 stage (`J:136-143`, `RepositorySHA1Processor.java`)

- B16. Stage text `"Processing SHA1 signatures..."`. Inputs are the deep leaf list (B12) and the
  cache.
- B17. First, remove from the cache every entry whose path does not exist on disk
  (`RepositorySHA1Processor.java:54-67`). Entries for existing files that are no longer in the tree
  are **kept**.
- B18. For each leaf, file = `<parent abs path>/<name>`. If it doesn't exist, skip it: `sha1`
  stays `null` and the leaf is written with a null `sha1` (race only, `:106-110`). Otherwise
  read `lastModified` (ms). A cache entry is a hit iff its `last_modified` equals the current
  mtime and its sha1 is non-null (`:113-127`); the size is **not** checked. A hit sets
  `leaf.sha1` from the cache. A miss is queued for hashing and the leaf is recorded in
  `updated_files` (`:129-156`).
- B19. Hashing: `a3s_hash::hash_files` (≤ `min(8, cpus)` threads, `:83-85`). An empty file hashes
  to `"0"` (`dao/FileAccessMethods.java:238-240`). Otherwise the hash is lowercase hex (`:24`, `:265-271`).
  Because `hash_files` does not report cache hits, classify hits yourself before calling it
  (`Sha1Cache::get(path, modified_millis(path))`) and pass only the misses.
- B20. Errors: hashing continues for the other files, successful results are written to the
  cache, then the **first** error is returned and the build aborts before any metadata is written
  (`:97-101`, `:146-151`).
- B21. Progress: `count*100/total` emitted only when the value changes (`:170-177`).

### Fingerprint and revision (`J:145-158`, `J:376-392`)

- B22. `content_updated = old_sync.is_none() || fingerprint(old) != fingerprint(new)`. Fingerprint
  = map from `relpath.replace('\\','/').to_lowercase()` (Java `toLowerCase(Locale.ROOT)`) to
  `format!("{}:{}", sha1.unwrap_or(""), size)`, over the deep leaf list. A later duplicate key
  (paths that differ only in case) overwrites an earlier one. Compression flags, zsync files,
  hidden folders and settings do **not** affect it.
- B23. `revision = 1` if there is no old serverinfo, otherwise `old.revision + (content_updated as i32)`
  (`J:150-152`). With no old serverinfo the revision is 1 **even if** content changed or old
  changelogs exist.
- B24. `ServerInfo`: `revision`; `buildDate = build_date`; `numberOfFiles` (B13);
  `totalFilesSize` (B14); `numberOfConnections = repository.number_of_connections` (raw);
  `noPartialFileTransfer = repository.no_partial_file_transfer` (`!isUsePartialFileTransfer()`,
  `J:157`); `repositoryContentUpdated = content_updated`; `compressedPboFilesOnly = false` (never
  set by the build; WP12 sets it on upload); `hiddenFolderPaths` (B25) (`J:149-170`).
- B25. Hidden folder paths (`J:160-170`), for each entry `p` of `excluded_folders_from_sync`:
  `main = path[path.rfind(SEP)+1..]` (SEP = `std::path::MAIN_SEPARATOR`; if there is none, the whole
  path); `i = p.to_lowercase().find(SEP + main.to_lowercase())` (first occurrence, `-1` if absent);
  `folder = p[(i + main.len() + 2)..]` with Java `substring` index semantics (`i = -1` gives
  `main.len()+1`); then replace every `\` with `/` (`J:355-369`). Quirks to preserve
  (wire-visible): first-occurrence prefix matching (repository `/srv/repo2/repo`, entry
  `/srv/repo2/repo/@x` → `"/repo/@x"`); a repository path ending in a separator gives `main = ""`;
  an out-of-range index fails the build (Java `StringIndexOutOfBoundsException`; Rust
  `BuildError::HiddenFolder`). Compute indices in UTF-16 code units as Java does (ASCII paths are
  the tested case). Hidden paths do not change the tree: `SyncTreeDirectory.hidden` stays `false`.

### AutoConfig (`J:172-176`)

- B26. `AutoConfig { repository_name: Some(repository.name), protocol: Some(repository.protocol),
  favorite_servers: repository.favorite_servers_set_to_autoconfig (same order) }`. Encode with the
  existing `a3s_types::AutoConfig` encoder (see Q3 on string sharing).
- B27. Java also sets `Repository.autoConfigURL` here (`J:279-280`). That is a local field, not

### Changelogs (`J:178-243`)

- B28. Addon names: `getAddonsByName` (`J:394-406`) is a DFS over directories in list order. A
  directory with `mark_as_addon` contributes its **name** (not path) and is not descended into.
  Others are descended into. Nested addons therefore appear by bare name, and duplicate names
  are possible.
- B29. Case A, no old changelogs file or an empty list: new list = `[c]` with `c.revision =
  revision`, `c.build_date = build_date`, `c.content_updated = content_updated`,
  `c.addons = addon names`, and `c.new_addons = c.addons` iff `revision == 1`, else empty. A
  changelog is created even when `content_updated == false` (`J:180-191`).
- B30. Case B, old list non-empty and `content_updated`: new list = old list + `[c]`. If its length is
  `> 10`, remove **only the first** entry (a hand-made list of 12 old entries stays at 12, `J:196-198`).
  `prev = list[len-2]` (the last old entry). `c.new_addons` = `c.addons` entries not
  `prev.addons.contains` (in `c.addons` order, duplicates kept). `c.deleted_addons` = `prev.addons`
  entries not in `c.addons` (in `prev` order). Comparisons are case-sensitive `equals`
  (`J:192-213`).
- B31. In case B, if an old sync exists, compute `c.updated_addons` (`J:214-240`):
  - `map(sync)` (`J:408-421`, `J:459-466`): DFS like B28. Each addon directory is put into a
    `new HashMap` under key `relpath.to_lowercase()` (Locale.ROOT; the relpath is never empty for
    an addon). A later duplicate key replaces the value but keeps the first key instance and
    position.
  - Iterate `map(new)` keys in **Java `HashMap` iteration order** (B56: sequential puts,
    capacity `hash_map_capacity(distinct keys)`, stable by bucket). For each key also in
    `map(old)`: take both deep leaf lists (B12) and stably sort each by `compareToIgnoreCase` of
    the leaf name. If the sizes differ, add the key. Otherwise, if any position `i` has
    `new[i].sha1 != old[i].sha1`, add the key. Only sha1s are compared, not names.
  - Wire-visible quirks: entries are **lowercased relative paths** (`"@cba_a3"`,
    `"mods/@ace"`), while `addons`, `new_addons` and `deleted_addons` hold bare names with
    original case. Java's `getSha1().equals` throws NPE when a new leaf's sha1 is null. Rust
    compares `Option`s instead (race only).
  - Java commit `50270ca` introduced the lowercase path key. Repositories built by older
    versions (e.g. the WOG fixture) have original-case names here. That is irrelevant for new
    entries, and old entries are carried over unchanged (B44).
- B32. Case C, old list non-empty and `!content_updated`: new list = old list unchanged, with no
  new entry and no trimming (`J:241-243`).
- B33. `Changelogs::MAX_ENTRIES` (10) is the trim threshold.

### Events (`J:245-274`)

- B34. If no old events file exists, the written events object has an empty list. The events
  file is **always** written (`J:246`, `J:342-344`).
- B35. Otherwise `addon_names` = B28 names of the new sync. `dlc_names` = the Java constant names
  of `GameDLCs` in declaration order: `Contact, GM, vn, CSLA, WS, SPE, EF, RF`
  (`constant/GameDLCs.java:9-16`, `J:251-255`). For each old event, in order:
  - the new event has the **same** `name` and `description` instances (`J:257-258`);
  - `old_map = new HashMap; old_map.putAll(old.addonNames); old_map.putAll(old.dlcNames)`
    (null `dlcNames` behaves as empty, `domain/repository/Event.java:43-48`). On a duplicate key the
    addon key instance is kept and the DLC value wins;
  - iterate `old_map` in Java order (B56). If `addon_names.contains(key)` (case-sensitive), put it
    into the new `addonNames`. Else if `key` is a DLC constant name (exact match), put it into the
    new `dlcNames`. Else drop it (`J:262-270`). Values are the old `Boolean` instances;
  - `new.userconfigFolderNames.putAll(old.userconfigFolderNames)`, unfiltered (`J:271`).
- B36. New event maps are fresh `HashMap`s. `addonNames` and `dlcNames` are filled by sequential
  `put`. `userconfigFolderNames` is filled by one `putAll` into an empty map, which has a
  **different** capacity rule (B56).

### zsync stage (`J:283-298`, `RepositoryZsyncProcessor.java`, `RepositoryDeleteZSyncProcessor.java`)

- B37. Runs only if the protocol is a Java `Http` instance, i.e. `ProtocolType::Http | Https`
  (`domain/AbstractProtocoleFactory.java:16-17`; WebDAV is `Webdav`, A3S has no class). Use
  `ProtocolType::is_http()`. Stage text `"Processing *.zsync files..."`.
- B38. For each deep leaf whose file exists, regenerate `<file>.zsync` iff the leaf is in
  `updated_files`, or the `.zsync` is missing, or it has length 0 (`J:595-617`). Content:
  `a3s_zsync::ControlFile::generate(file, len, name, format_mtime(mtime_ms), url, sha1).to_bytes()`
  with `url = protocol_type.prompt() + protocol.url + "/" + relpath`. There is **no port** and no
  URL-encoding (`RepositoryZsyncProcessor.java:71-72`). `sha1` is the leaf's sha1 (`"null"` if
  absent, `HeaderMaker.java:84`). The mtime is formatted in the local time zone with `Locale.US`
  (`HeaderMaker.java:111-116`), which `format_mtime` already does. Byte identity: required.
- B39. Otherwise stage text `"Deleting *.zsync files..."`. Java only deletes leaves whose own
  extension is `.zsync`, and the scan never produces such leaves (B6), so **no `.zsync` file is
  ever deleted** (`RepositoryDeleteZSyncProcessor.java:54-86`). Preserve this no-op
  (wire-visible through B14): emit the stage text and `Progress` events, delete nothing.
- B40. Orphan `.zsync` files (source deleted) are never removed. The `.ebo.zip` files of a
  compressed repository are leaves (B6) and get their own `.zsync`.

### Zip stage (`J:300-317`, `J:548-593`, `ZipBatchProcessor.java`, `DeleteZipBatchProcessor.java`, `ZipDAO.java:112-185`)

- B41. Compressible leaf: the extension after the last `.`, lowercased, is `.pbo` or `.ebo`
  (`a3s_repo_files::layout::is_compressible`). `foo.ebo.zip` is **not** compressible.
- B42. `compressed == true`: stage text `"Processing *.pbo.zip files..."`. For each compressible
  leaf, zip = `<file>.zip`:
  - leaf in `updated_files`: delete the zip, then (re)compress;
  - else, zip missing: compress;
  - else: `leaf.compressed = true` and `leaf.compressed_size = zip file length`, without
    recompressing.
  Compressing writes one entry named after the file (`File.getName()`), method DEFLATE level 9
  (`ZipDAO.java:133-144`). Afterwards `compressed = true` and `compressed_size = length of the
  whole .zip file` (`ZipBatchProcessor.java:69-74`). Semantic compatibility only (D-2): Java's
  `ZipInputStream.getNextEntry()` must read it, and the extracted content must match the source.
  Use ZIP64 only when the source is ≥ 4 GiB. Non-compressible leaves keep `compressed=false`,
  `compressed_size=0`.
- B43. `compressed == false`: stage text `"Deleting *.pbo.zip files..."`. For each compressible
  leaf, delete `<file>.zip` if it exists, and set `compressed = false` on every compressible
  leaf (`J:577-593`, `DeleteZipBatchProcessor.java:54-75`). `deleteFile` swallows failures
  (`dao/FileAccessMethods.java:74-80`). Rust logs them with `tracing::warn!`. Orphan zips stay.

### Instance sharing and graph-level emission (wire-visible)

Java writes one object graph per file. A `String`, `Boolean` or `Date` that is the **same
instance** in two places is written once, then as a back-reference. The rules below are what
Java does when building. They were checked against the WOG fixture (`tests/fixtures/java_repos/wog_ftp`).

- B44. Carried-over objects (old `Changelog`s, old event names, descriptions, keys and values)
  are deserialized Java objects. They keep the instance identity they had in the old stream:
  Java's deserialization re-creates the sharing and the re-serialization reproduces it. WP11
  therefore reads the old `changelogs` and `events` files as raw `a3s_jserial::Graph`s too, and
  re-emits every old `String`/`Date`/`Boolean` node through a memo `old NodeId → new Value`. All
  references to one old node become one new instance. Old `Changelog`/`Event` objects are
  re-emitted with the **current** class descriptors (`a3s_types::wire::changelog_desc` etc.),
  as Java does. An absent object field is emitted as null and an absent primitive as 0/false.
- B45. Builder rules for **new** objects:
  - `racine` (root name) is a literal → `Builder::interned` (already the case in `sync_tree.rs`).
  - Leaf and directory names come from `File.getName()`, a new instance each time →
    `Builder::string`.
  - **`sha1 == "0"`** is the literal from `computeSHA1`, so all empty-file leaves share one
    instance → `Builder::interned("0")` (owned exception in `sync_tree.rs`). Hashes from a
    Java-persisted cache would also be shared (one instance in the repository file). Mixed
    histories cannot be reproduced (Q11).
  - Other sha1s, hidden folder paths and protocol/favorite-server strings are unshared.
- B46. New changelog `c`:
  - every `c.addons` element is a **distinct** new instance, even for duplicate names (the
    existing `a3s_types` `Changelog` encoder dedups by value; do not use it for writing);
  - each `c.new_addons` element is the **same instance** as the `c.addons` element it was taken
    from (B29/B30 iterate `c.addons`, so it is an in-order subsequence);
  - each `c.deleted_addons` element is the **same instance** as the `prev.addons` element it was
    taken from (memo of the old node), so it is a back-reference into the previous changelog;
  - each `c.updated_addons` element is the `HashMap` key instance: if the addon is top-level
    and `name.to_lowercase() == name`, Java's `toLowerCase` returns `this`, so it is the
    **same instance** as that addon's `c.addons` element (WOG shows these back-references).
    Otherwise (nested, or any uppercase character) it is a new string.
  - `buildDate` is a new `Date`.
- B47. New events: `name`, `description`, map keys and `Boolean` values come from the old
  graph's nodes via the memo (B44). `Builder::boolean` is canonical, which matches Java
  autoboxing. If an old stream holds several `Boolean` objects with the same value, they collapse
  into one (known limitation, Q11).
- B48. `ServerInfo` and `AutoConfig` are encoded with the existing `a3s_types` encoders.
  `hiddenFolderPaths` is a `new HashSet` filled by `add` in the iteration order of Java's
  `excludedFoldersFromSync` `HashSet`. That order can't be recovered from the TOML store, so the
  encoder inserts in sorted order, which only matters for bucket collisions (Q11).
- B49. `ArrayList` is used for `Changelogs.list`, `Changelog.*` lists, `Events.list` and
  `AutoConfig.favoriteServers`; `HashMap` for event maps; `HashSet` for `hiddenFolderPaths`.
- B50. Only the top-level relpath is the name instance itself (B11). Deeper relpaths are new
  concatenations.

### Write (`J:319-345`, `dao/A3SFilesAccessor.java:144-201`)

- B51. Run every stage (scan, SHA-1, metadata, zsync, zip) **before** anything is written to
  `.a3s/`. Then create `<path>/.a3s` (single level, `mkdir`, error message
  `"Cannot create directory <path>\nPlease checkout file access permissions."`) and write, in this
  order: `sync`, `serverinfo`, `changelogs`, `autoconfig`, `events`. Each goes through
  `a3s_repo_files::write_a3s` (gzip, temporary file then rename, as in Java). Rust encodes all
  five into memory first, so an encoding error writes nothing. A write failure stops the build
  and leaves the files written so far (Java behaves the same).
- B52. `sync` is written with the post-zip leaf flags (`compressed`, `compressed_size`).
- B53. Graph-level outputs (`changelogs`, `events`) are written through `write_a3s` by wrapper
  types implementing `a3s_types::JavaCodec` whose `encode` drives the given `Builder` (B44–B47).
  Their `decode` captures the raw graph (`Graph: Clone`), so `read_a3s::<RawGraph>(path)` reads old
  files with the gzip size limit.

### Result, repository update, service wrapper

- B54. On success Java re-reads the written metadata and sets `repository.revision =
  serverInfo.revision` (`service/RepositoryService.java:894-918`), then persists the repository,
  including the cache (`service/administration/RepositoryBuildProcessor.java:44-46`). Rust returns
  a `BuildOutcome` whose `sync`, `server_info`, `changelogs`, `auto_config` and `events` are equal
  to `read_a3s` of the written files. `BuildOutcome::apply_to(&mut Repository)` sets `revision`.
  The caller persists the cache and repository (WP14/WP19/WP27).
- B55. Progress: `BuildEvent::Stage(text)` with the five verbatim Java texts (B16, B37, B39, B42,
  B43), `BuildEvent::Progress(0..=100)` per stage, `BuildEvent::Warning(text)` for B10. Java's
  `System.out` counters (`"Number of zsync files generated = N"`, `"Number of files compressed = N"`,
  `"Number of zip files deleted = N"`, `"Number of zsync files deleted = N"`) become `tracing::info!`
  and `BuildOutcome` counters.

### Java `HashMap` model (`build/java_hash.rs`)

- B56. Implement a minimal OpenJDK 25 `HashMap<String,_>` model. It is needed for B31 (key order),
  B35 (`old_map` order) and B36 (write order and capacity):
  - `hash = spread(String.hashCode)` (`a3s_jserial::jdk::java_string_hash`); bucket =
    `hash & (cap-1)`; iteration = entries stably sorted by bucket, ties in insertion order (true
    across resizes because splits preserve relative order; treeified bins with ≥ 8 colliding keys
    in a table ≥ 64 are ignored, as a documented limitation);
  - `put`: if the table is null, `resize()`; a new key is appended; an existing key keeps its
    key instance and position and gets the new value; then `if ++size > threshold resize()`;
  - `resize()`: `cap>0` → `cap*2`, `thr = cap>=16 ? thr*2 : (int)(newCap*0.75f)`; `cap==0 && thr>0` →
    `newCap = thr`, `thr = (int)(newCap*0.75f)`; else 16/12;
  - `putAll(m)` (JDK ≥ 19, JDK-8281631): `s = m.len()`; if `s > 0`: table null →
    `t = ceil(s / 0.75)`, `if t > threshold { threshold = tableSizeFor(t) }`; else
    `while s > threshold { resize() }`; then `put` each entry in `m`'s iteration order;
  - deserialized map with `n > 0` entries (`readObject`): `fc = (n as f32)/0.75f32 + 1.0f32`;
    `cap = if fc < 16 {16} else {tableSizeFor(fc as i32)}`; `threshold = (cap as f32*0.75) as i32`;
    entries inserted in stream order (`a3s_jserial::jdk::map` returns stream order). With `n == 0` the
    table stays null;
  - `writeObject`: `buckets = table_len if >0, else threshold if >0, else 16`; `threshold` field;
    `size`; entries in iteration order.
  - Reference capacities (n → putAll cap/threshold, readObject cap, sequential-put cap):
    1→2/1,16,16; 2→4/3,16,16; 4→8/6,16,16; 6→8/6,16,16; 7→16/12,16,16; 12→16/12,32,16;
    13→32/24,32,32; 24→32/24,64,32; 25→64/48,64,64. Sequential puts equal
    `a3s_jserial::jdk::hash_map_capacity`.
- B57. `a3s_jserial::jdk::Builder::hash_map(&mut self, entries: &[(Value, Value)], buckets: i32,
  threshold: i32) -> Value` (additive): writes a `java.util.HashMap` with the existing descriptor
  (same as `hash_map_str`), `loadFactor 0.75f`, the given `threshold`, block data
  `[buckets, size]`, then the entries **in the given order**, with the key/value `Value`s as given
  (shared instances allowed). `hash_map_str` keeps its behaviour.
- B58. Validation of the model against Java output: the WOG fixture's last changelog (built by
  pre-`50270ca` code, keys = original-case names, 14 addons, cap 32) lists `updatedAddons`
  `[@WOG_Islands, @WOG_Mods, @WOG_ACE]`. The model's iteration order of the 14 names is
  `@RHSUSAF, @RHSAFRF, @RHSSAF, @YuEmod, @TFAR, @RHSGREF, @WOG_Islands, @WOG_Mods,
  @CUP_Terrains_Core, @WOG_Extra, @CUP_Terrains_Maps, @WOG_BW, @WOG_BAF, @WOG_ACE`, which

### Java quirks to preserve (wire-visible)

- Leaf skip uses `contains` on `.zsync`, `.pbo.zip`, `.a3s` (case-sensitive), so `.ebo.zip`
  outputs become leaves (B6, B40).
- `.a3s` directories are skipped at every depth, but `totalFilesSize` only excludes the
  top-level one (B5, B14).
- `totalFilesSize` is computed before the zip/zsync stages and counts their previous outputs
  (B14).
- Empty directories are pruned. `mark_as_addon` is triggered by any child named `addons` in any
  case, file or directory, even if it is later pruned (B5, B10).
- Revision is 1 whenever serverinfo is missing (B23). Only one changelog is trimmed per build
  (B30). A changelog is created on the first build even without a content change (B29).
- `updatedAddons` holds lowercased relative paths in `HashMap` order. The other lists hold names
  (B31).
- Non-HTTP builds never delete `.zsync` files (B39). The zsync URL has no port (B38).
- `compressedPboFilesOnly` is always false in a built serverinfo (B24).
- The hidden-folder path computation, including its prefix and index bugs (B25).
- Event filter: DLC keys also present as addon names go to `addonNames` with the DLC's value
  (B35).
- String/Boolean/Date instance sharing and `HashMap` capacities (B44–B57).

### Java quirks that may be dropped (local-only; needs an approved deviation)

- Cancel: Java's sub-processors just stop scheduling work. `run()` returns normally and the
  build goes on to write metadata with null sha1s or partial zips
  (`RepositorySHA1Processor.java:134`, `ZipBatchProcessor.java:61-79`, UI
  `RepositoryBuilder.java:181-183`). Rust returns `BuildError::Cancelled` and writes no `.a3s`
  file (Q4).
- `.zsync` files are written non-atomically (`MetaFileMaker.java:79-118`). Rust writes a temporary
  file and renames it. Final bytes are identical (Q10).
- zsync is single-threaded in Java (`RepositoryZsyncProcessor.java:46`). Rust may use
  ≤ `min(8, cpus)` threads (Q5).
- Symlink loops cause infinite recursion in Java (`StackOverflowError`). Rust detects them and
  fails with `BuildError::Scan` (Q8).
- Directory-listing order for names that differ only in case (B8, Q7).
- Java's temporary file names (`<name>.<random>.tmp`) are not reproduced.
- Java mutates the in-memory repository before the build finishes (`J:277-281`). Rust has no
  partial updates.
- Two `new Date()` calls (serverinfo, changelog) can differ by 1 ms. Rust uses one `build_date`.

### Errors, cancellation, progress

- Any read error on old metadata, scan error (B9), walk error (B15), hash error (B20), hidden
  folder index error (B25), zsync error (first one, after the others finish:
  `RepositoryZsyncProcessor.java:59-61`), zip error (first one, which cancels the remaining zips:
  `ZipBatchProcessor.java:76-79`, `:51-53`) aborts the build **before** `.a3s` is written. Partially
  generated `.zsync`/`.zip` files stay (as in Java). The SHA-1 cache keeps the hashes computed
  so far.
- Zip and `.zsync` deletion failures are swallowed and logged.
- `cancel: &AtomicBool` is checked between stages and before each file in every parallel stage.
  An in-progress zip is abandoned and its partial `.zip` deleted (`ZipDAO.java:142-153`). Result:
  `Err(Cancelled)` (Q4).
- No retries anywhere.

### Concurrency

- SHA-1: `max(1, min(8, availableProcessors))` (`RepositorySHA1Processor.java:39,83-85`) →
  `a3s_hash::hash_files`.
- zsync generation: 1 thread in Java (Q5).
- Zip, zip deletion, zsync deletion: `availableProcessors` threads
  (`ZipBatchProcessor.java:37-38`, `DeleteZipBatchProcessor.java:39-40`,
  `RepositoryDeleteZSyncProcessor.java:39-40`) → a named rayon pool (`a3s-zip-{i}`).
- Stages run one after another. Progress callbacks may be invoked from worker threads
  (`on_event: &(dyn Fn(BuildEvent) + Sync)`).

## Orchestrator amendments (2026-10-11, from WP01 measurements on JDK 25)

- Q3: autoconfig `repositoryName` is written as a back-reference to the first favorite server whose `repositoryName` equals it by value (Java shares the String instance).
- B56: HashMap/HashSet `readObject` capacity on JDK 19+ is `tableSizeFor(ceil(n / loadFactor))` (e.g. n = 12 → 16, not 32). Use the JDK 25 formula; WP01 fixtures verify it.
- D-14 (user, 2026-10-11): the builder excludes BOTH `.pbo.zip` and `.ebo.zip` (generally: any `<name>.zip` produced by the compression stage) from the sync tree. Java only excludes names containing `.pbo.zip` (RepositoryBuildProcessor.java:487-489), so its own `X.ebo.zip` becomes a leaf on the next build, bumps the revision and marks the mod updated. Rust fixes this (wire-visible, approved by the user). Tests against `tests/fixtures/java_built/*_zip` must expect the Java quirk only where comparing against Java output, and assert the fixed behaviour for Rust-built repos.
