## Scope

- `ViewerContext`: the single object the egui app holds, replacing Java's `Facade`
  (`ui/Facade.java`). It owns the tokio runtime, the shared `AppState`, the command bus
  (UI → background), the event channel (background → UI) with a repaint callback, and the task
  registry.
- `AppState`: WP14's `ClientData` (configuration, preferences, profiles, repositories) plus the
  transient per-repository runtime state Java keeps in `transient` fields of `Repository`
  (status, remote metadata, download report, last transferred index), the `Facade` flags
  (`devMode`, `runMode`), and one state struct per domain.
- One event enum that replaces the `controller/*` observer interfaces and the `UIConstants.OP_*`
  update codes. Progress uses WP07's `a3s_sync::events::SyncEvent` as is.
- A task registry: named background tasks, one `CancellationToken` each (children of a root
  token), exclusivity keys, outcome reporting, panic capture, and coalesced progress snapshots.
- The periodic repository checker (`TasksManager` + `TaskCheckRepositories`): pure schedule logic,
  an injectable `Clock`, at most 4 concurrent checks, status update and persistence through WP14,
  notification de-duplication and auto-update requests through WP07's `decide_check_cycle`.
- The manual "check repositories" operation (`ProgressSynchronizationDialog`), which shares the
  same check engine and concurrency limit.
- Stub domain modules (`repositories`, `sync`, `admin`, `profiles`, `launch`, `tools`), so that later
  viewer WPs only add handlers inside their own module.

## Behaviour contract

### Context and runtime (`ui/Facade.java`, `ui/main/MainPanel.java`, `main/ArmA3Sync.java`)

- B1. `ViewerContext::new(client: ClientData, options: ContextOptions) -> Result<ViewerContext,
  ContextError>`. The caller has already run WP14's `ClientData::load` and shown its warnings
  (WP22). `ContextOptions` has these fields and defaults:
  - `worker_threads = 4`;
  - `runtime: Option<tokio::runtime::Handle> = None` (tests may pass an external runtime; the
    context then owns none);
  - `checker: Arc<dyn RemoteChecker> = Arc::new(NetworkChecker)`;
  - `clock: Arc<dyn Clock> = Arc::new(SystemClock)`;
  - `repaint: RepaintHook = RepaintHook::noop()`;
  - `dev_mode = false`, `run_mode = false`;
  - `shutdown_timeout = 2 s`.

  With `runtime == None` it builds a multi-thread runtime with `worker_threads` workers, thread
  name `a3s-worker` (CODE_STYLE: named threads), `enable_all()`. A build failure gives
  `ContextError::Runtime(io::Error)`. Nothing is started yet: no checker and no task (Java starts
  background work separately, `ui/main/MainPanel.java:584-596`).
- B2. `AppFlags { dev_mode, run_mode }` replaces `Facade.devMode` / `runMode`
  (`ui/Facade.java:16-46`), both set at start (`main/ArmA3Sync.java:231-233`). They are plain `pub`
  fields of `AppState.flags`. `run_mode` is changed later by the preferences dialog on Windows
  (`ui/help/PreferencesDialog.java:404-416`, WP29). Java's panel references
  (`ui/Facade.java:20-30, 48-126`) are **not** ported: egui panels are immediate-mode and read
  `AppState` directly.
- B3. State access. `AppState` lives in `Arc<parking_lot::RwLock<AppState>>`.
  - `ViewerContext::read()` returns a read guard (UI, every frame).
  - `ViewerContext::mutate(change: Option<Change>, f: impl FnOnce(&mut AppState) -> Result<R, E>)
    -> Result<R, E>` runs `f` under the write lock. If `f` returns `Ok` and `change` is `Some`, it
    emits `AppEvent::Changed(change)` (B8).

  Rule for every module: never hold a guard across `.await`, and never do network or recursive
  file I/O under the lock. WP14's small TOML writes are allowed. `parking_lot` guards are `!Send`,
  so the compiler enforces the first part inside spawned tasks.
- B4. Thin wrappers keep the runtime state consistent with WP14 operations:
  - `remove_repository(name) -> Result<bool, ServiceError>`: first cancel every task whose key has
    `repository == Some(name)` (B19). Then call `ClientData::remove_repository` (WP14 B39). On
    `Ok`, drop the runtime entry and call `NotificationTracker::forget(name)`, then emit
    `Changed(Repository)`.
  - `rename_repository(old, new) -> Result<(), ServiceError>`: call
    `ClientData::rename_repository` (WP14 B38). On `Ok`, move the runtime entry from `old` to
    `new`, call `forget(old)`, then emit `Changed(Repository)`. Running tasks keep their key (they
    finish or fail on their own).
  - `set_preferences(p: Preferences) -> Result<(), ServiceError>`: call
    `ClientData::set_preferences` (WP14 B21). On `Ok`, if `check_repositories_frequency` changed,
    call `reschedule_checks(new)` (B27, Q3).
  - `save_on_exit(height, width) -> Result<(), ServiceError>` = `ClientData::save_on_exit`
    (WP14 B7). See B32 for the order.

### Events (`controller/*`, `ui/UIConstants.java`, `ui/repository/workers/SwingUi.java`)

- B7. Background code never touches UI objects. It sends `AppEvent`s into an unbounded
  `crossbeam_channel` and then calls the `RepaintHook`. This replaces
  `SwingUi.run` / `SwingUtilities.invokeLater` (`ui/repository/workers/SwingUi.java:9-12`). The UI
  drains the channel with `poll_events() -> Vec<AppEvent>` (non-blocking, in send order) once per
  frame. `next_event_timeout(d) -> Option<AppEvent>` blocks for at most `d` (for tests and
  non-egui hosts). Java runs the action inline when already on the EDT. In Rust, an event emitted
  on the UI thread is seen at the next `poll_events`. Sending never blocks and never fails: if the
  receiver is gone, the event is dropped.
- B8. `Change` replaces the `OP_*` codes (`ui/UIConstants.java:14-20`), same order and Java value
  in the doc comment: `Profile` (1), `AddonFiles` (2), `AddonPriority` (3), `AddonSelection` (4),
  `Online` (5), `Repository` (6), `Group` (7). `#[non_exhaustive]`. Java broadcasts every code to
  every panel, and `Profile` also rebuilds the profiles menu (`ui/main/MainPanel.java:600-614`).
  That fan-out is WP22's job.
- B9. `RepaintHook` wraps `Arc<dyn Fn() + Send + Sync>`. It provides `noop()`, `from_fn(f)` and,
  with the `egui` feature, `from_egui(ctx: egui::Context)`, which calls `ctx.request_repaint()`.
  The hook is called once after every queued event and after every snapshot update (B12). It can
  be replaced at runtime with `set_repaint_hook`, because eframe gives the `egui::Context` only
  when the app is created.
- B10. `AppEvent` (`#[non_exhaustive]`):
  - `Changed(Change)`;
  - `Task(TaskEvent)` (B11);
  - `Error { context: String, error: EventError }`: a background failure that is not tied to a
    task outcome, e.g. a persistence failure in B24;
  - one variant per domain: `Repositories(repositories::Event)`, `Sync(sync::Event)`,
    `Admin(admin::Event)`, `Profiles(profiles::Event)`, `Launch(launch::Event)`,
    `Tools(tools::Event)`.
- B11. `TaskEvent`:
  - `Started(TaskInfo)`;
  - `Sync { id: TaskId, event: SyncEvent }`: the queued (non-coalesced) WP07 events of a task;
  - `Finished { info: TaskInfo, outcome: TaskOutcome }`.
- B12. Coalescing. When a task's `EventSender` (B18) receives one of `Progress`, `TransferTotal`,
  `Transfer`, `Speed`, `DiskUsage`, `ActiveConnections` or `ConnectionWaiting`, the event is **not**
  queued. Instead it updates the task's `TaskSnapshot`, then the repaint hook is called. Every
  other variant is queued as `TaskEvent::Sync`. That includes `Phase`, `MetadataFetched`,
  `FileStarted`, `FileDone`, `FileFailed`, `LastIndexTransferred`, `ConnectionLost`, `Finished`,
  and any future variant (`SyncEvent` is `#[non_exhaustive]`). `Phase` also updates the snapshot.
  `task_snapshot(id) -> Option<TaskSnapshot>` returns a clone. The snapshot is removed when the
  task finishes. This bounds the queue when the window is hidden to the tray and the UI does not
  poll (Q8).

  `TaskSnapshot { phase: Option<Phase>, progress: Option<(Phase, u8)>, total: Option<(u64, u32)>,
  transfer: Option<TransferProgress>, speed: Option<u64>, disk_usage: Option<u64>,
  active_connections: Option<u32>, waiting_seconds: Option<u32> }`, each field the last value seen.
- B13. Observer mapping (documentation table in `event.rs`, and the contract for later WPs).
  Already-covered rows point to the WP07 variant:

  | Java (`controller/`) | Rust |
  | --- | --- |
  | `ObserverText.update(String)` (`ObserverText.java:4`) | `SyncEvent::Phase(Phase)` (`Phase::label` gives the Java texts) |
  | `ObserverCountInt.update(int)` (`ObserverCountInt.java:4`) | `SyncEvent::Progress { phase, percent }`; admin check error count → `admin::Event` (WP27) |
  | `ObserverCountLong.update(long)` (`ObserverCountLong.java:4`) | `TransferTotal` / `Transfer` / `Speed` / `DiskUsage` (by registration site) |
  | `ObserverDownload.*` (`ObserverDownload.java:7-23`) | `TransferTotal`, `Transfer`, `Speed`, `ActiveConnections`, `Finished(Success / CompletedWithErrors / TooManyErrors)`, `ConnectionLost` |
  | `ObserverUpload.*` (`ObserverUpload.java:5-15`) | `TransferTotal`, `Transfer`, `Speed`, `LastIndexTransferred`, `ConnectionLost` |
  | `ObserverUncompress.start/update/end/error` (`ObserverUncompress.java:7-13`) | `Phase(Uncompressing)`, `Progress { Uncompressing, % }`, next phase, `FileFailed` / `Finished(Failed)` |
  | `ObserverConnectionLost.lost` (`ObserverConnectionLost.java:6`) | `SyncEvent::ConnectionLost` |
  | `ObserverEnd.end` (`ObserverEnd.java:5`) | `TaskEvent::Finished { outcome: Completed }` (or `SyncEvent::Finished(Success)`) |
  | `ObserverError.error(List)` (`ObserverError.java:6`) | `TaskOutcome::Failed` / `Outcome::CompletedWithErrors` |
  | `ObserverStart.start` (`ObserverStart.java:5`) | `TaskEvent::Started` / `SyncEvent::Phase` |
  | `ObserverProceed.proceed` (`ObserverProceed.java:4`) | none: internal sequencing (`await`), not an event |
  | `ObserverErrorMessage` (`ObserverErrorMessage.java:5-7`) | none: never implemented outside `controller/` (dead in Java) |
  | `Observable*` (`ObservableDownload.java:5-27` etc.) | none: replaced by `EventSender::emit` |

### Tasks (`ui/main/tasks/TasksManager.java`, `ProgressSynchronizationDialog.java`)

- B14. `TaskKind` (`#[non_exhaustive]`, `Copy`) lists every background operation of the client now,
  so later WPs do not edit the shared file: `PeriodicCheck`, `CheckRepositories`, `Download`,
  `AutoUpdate`, `Build`, `AdminCheck`, `Upload`, `UploadEvents`, `ImportAutoConfig`,
  `PartialTransferTest`, `AddonScan`, `Launch`, `ExtractBikeys`, `RptTail`, `InstallRadioPlugin`,
  `SelfUpdateCheck`. `TaskKind::label()` gives a short English text (e.g. `"Checking repositories"`)
  for logs and UI.
- B15. `TaskKey { kind: TaskKind, repository: Option<String> }`. `TaskInfo { id: TaskId, key:
  TaskKey, started: SystemTime }`. `TaskId` is a `u64` that increases from 1 and is never reused.
- B16. `Cx::spawn_task(key, exclusive: bool, f: impl FnOnce(TaskCtx) -> Fut) -> Result<TaskId,
  ContextError>` where `Fut: Future<Output = Result<(), TaskError>> + Send + 'static`:
  1. after shutdown started → `ContextError::Closed`;
  2. if `exclusive` and a running task has an equal `key` → `ContextError::TaskBusy { id, key }`;
  3. register the task with a fresh `root.child_token()` and an empty snapshot, emit
     `TaskEvent::Started(info)`;
  4. spawn `f(task_ctx)` on the runtime inside a supervising task that awaits its `JoinHandle`;
  5. on completion compute the `TaskOutcome` (B17), remove the task and its snapshot, then emit
     `TaskEvent::Finished`. Removal happens before the event, so `running_tasks()` no longer lists
     the task when the UI sees `Finished`.
- B17. `TaskOutcome`: `Ok(())` → `Completed`. `Err(_)` when the task's token is cancelled, or
  `Err(TaskError::Cancelled)` → `Cancelled`. Other `Err(e)` → `Failed(EventError)`. A panic →
  `Panicked(String)` with the panic message (`&str` / `String` payload, otherwise
  `"task panicked"`), logged with `tracing::error!`. The context stays usable after a panic.
  `TaskError`: `Cancelled`, `Remote(RemoteError)`, `Service(ServiceError)`, `Message(EventError)`.
  It converts to `EventError` through `EventError::from_remote` / `UserFacing`.
- B18. `TaskCtx { id, cancel: CancellationToken, cx: Cx }` with:
  - `transfer_ctx() -> a3s_transport::TransferCtx`, with `cancel = self.cancel.clone()`, a fresh
    progress counter and no throttle;
  - `sync_events() -> a3s_sync::EventSender`, which routes into B12 for this task id.
- B19. Cancellation:
  - `cancel_task(id) -> bool` (`false` if the id is unknown or finished);
  - `cancel_repository_tasks(name) -> usize` (count cancelled);
  - `cancel_all()`;
  - `running_tasks() -> Vec<TaskInfo>` in id order;
  - `is_running(&TaskKey) -> Option<TaskId>`.

  Cancelling only fires the token. Tasks must stop promptly (WP07/WP09 guarantee < 1 s for their
  own work), and the `Finished` event reports the result.
- B20. Command bus. `Command` has one variant per domain: `Repositories(repositories::Command)`,
  `Sync(sync::Command)`, `Admin(admin::Command)`, `Profiles(profiles::Command)`,
  `Launch(launch::Command)`, `Tools(tools::Command)`.
  - `ViewerContext::send(cmd) -> Result<(), ContextError>` pushes it into an unbounded
    `tokio::sync::mpsc` channel. A dispatcher task on the runtime receives commands in order and
    calls `<domain>::handle(&cx, cmd)`.
  - Handlers are synchronous `fn`s. They do quick in-memory work and/or `spawn_task`, and must not
    block or await. A handler error (for example `TaskBusy`) is emitted as `AppEvent::Error` with
    `context` = the command's `Debug` text.
  - After shutdown, `send` returns `ContextError::Closed`.

  The `admin`, `profiles`, `launch` and `tools` `Command` and `Event` enums start **empty**
  (uninhabited; `match c {}`), and their `State` structs are empty `Default` structs.
  `sync::Command` and `sync::Event` start with the auto-update variant of B26.

### Repository checks (`TaskCheckRepositories.java`, `ProgressSynchronizationDialog.java`)

- B21. `RemoteChecker` is the only network seam:
  `fn check<'a>(&'a self, req: CheckRequest<'a>) -> BoxFuture<'a, Result<(), RemoteError>>`, with
  `CheckRequest { repository_name, protocol, options, metadata: &mut RemoteMetadata, ctx:
  &TransferCtx, events: &EventSender }`. `NetworkChecker` forwards to
  `a3s_sync::remote::check_repository` (WP07: connect, fetch the five `.a3s` files, update
  `metadata` in place). Tests inject fakes.
- B22. Check engine `check_many(cx, names, trigger, task: &TaskCtx) -> Vec<RepositoryCheckResult>`,
  shared by B23 and B25:
  1. Snapshot under the read lock, in `ClientData::repositories()` order (name order; Java iterates
     a `HashMap`, `service/RepositoryService.java:150-159`, WP14 DV10), restricted to `names`
     (`None` = all), into `{ name, protocol, notify, auto }`. Unknown names are skipped with
     `tracing::warn!`.
  2. Transport options per repository = `a3s_sync::proxy::transport_options(&protocol,
     client.proxy())` (WP14 B55). A `ProxyError` makes that repository's check fail with
     `EventError::new(ErrorKind::InvalidInput, err.to_string())` and sets its
     `metadata.server_info = None`, like a Java connect failure (WP07 `check_repository`). No
     connection is attempted.
  3. Run all checks concurrently. Each check:
     1. takes the repository's async mutex (one check per repository at a time across periodic and
        manual runs, Q5);
     2. takes one permit of the context-wide `Semaphore(MAX_CONCURRENT_REPOSITORY_CHECKS)` (= 4,
        `TaskCheckRepositories.java:26, 66-67`), so no more than 4 checks run at once in the whole
        process (Q5);
     3. clones the current `RemoteMetadata` out of the runtime entry (cheap `Arc`s) and calls
        `checker.check(..)` with `task.transfer_ctx()` and an `EventSender` (B23/B25 say which);
     4. unless the result is `RemoteError::Cancelled`, writes the metadata back into the runtime
        entry and sets `last_check_error` (`None` on success, `EventError::from_remote` on failure);
        a cancelled check leaves the previous metadata untouched;
     5. logs a failure with the trigger's error text (B23 / B25).
  4. Return one `RepositoryCheckResult { name, outcome: CheckOutcome, status:
     Option<RepositoryStatus> }` per snapshot entry, **in snapshot order** (Java waits for all with
     `invokeAll`, `TaskCheckRepositories.java:69`). `CheckOutcome` is `Ok`, `Failed(EventError)` or
     `Cancelled`. `status` is filled by B24.
- B24. Apply step, after all checks of a run (`TaskCheckRepositories.java:78-81`,
  `ProgressSynchronizationDialog.java:139-145`), for each result in order, skipping `Cancelled`
  ones and names no longer present:
  1. under the write lock, clone `configuration`, then call
     `client.update_repository(name, |r| { u = a3s_sync::status::update_repository(r, &mut cfg,
     &metadata); Ok(u.repository_changed) })` (WP07 B18, WP14 B40);
  2. if `u.configuration_changed`: `client.update_configuration(|c| { *c = cfg; true })`;
  3. `runtime.status = u.status`, `result.status = Some(u.status)`.

  A persistence error (step 1 or 2) is logged with `tracing::warn!` and emitted as `AppEvent::Error
  { context: "Saving repository <name>", .. }` (or `"Saving configuration"`). The status is still
  set. Java persists nothing here and writes at exit (Q9).

  After the loop, emit `Changed(Change::Repository)` once
  (`TaskCheckRepositories.java:83`, `ProgressSynchronizationDialog.java:74, 147`), then
  `Repositories(Event::CheckCompleted { trigger, results })`.
- B25. Manual check, `repositories::Command::Check { names: Vec<String> }`
  (`ProgressSynchronizationDialog.java:82-154`; a single name is the `init(String)` form, `:30-80`):
  - empty `names` → do nothing and log `"No repository to synchronize with."`. Java returns before
    that print when the list is empty (`:84`) and prints it only on an unreachable path (`:93-94`);
    Rust logs it and emits `CheckCompleted` with no results, so the UI's progress dialog always
    closes.
  - otherwise `spawn_task(TaskKey { CheckRepositories, None }, exclusive = true)`. A second request
    while one runs → `TaskBusy` (Java disables the buttons, `:34, 88`). The task:
    1. logs `"Synchronization with repository: <name>"` for one name (`:32-33`), else
       `"Synchronization with repositories..."` (`:86`);
    2. runs B22 with `task.sync_events()`, so the UI may show phases (Java shows an indeterminate
       bar, `:35, 89`), then B24;
    3. logs a failed check as `"Error when checking repository <name>: <message>"` (note `": "`,
       not `":\n"`, `:111-115`);
    4. logs `"Synchronization with repositories done."` (`:66, 136-137`).
  - `repositories::Command::CancelCheck` cancels the running manual check and logs
    `"Synchronization with repositories canceled."` (`:156-166`). Java cancels only the last
    connection created (one shared field, `:105-106, 162-163`) and skips not-yet-started checks
    (`:102`). Rust cancels all of them (local-only).
  - No auto-update and no notification, and the tracker is untouched (the manual dialog does
    neither).
  - Error presentation (`RepositoryException` → error dialog, I/O → warning dialog, other →
    unexpected-error dialog, suppressed after cancel, `:44-63`) is WP25's: it reads the results.
- B26. Periodic cycle (`TaskCheckRepositories.run`, `:38-171`), run as task
  `TaskKey { PeriodicCheck, None }` (exclusive; the scheduler never overlaps cycles, B28):
  1. log `"Checking repositories..."` (`:43`);
  2. B22 over all repositories with `EventSender::noop()` (Java shows nothing during the cycle).
     Failures are logged with `a3s_sync::remote::check_error_message(name, err)`, i.e.
     `"Error when checking repository <name>:\n<message>"` (`:56-58`);
  3. if the cycle's token was cancelled (shutdown), log
     `"Checking repositories has been anormaly interrupted."` (sic, `:70-71`) and return
     `Err(Cancelled)` **without** B24 or anything below (Java continues, but the Rust context is
     shutting down);
  4. log `"Checking repositories done."` (`:76`), then B24 with `trigger = Periodic`;
  5. build `CheckedRepository { name, notify, auto, status, server_revision }` for every applied
     result, with `notify`/`auto` from the **snapshot** taken at cycle start (Java uses the DTO
     list, `:45, 111-117, 138-158`) and `server_revision = metadata.server_revision()` (`:147-154`).
     Call `decide_check_cycle(&checked, &mut state.repositories.tracker)` (WP07 B23);
  6. if `decision.console_message()` is `Some`, log it (`:100-107`);
  7. for each name in `decision.auto_update`, log `"Auto updating repository: <name>"` (`:121`),
     then call `sync::auto_update_due(cx, &decision.auto_update)`. In WP21 this hook only emits
     `AppEvent::Sync(sync::Event::AutoUpdateRequested { repositories })`. WP26 replaces its body
     with the WP10 pipeline (Java opens a hidden tab, runs `autoUpdate` and closes it at the end,
     `:123-133`);

     `Repositories(Event::UpdatesAvailable { repositories: decision.notify })`
     (`:160-170`). UI contract (WP22/WP25): show the tray message

     hidden to the tray, also select the Sync tab and show the updated-repositories dialog

  The event order of one cycle is therefore fixed: `Task(Started)`, `Changed(Repository)`,
  `Repositories(CheckCompleted)`, optional `Sync(AutoUpdateRequested)`, optional
  `Repositories(UpdatesAvailable)`, `Task(Finished)`.

### Schedule (`TasksManager.java`, `MainPanel.java:1073-1087`, `PreferencesDialog.java:418-427`)

- B27. Pure `CheckSchedule { frequency, next_due: Option<SystemTime> }`, independent of any
  runtime:
  - `period(f) -> Option<Duration>` = `f.minutes() * 60 s`, `None` for `Disabled`
    (`MainPanel.java:1082-1083`);
  - `at_startup(f, now)`: `next_due = Some(now)` for **every** frequency, including `Disabled`
    ("execute now, no repetition", `MainPanel.java:1079-1080`; quirk kept: `Disabled` still checks
    once at start-up);
  - `after_change(f, now)`: `Disabled` → `None`; otherwise `Some(now + period)`. The first check
    comes one period after the change, not immediately (`PreferencesDialog.java:421-426`);
  - `on_cycle_started(&mut self, started)`: `next_due = started + period`, or `None` for
    `Disabled`. Java's `Timer.schedule(task, delay, period)` is fixed-delay: the next run is due
    one period after the **start** of the current one, and runs never overlap (single timer
    thread), so a cycle longer than the period is followed immediately by the next one.
- B28. Scheduler loop, started by `ViewerContext::start_background()` (Java `initBackGround` →
  `checkRepositories`, `MainPanel.java:584-596, 1073-1087`):
  - schedule = `at_startup(preferences.check_repositories_frequency, clock.now())`;
  - loop: if `next_due` is `None`, wait for a reschedule signal. Otherwise race
    `clock.sleep_until(due)` against the reschedule signal and the stop token. When the sleep
    wins: `on_cycle_started(clock.now())`, spawn the B26 task, and **await its end** before
    looping (no overlap);
  - a second `start_background()` while the loop runs is a no-op;
  - Java runs the self-update check first on the same thread and blocks on its modal dialog
    (`MainPanel.java:589-592`). Rust starts the checker on its own; WP22 decides the order
    (Q6).
- B29. `reschedule_checks(f)` (Java `TasksManager.reset()` + new `TaskCheckRepositories`,
  `PreferencesDialog.java:419-427`): replace the schedule with `after_change(f, clock.now())` and
  wake the loop. A cycle already running is **not** cancelled and finishes normally (Java's
  `Timer.cancel` does not interrupt a running task). The next due time comes from the new schedule,
  because `on_cycle_started` ran before the cycle (Q11). The `NotificationTracker` is kept (Q4).
- B30. `stop_background()` (Java `TasksManager.reset()` at exit, `MainPanel.java:882`): stop the
  loop and cancel a running periodic cycle. `start_background()` may be called again afterwards
  (Q7).
- B31. `Clock` trait: `now() -> SystemTime` and `sleep_until(deadline: SystemTime) ->
  BoxFuture<'static, ()>`.
  - `SystemClock` sleeps in slices of at most 30 s and re-reads `SystemTime::now()` after each one,
    so a check that became due during system suspend runs within 30 s of resume, as Java's
    wall-clock `Timer` does (Q2).
  - `ManualClock` (always compiled, for tests of this crate and of WP25/WP26): `new(start)`,
    `advance(d)` (wakes every sleeper whose deadline is now reached), `set(t)`, `sleepers() ->
    usize`, and `async wait_for_sleepers(n)`, which resolves once at least `n` futures are parked
    so tests never race the scheduler.

### Shutdown (`MainPanel.java:877-900`)

- B32. Exit sequence, driven by WP22:
  1. `prepare_exit()` runs B30, `cancel_all()` (Java `dynamicTabManager.cancelOperations()`,
     `:883`), and waits up to `shutdown_timeout` until no task is running. Tasks still running after
     the timeout are logged with `tracing::warn!` (kind, repository). The call returns the list
     of those tasks;
  2. `save_on_exit(height, width)` (`:887`). On error, WP22 shows
     `"<message>\nExit ArmA3Sync anyway?"` (`:889-891`). If the user stays, WP22 calls
     `start_background()` again (Java leaves the timer dead until restart, Q7);
  3. `shutdown()`: close the command channel (`send` → `Closed`), cancel the root token, and for an
     owned runtime call `Runtime::shutdown_timeout(shutdown_timeout)`. It is idempotent. `Drop`
     calls it if it was not called. Note: dropping the context **inside** an async context panics
     (tokio rule for owned runtimes), so the doc comment says to drop it on the UI thread.

### Java quirks to preserve (wire-visible)

- None. This WP reads and writes no repository data. Persistence goes through WP14, network
  access through WP07.

### Java quirks kept although local-only (cheap)

- `Disabled` still runs one check at start-up (B27).
- After a frequency change, the first check comes one period later, not immediately (B27).
- Fixed-delay schedule measured from the start of a cycle, with no overlapping cycles (B27, B28).
- Notifications only for `notify && !auto`, once per server revision; a non-updated repository

  (`":\n"` periodic, `": "` manual) (B25, B26).

### Java quirks that may be dropped (local-only; needs an approved deviation)

- DV1 One global limit of 4 concurrent repository checks across periodic and manual runs, and at
  most one check per repository at a time. Java's manual check uses `availableProcessors()`
  threads and can overlap the timer's pool on the same repository
  (`ProgressSynchronizationDialog.java:123-125`) (Q5).
- DV2 A cancelled manual check cancels every in-flight connection, not just the last one created
  (B25).
- DV3 Status side effects (hidden folders, client connections, merged favorite servers) are
  persisted right after each check instead of at exit (B24, Q9).
- DV4 Progress events are coalesced into snapshots (B12, Q8).
- DV5 The notification tracker survives a reschedule (B6, B29, Q4).
- DV6 Rescheduling only when the frequency actually changed (B4, Q3).
- DV7 The checker starts independently of the self-update check (B28, Q6).
- DV8 The background checker can be restarted after a failed exit (B32, Q7).
- DV9 Shutdown skips the post-check work of an interrupted periodic cycle (B26.3).
- DV10 An event emitted from the UI thread is delivered on the next poll instead of inline (B7).

### Errors, cancellation, progress

`ContextError` (`thiserror`):

| Variant | Text |
| --- | --- |
| `Closed` | `The application is shutting down.` |
| `TaskBusy { id: TaskId, key: TaskKey }` | `{key.kind.label()} is already running.` |
| `Runtime(std::io::Error)` | `Failed to start the background runtime: {0}` |
| `Service(ServiceError)` | transparent (WP14) |

`impl a3s_error::UserFacing for ContextError`: `Closed` → `Cancelled`, `TaskBusy` → `InvalidInput`,
`Runtime` → `Internal`, `Service` → the WP14 kind.

- No retries anywhere in this crate. A failed periodic check is retried at the next cycle, as in
  Java.
- Cancellation: every task gets a child token of the root token (B16). `prepare_exit`/`shutdown`
  cancel the root.
- Progress: `TaskEvent::Started`/`Finished` for every task, `SyncEvent`s for manual checks,
  snapshots (B12). Periodic checks emit no `SyncEvent`s.
- Logging: `tracing::info!` for the Java `System.out` lines quoted above. `tracing::warn!` for
  persistence failures, unknown names and tasks that outlive the shutdown timeout.
  `tracing::error!` for panics.

### Concurrency

- Java: one non-daemon `java.util.Timer` thread (`TasksManager.java:9-13, 30-33`). Each cycle
  creates a fixed pool of `max(1, min(4, n))` threads (`TaskCheckRepositories.java:66-67`). The
  manual check uses a pool of `availableProcessors()` threads. Each UI worker is an ad-hoc
  `Thread`.
- Rust: one multi-thread tokio runtime (`worker_threads = 4`, `a3s-worker`), one dispatcher task,
  one scheduler task, one task per operation, and at most 4 concurrent repository checks per
  process (semaphore). Blocking work (SHA-1, decoding) is already moved to `spawn_blocking` by
  upstream crates. `AppState` behind a `parking_lot::RwLock` that is never held across `.await`.

## Acceptance tests

All tests run without egui and without network, except A15 (closed local port). Tests use
`ClientData::from_parts` over a `tempfile` store, a `FakeChecker` (scripted per repository: a
result, a `RemoteMetadata` to install, an optional gate `Arc<tokio::sync::Semaphore>` to hold the
check, and an in-flight counter that records the maximum) and `ManualClock`. Event assertions use
`next_event_timeout(5 s)`.

- A1 (unit, `checker.rs`) `CheckSchedule` table. Covers B27.
  - `period`: 15/30/60 min, `Disabled` → `None`.
  - `at_startup(Disabled, t)` = `Some(t)`; after `on_cycle_started(t)` → `None`.
  - `at_startup(Freq1, t)` = `Some(t)`; `on_cycle_started(t + 2 min)` → `t + 17 min` (from the start,
    not the end).
  - `after_change(Freq2, t)` = `t + 30 min`; `after_change(Disabled, t)` = `None`.
- A2 (unit, `clock.rs`) `ManualClock`: a sleeper for `t + 10 s` is pending after `advance(9 s)`,
  resolves after `advance(1 s)`; `sleepers()` counts it while parked; a deadline in the past
  resolves at once. `SystemClock::sleep_until(now - 1 s)` resolves at once, and
  `sleep_until(now + 50 ms)` resolves after ≥ 50 ms. Covers B31.
- A3 (`tests/tasks.rs`) Lifecycle. Covers B11, B14-B17, B19.
  - A task returning `Ok` gives `Started` then `Finished { Completed }`. `running_tasks()` lists it
    in between and not after `Finished` is received.
  - An `Err(Remote(MissingMetadata(Sync)))` gives `Failed` with message
    `"Remote file no found: /.a3s/sync"` (WP07 text).
  - A task awaiting `cancel.cancelled()` and then returning `Err(Cancelled)`: `cancel_task(id)` →
    `true`, outcome `Cancelled` within 1 s; a second `cancel_task(id)` → `false`.
  - A panicking task → `Panicked("boom")`; a task spawned afterwards completes normally.
  - Exclusive keys: a second `spawn_task` with an equal key → `TaskBusy`, text
    `"Checking repositories is already running."` (for `CheckRepositories`); a different repository
    in the key is accepted; a non-exclusive spawn with an equal key is accepted.
  - `cancel_repository_tasks("R")` cancels exactly the tasks keyed with `Some("R")`.
  - Ids increase from 1.
- A4 (`tests/events.rs`) Coalescing and repaint. Covers B7, B9, B12.
