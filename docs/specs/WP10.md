## Scope

- `unzip`: the single-entry extraction of downloaded `<leaf>.zip` files (`.pbo.zip`, `.ebo.zip`, any
  compressed leaf), hardened (fixed target, `.part` + rename, size cap, no links, SHA-1 check), and
  `UnzipPool`, the asynchronous unzip pool that implements WP09's `ZipSink`. Also
  `extract_to_folder` (zip-slip-safe multi-entry extraction, port of `FileAccessMethods.extractToFolder`).
- `cleanup`: deletion of the plan's `DeleteTask`s without following links and with a
  destination-root re-check; `copy_directory` (port of `FileAccessMethods.copyDirectory`).
- `report`: the download report text (`FilesSynchronizationReportManager`), character-identical to
  Java except for the date format.
- `pipeline`: `SyncSession` (check → selection → download+unzip+cleanup, resumable within a
  session), the userconfig copy (`UserconfigUpdater`), and `sync_repository` (the headless
  auto-update / CLI flow: check → select all → download → userconfig → re-check → revision).
- Persistence of the revision, the merged repository/configuration changes and the SHA-1 cache
  through an injected `SyncStore` trait (WP04/WP14 adapters live with their callers).
- Emits `Finished(Outcome)` for every download run except after `ConnectionLost` (WP09 Q7).

## Behaviour contract

Terms: **session** = one `SyncSession` (Java: one `FilesSynchronizationManager` + its DTO tree);
**run** = one `SyncSession::download` call (Java: one `FilesSynchronizationProcessor.run`).

### Unzip of one file (`unzip::unzip_file`)

- B1. **Input** is a WP09 `DownloadedZip { relative_path, zip_path, target_path, sha1, size }`.
  The only output path is `target_path`; the zip's entry names are **ignored entirely** (Java
  reads the first entry's bytes and never looks at its name, `dao/zip/ZipDAO.java:35-36, 58-66`).
  Log `tracing::info!("Uncompressing file: {abs zip_path}")` (`:31`).
- B2. **Pre-checks** (thrown before Java's try, so not wrapped, `:44-48`):
  - zip missing → `UnzipError::NotFound`, message `"File not found on disk: {abs zip_path}"`
    (kind `NotFound`);
  - the zip file name's extension (from the last `.`) is not `.zip` → `UnzipError::BadExtension`,
    message `"Can not unzip file - bad file extension"` (kind `InvalidInput`). Every name ending in
    `.zip` is accepted: `.pbo.zip`, `.ebo.zip`, anything (amendment 2026-10-10; Java only *handed*
    `.pbo.zip` to the pool, `service/connection/ConnectionDownloadProcessor.java:98-104`).
  - `target_path` must be `zip_path` without its trailing `.zip` (WP09 always builds it so);
    otherwise `UnzipError::UnsafeTarget` (kind `InvalidData`), nothing written (defense in depth).
- B3. **Archive** (`:58-66`): open with `zip::ZipArchive`, take entry index 0 only. Further entries
  are ignored (Java parity), logged at debug. Rejected, as `UnzipError::Archive` (B6 message):
  - no entry at all (Java writes an empty target; Rust: error unless `size == 0` and
    `sha1 == Some("0")`, in which case an empty target is written — same result as Java for an
    empty file);
  - entry 0 is a directory (`ZipFile::is_dir`);
  - entry 0 is a symbolic link: `ZipFile::is_symlink()` or `unix_mode() & 0o170000 == 0o120000`
    (S_IFLNK). A link is **never** created; the entry is not read as data either (D-16 input);
  - an unsupported compression method or a corrupt stream (zip crate error).
- B4. **Write** to `"{target_path}.part"` (append `.part` to the file name, `OsString`
  concatenation; WP08's extra-file scan never lists names containing `.part`). Create/truncate it,
  copy the entry's decompressed bytes in chunks of ≤ 64 KiB, feeding a SHA-1 hasher.
  - **Size cap (zip bomb)**: read at most `size + 1` bytes (`Read::take`). More than `size`
    bytes → error `"…\nUncompressed size exceeds the expected size of {size} bytes"`; fewer →
    `"…\nUncompressed size {actual} differs from the expected size of {size} bytes"`.
  - **Integrity**: the SHA-1 (lowercase hex, `"0"` for an empty file, `a3s_hash` convention) must
    equal `sha1` when `sha1` is `Some`; otherwise `"…\nSHA-1 mismatch: expected {sha1}, got {actual}"`.
    Java checks neither (DV-U2).
  - Then `fsync`, rename `.part` → `target_path` (replacing an existing file). The old target stays
    untouched until the rename (Java deletes it before extracting, `:50-52`; DV-U1).
- B5. **Success**: delete the zip (Java `finally`, `:96-98`); return `UnzipStats { bytes }`.
- B6. **Failure** (not cancelled): delete the `.part` and the zip (`:77`, `:96-98`), keep the old
  target. Message `"Failed to unzip file: {abs zip_path}\n{detail}"` (`:78-84`; Java appends
  `"\n" + e.getMessage()` only when non-null — Rust always has a detail). Kind: `InvalidData` for
  archive/size/SHA-1 errors, `ErrorKind::from_io` for I/O errors.
- B7. **Cancel** (`:64`, `:93-95`, `:191-193`): the flag is polled between chunks (so ≤ 64 KiB of
  work after it is set). Delete the `.part`, **keep the zip** (Java keeps it and deletes the
  partial target), return `UnzipError::Cancelled` (never reported as an error).

### Unzip pool (`unzip::UnzipPool`, implements WP09 `ZipSink`)

- B8. **Workers** (`dao/zip/UnZipFlowProcessor.java:24-29, 60-87`): at most
  `N = available_parallelism()` (≥ 1) extractions run at once, on named threads `unzip-{i}`
  (`std::thread::Builder`), created lazily. Zips start in submission order (FIFO, `:93-101`).
- B9. **`submit(zip)`** never blocks (queue push + wake) (`:31-35`). After `cancel()` submissions
  are ignored.
- B10. **`is_idle()`** = queue empty and no extraction running (`uncompressionIsFinished`,
  `:132-142`). WP09 uses it for the connection-waiting counter.
- B11. **`finish(events) -> UnzipSummary`** (async, called once after the download): if not idle,
  emit `Phase(Uncompressing)` (`ConnectionDownloadProcessor.java:176-179` →
  `UnZipFlowProcessor.java:37-50` → `AddonsDownloader.java:179-193`), then
  `Progress { phase: Uncompressing, percent }` from a `PercentCounter` whose total is
  `queued + running` at that moment (`:39-46`) and which increments once per extraction finished
  afterwards (`:76-78, 108-112`). Waits until idle; returns the errors in completion order and the
  number of files extracted. If the pool was idle, no phase/progress event is emitted.
- B12. **`cancel()`** (`:52-58`): sets the flag of every running extraction (B7), drops the queue
  (queued zips stay on disk), and returns without waiting; a later `finish` returns within 1 s.
  Dropping the pool cancels it and joins nothing on the async thread.
- B13. Errors are collected (never abort the pool), each as an `EventError { kind, message (B6),
  relative_path: Some(zip.relative_path) }` (`:73-75, 114-116`).

### `extract_to_folder` (`dao/FileAccessMethods.java:109-161`)

- B14. `extract_to_folder(zip: &Path, folder: &Path) -> Result<(), ExtractError>`: canonicalize
  `folder` (create it with `create_dir_all` first if missing: `"Unable to create extraction folder: {folder}"`;
  not a directory: `"Extraction target is not a directory: {folder}"`, `:111-117`). For each entry
  in archive order:
  - empty name → `"ZIP entry has no name."` (`:150-152`);
  - the resolved path `folder.join(name)`, normalized lexically and then checked component-wise,
    must equal the root or be below it; otherwise `"Unsafe ZIP entry: {name}"` (`:153-159`).
    Absolute names, `..` escapes and (Rust addition) any `..` component, drive prefixes and `\`
    separators are rejected; `ZipFile::enclosed_name()` returning `None` is unsafe;
  - symlink entries (B3 test) → `"Unsafe ZIP entry: {name}"`, never created;
  - directory entry → `create_dir_all` (`"Unable to create extracted directory: {path}"`, `:124-129`);
  - file → create parents (`"Unable to create extracted file parent: {parent}"`, `:131-134`), write;
    on write error delete the partial file and fail (`:141-144`). Existing files are overwritten.
  - Nothing is ever written outside `folder` (check before any write of that entry).
  No caller in the Java client today (the updater has its own, WP31); kept as a library helper.

### Deleting extra local files (`cleanup::delete_extra_files`)

- B15. **Input**: the session's selected `DeleteTask`s (WP08 `PlanSummary::delete_tasks`, pre-order:
  a folder before its content, `FilesSynchronizationManager.java:46-90`), `DeleteRoots`, a set of
  protected paths, the hidden folder paths, the cancel token. Emit `Phase(DeletingExtraFiles)`
  once before the first task when the list is non-empty (Rust-only label, WP07 B37). Java deletes
  synchronously before downloading (`FilesSynchronizationProcessor.java:186`,
  `service/ConnectionService.java:513-531`).
- B16. **Root re-check** (amendment 2026-10-11; Java has none). `DeleteRoots::from_plan(tree,
  destination)` = `{ absolute(destination) }` ∪ `{ d.local_path() }` for every directory `d` of the
  plan whose `destination_path` was redirected by auto-discover (i.e. `absolute(d.destination_path)
  != absolute(parent local path)`, the parent of a root child being `destination`). A task is
  deleted only if **all** hold, else it is skipped as `Refused` with `tracing::warn!`:
  - every segment of `relative_path` passes `plan::is_safe_name`;
  - `local_path` is absolute and contains no `CurDir`/`ParentDir`/`Prefix`-after-start components;
  - `local_path` starts with (component-wise `Path::starts_with`) one of the roots and is
    **strictly** longer than that root (a root itself is never deleted);
  - `relative_path` is not under a hidden folder (`plan::is_hidden_path`), defense in depth;
  - `local_path` is not in the protected set (B21).
  The check is lexical (consistent with D-16: user-created symlinks *above* the final component,
  e.g. an `@mod` folder linked to another disk, are honoured; see Q2).
- B17. **No link following** (D-15/D-16, amendment 2026-10-11). Inspect `local_path` with
  `symlink_metadata` (never `metadata`):
  - missing → `Skipped` (Java `file.exists()` false, `:523`). This is normal for the content of a
    folder already deleted earlier in the list;
  - a symbolic link (any target, dangling included) → remove **the link only**: on Unix
    `remove_file`; on Windows `remove_dir` when `FileTypeExt::is_symlink_dir()` (directory symlinks
    and junctions), else `remove_file`. WP08 lists a symlinked folder as a single **file** node,
    so `is_directory` is false for it; the on-disk type decides, not `is_directory`;
  - a regular file → `remove_file` (`FileAccessMethods.deleteFile`, `:74-80`);
  - a real directory → `std::fs::remove_dir_all` (it removes nested links without following them;
    Java's `deleteDirectory` follows them, `:47-62`, and can delete outside the destination).
  The on-disk type wins over `DeleteTask::is_directory` (Java checks `isFile()`/`isDirectory()` on
  disk too, `:524-528`).
- B18. **Failures** are not errors of the sync (Java ignores `File.delete()` results, `:74-80`):
  each is logged `tracing::warn!("Failed to delete {path}: {err}")` and listed in
  `CleanupReport::failed`. `CleanupReport { deleted, skipped, refused, failed: Vec<(PathBuf, io::Error kind + message)> }`.
- B19. Cancellation is checked between tasks; a cancelled cleanup returns what it did so far.
- B20. Blocking: the pipeline runs it in `spawn_blocking`.
- B21. **Protected paths** (Rust addition): for every file `DownloadTask` of the session, its
  `local_path() + ".zip"`, `+ ".part"`, `+ ".zip.part"`. Reason: a stale `x.ebo.zip` is an extra
  file for WP08 (only `.pbo.zip` names are filtered), while the same path may be the zip a paused
  run downloaded and that this run re-unzips (B27). Protected paths are reported as `skipped`.

### Copying a directory (`cleanup::copy_directory`, `dao/FileAccessMethods.java:26-45`)

- B22. `copy_directory(source, target) -> io::Result<CopyStats>`: if `source` is a directory,
  create `target` with `create_dir` if missing (Java `mkdir`, not `mkdirs`), then recurse over its
  entries (any order); otherwise copy the file content to `target` (create/truncate). Extra files in
  `target` are kept; mtimes are not preserved (Java parity). Symbolic links in `source` are
  **skipped** with `tracing::warn!` (Java follows them; DV-C2). A missing `source` is an
  `io::ErrorKind::NotFound` error. Errors abort the copy at the first failure (Java throws).

### Download report (`report`, `FilesSynchronizationReportManager.java`)

- B23. `success_report(r: &ReportInput) -> String` (`:37-107`), exactly (lines joined with `\n`,
  no trailing newline):

  ```text
  --- Download report ---
  Repository name: {repository_name}
  Repository url: {repository_url}
  Download finished on: {finished_on}

  Download finished successfully.

  Server connection:
  - Average download speed: {avg}
  - Number of active connections used: {max_active_connections}

  Global file transfer:
  - Number of files updated: {files_updated}
  - Total files size on disk: {size(disk)}
  - Downloaded data: {size(resumed)}
  - Saved: {size(disk - resumed)} ({pct(disk, resumed)}%)

  Partial file transfer:
  - Number of files updated: {incomplete_files}
  - Total files size on disk: {size(incomplete_disk_size)}
  - Downloaded data: {size(incomplete_expected_size)}
  - Saved: {size(incomplete_disk_size - incomplete_expected_size)} ({pct(..)}%)

  Compressed file transfer:
  - Number of files updated: {compressed_files}
  - Total files size on disk: {size(uncompressed_files_size)}
  - Downloaded data: {size(compressed_files_size)}
  - Saved: {size(uncompressed_files_size - compressed_files_size)} ({pct(..)}%)
  ```

  - `repository_url` = `a3s_types::local::protocol::host_url(protocol)`
    (`service/RepositoryService.java:192-201`).
  - `finished_on` = `a3s_format::datetime_medium(&chrono::Local::now())` (Java: localized MEDIUM,
    `:18-19, 138-140`; WP02 fixed en-US format). The pure function takes it as a parameter.
  - `avg` = `"unavailable"` if the session's average speed is 0, else `a3s_format::speed(avg)`
    (`:45-48`).
  - `files_updated` = number of `download_tasks` **including folders** (Java
    `getListFilesToUpdate().size()`, `:63-64`; quirk kept).
  - `disk`, `incomplete_*`, `compressed_*`, `uncompressed_*` = WP08 `ReportTotals::compute(tasks)`
    (`FilesSynchronizationManager.java:105-134`). `resumed` = WP08 `resumed_size(tasks)` at report
    time (download size of `Done` files, `:183-196`).
  - `size(x)` = `a3s_format::size(x as i64)`; differences are computed in `i64` (a negative value
    prints as Java does, e.g. `-5.0 B`).

- B24. `error_report(r: &ReportInput, message: &str, errors: &[EventError]) -> String`

- B25. Which report a run stores (`FilesSynchronizationProcessor.java:314-332`):
  `Success` → `success_report`; `CompletedWithErrors`/`TooManyErrors`/`Failed` → `error_report`

### Download run (`SyncSession::download`, `FilesSynchronizationProcessor.run`)

- B26. **Destination check first** (`:162-170`): `options.destination` empty →
  `SyncOptionsError::DestinationEmpty`, missing → `DestinationMissing`; either ends the run with
  `Finished(Failed{..})` and an error report (Java `executeError("Download finished with error")`,
  `:196-202`). No network, no deletion.
- B27. **Order** of one run (`:181-194`, `service/ConnectionService.java:497-511`):
  1. Create a fresh `UnzipPool` (Java: one per `ConnectionService`, `:54`).
  2. Re-unzip already downloaded zips: for every task in WP08 `downloaded_compressed(tasks)` whose
     `complete == 0.0` (Rust addition: a zsync-patched leaf is never overwritten by a stale zip)
     and whose `local_path() + ".zip"` exists, `submit` a `DownloadedZip` built from the task.
  3. Delete extra files (B15–B21) in `spawn_blocking`.
  4. WP09 `download(&request, &mut tasks, pool.clone(), &cancel, &events)` with
     `DownloadRequest::new(protocol, transport_options, &options, server_info)`. WP09 emits
     `Phase(Downloading)`, `TransferTotal`, progress, `FileStarted/Done/Failed`, `ConnectionLost`.
  5. `download::apply_statuses(&mut tree, &tasks)` (WP09 B38), so a later
     `PlanSummary::compute` keeps the statuses.
  6. Session accumulators (`:263-270, 294-297`): `average_speed = if prev == 0 { run } else if run == 0 { prev } else { (prev + run) / 2 }`;
     `max_active_connections = max(prev, run)`.
- B28. **End of run** by `DownloadReport::end` (`ConnectionDownloadProcessor.java:139-192`,
  `AddonsDownloader.java:286-415`):
  - `Completed` → `pool.finish(events)` (B11), then `outcome = report.outcome(unzip_errors)`
    (WP09: download errors first, then unzip errors). Java sends `end` only when both lists are
    empty (`ConnectionDownloadProcessor.java:165-175`).
  - `TooManyErrors`, `Failed` → `pool.cancel()` (the Java UI cancels the processor on every end
    callback, `AddonsDownloader.java:312-336, 413-415`), `outcome = report.outcome(vec![])`.
  - `Cancelled` → `pool.cancel()`, outcome `Cancelled`.
  - `ConnectionLost` → `pool.cancel()`, **no** `Finished` (WP09 Q7: `ConnectionLost` is
    terminal), no report; the session stays resumable (B30).
  Then store the report (B25) in the session and emit `Finished(outcome)` as the **last** event of
  the run. Return `RunReport { outcome: RunEnd, report_text, download: DownloadReport,
  unzip: UnzipSummary, cleanup: CleanupReport }`.
- B29. Every `EventError` carries `relative_path`. A run never panics on bad input.
- B30. **Pause / resume / retry** (`AddonsDownloader.java:389-401`, `DownloadPanel.java:1082-1100`,
  `console/CommandGeneral.java:318-329`): pause = cancel the token. The session keeps the tree with
  `Running`/`Done` statuses (WP09 B9 resumes `Running` files), the delete list and the
  accumulators. A later `download` call with a fresh token resumes: `Done` tasks are skipped and
  counted as transferred (WP09 B1), their zips re-unzipped (B27.2). Deletions are re-run (already
  deleted paths are `skipped`).
- B31. **Selection**: `SyncSession::tree_mut()` gives the UI the plan tree; `refresh_summary()`
  recomputes `PlanSummary::compute(&tree)` (statuses survive via B27.5). `select_all()` =
  WP08 `select_all_except_root` + refresh (CLI and auto-update, `AddonsAutoUpdater.java:94-96`,
  `CommandGeneral.java:430-441`).

### Check (`SyncSession::check`, `FilesCheckProcessor` + `AddonsChecker`)

- B32. Order (`service/synchronization/FilesCheckProcessor.java:37-67`,
  `ui/repository/workers/AddonsChecker.java:93-108`), all with one `TransferCtx` on the caller's
  token:
  1. `remote::check_repository(name, protocol, transport_options, &mut metadata, ctx, events)`
     (WP07; emits `Phase(CheckingRepository)`).
  2. `metadata.require_for_sync(event_name)` (`:43-54`).
  3. `store.update(name, |repository, configuration| …)`: WP07 `status::update_repository`
     (hidden folders, client connections, favorite servers), then
     `SyncOptions::from_repository(repository, event_name)` (may rewrite download locations);
     persist what changed (`StoreChanges`). Java writes the repository at `:67` and the
     configuration on exit; Rust persists both immediately (DV-P1).
  4. `store.read_sync_cache(name)`; `spawn_blocking(plan_repository(&metadata, &options,
     addons, &mut cache, &cancel, &events))` (WP08; emits `Phase(CheckingFiles)` and SHA-1
     `Progress`); `store.write_sync_cache(name, &cache)` (Java `write`, `:67`).
  5. `completion::determine_completion(&mut tree, protocol, transport_options, server_info, ctx, events)`
     (WP08; emits `Phase(DeterminingCompletion)`).
  6. Build the session: tree, `PlanSummary::compute` (nothing selected yet), fresh accumulators.
- B33. `check` emits no `Finished` (WP07 B42). Errors: `CheckError::{Remote, Options, Plan,
  Completion, Store, Cancelled}`; `UserFacing` messages are the inner Java messages. A cancel at

### Java quirks that may be dropped (local-only; need approval)

- DV-U1. Unzip writes `<target>.part` and renames; the old target survives failures and cancels.
  Java deletes the target first and leaves a partial target on error (`ZipDAO.java:50-52, 74-86`).
- DV-U2. Unzip verifies the uncompressed size (cap = expected size, zip-bomb guard) and SHA-1,
  rejects symlink and directory entries, and requires `target == zip minus ".zip"`. Java writes
  whatever the first entry inflates to.
- DV-U3. Every compressed leaf is unzipped, `.ebo.zip` included (amendment 2026-10-10, WP09 DV9).
- DV-U4. Already-downloaded zips of zsync-patched leaves (`complete > 0`) are not re-unzipped.
- DV-U5. Deterministic outcome message: Java says `"Download finished with error"` (singular) when
  unzip was still running at the end of the download and `"…with errors"` otherwise
  (`UnZipFlowProcessor.java:118-130` vs `ConnectionDownloadProcessor.java:165-175`); Rust always
  uses WP09's `outcome()` mapping (`CompletedWithErrors` → `"…with errors"`).
- DV-D1. Deletions never follow links and are re-checked against the destination roots (B16,
  B17); a symlinked folder is removed as a link (Windows: `remove_dir`). Java's
  `deleteDirectory` recurses through links (`FileAccessMethods.java:47-62`).
- DV-D2. Protected zip/part paths are never deleted (B21).
- DV-C1. Silent userconfig update with a missing source does nothing (Java creates an empty target
  folder and swallows the error, `UserconfigUpdater.java:87-118`).
- DV-C2. `copy_directory` skips symbolic links (Java follows them).
- DV-R1. Error reports have no Java stack traces (B24).
- DV-P1. Repository and configuration changes of a check are persisted immediately; SHA-1 cache
  in its own store (WP04).
- DV-P2. `mark_failed` persists revision −1 at once (Java `resetRepositoryRevision` only changes
  memory, `RepositoryService.java:746-752`).
- DV-P3. A cancelled sync does not touch the revision (Java's panel re-checks after cancel and
  marks the repository `OK` with the server revision, `DownloadPanel.java:1117-1125, 970-976`).
- DV-P4. `sync_repository` always maintains the revision; the Java CLI never does
  (`CommandGeneral.java:281-316`). WP19 may ignore it (Q3).

### Errors, cancellation, progress

- Retries: only WP09's (inside a run) and B41 (whole run after connection lost).
- Collected, non-fatal: download file errors (WP09), unzip errors (B13), delete failures (B18,
  not in the outcome), userconfig outcome (B37, not in the outcome).
- Fatal for a run: destination check (B26), WP09 `Failed`/`TooManyErrors`/`ConnectionLost`.
- Cancel: `download` returns within 1 s of `cancel.cancel()` (WP09 ≤ 1 s + unzip ≤ 64 KiB per
  worker + no waiting on cancelled unzip threads). `check` returns within 1 s (WP07/WP08 guarantees).
- Events emitted by WP10 itself: `Phase(DeletingExtraFiles)`, `Phase(Uncompressing)`,
  `Progress{Uncompressing}`, `Phase(UpdatingUserconfig)`, `Finished(Outcome)`. Everything else
  comes from WP07/WP08/WP09.

### Concurrency

- Java: unzip pool of `availableProcessors()` threads (`UnZipFlowProcessor.java:24-29`), one
  thread per worker class (`AddonsChecker`, `AddonsDownloader`, `AddonsAutoUpdater`).
- Rust: everything is `async` on the caller's tokio runtime; blocking work (`plan_repository`,
  `delete_extra_files`, `copy_userconfig`) in `spawn_blocking`; unzip on ≤ N named std threads.
  `SyncSession` is `Send`; `download`/`check`/`sync_repository` futures are `Send`. No lock held
  across `.await`. `UnzipPool` state behind one `parking_lot::Mutex` + `Condvar`.
- Disk contention: unzip threads write while WP09 downloads (as Java).
