## Scope

- **Repository content check** (admin "Check" button / console `-check`): fetch the remote
  `sync`, `serverinfo`, `changelogs`, `autoconfig` over the download protocol, derive the expected
  remote file list (raw files, `.zip`, `.zsync`), test each with `Transport::exists` on up to 4
  parallel connections, and report missing files with Java's texts and progress.
- **Upload pipeline**: read the five local `.a3s` files, fetch the remote `.a3s/sync` over the
  upload protocol, plan check / upload / delete sets (`FilesUploadManager`), re-upload files that
  the check finds missing, upload files (sequential, or ≤ 10 parallel FTP/SFTP connections),
  upload the metadata (with `compressedPboFilesOnly` set from the upload settings), then delete
  extra remote files. Progress, speed, remaining time, connection-lost and resume state.
- **Java round trip of metadata**: Java uploads metadata by deserialising the local files and
  serialising the objects again. Reproduce that transformation so uploaded `.a3s/*` bytes equal
  Java's (HashMap/HashSet capacities change, current class descriptors are used).
- **Events editing** (`RepositoryService` events CRUD): an `EventsDoc` that models Java's
  in-memory `Events` object graph (string/Boolean instance identity, `HashMap` state) so that
  add / rename / duplicate / remove / save, local write (`.a3s/events`) and events-only upload
  produce the bytes Java would write.
- Admin-connect metadata fetch (`ProgressConnectionAsAdminDialog`): sync, serverinfo, changelogs,
  events (raw, for the `EventsDoc`), no autoconfig.

## Behaviour contract

Abbreviations: `CS` = `service/ConnectionService.java`, `RS` = `service/RepositoryService.java`,
`RUP` = `service/administration/RepositoryUploadProcessor.java`, `CUP` =
`service/connection/ConnectionUploadProcessor.java`, `CCP` =
`service/connection/ConnectionCheckProcessor.java`, `ACP` =
`service/connection/AbstractConnectionProcessor.java`, `FUM` =
`service/administration/FilesUploadManager.java`, `ACD` = `dao/connection/AbstractConnexionDAO.java`.

### Common: expected remote files (`check/expected.rs`)

- B1. `expected_remote_files(nodes, compressed_pbo_files_only, with_zsync)` mirrors `ACP.extract`
  (`ACP:33-79`). For each node, in input order, with `parent` = the node's parent relative path
  and `name` its name:
  - directory → one `RemoteFile(name, parent, is_directory = true)` (`ACP:71-76`);
  - leaf with `compressed == true` and `compressed_pbo_files_only` → only `name + ".zip"`
    (`ACP:44-47`);
  - leaf with `compressed == true`, not only-zip → `name`, `name + ".zip"`, then
    `name + ".zsync"` if `with_zsync` (`ACP:48-59`);
  - leaf not compressed → `name`, then `name + ".zsync"` if `with_zsync` (`ACP:61-70`).
  Extensions are `DataAccessConstants.ZIP_EXTENSION = ".zip"` and `ZSYNC_EXTENSION = ".zsync"`
  (`dao/DataAccessConstants.java:21,23`; `a3s_repo_files::layout::{ZIP_EXTENSION,
  ZSYNC_EXTENSION}`). Cancellation is checked before each node (`ACP:36-37`). Use WP07's
  `a3s_sync::RemoteFile` (its `relative_file_path()` has the leading `/` used in messages,
  `transport_path()` is passed to the transport).
- B2. `with_zsync` is always derived from the **download** protocol: `repository.protocol` is a
  Java `Http` instance, i.e. `ProtocolType::is_http()` (HTTP or HTTPS, not WebDAV)
  (`CS:371, 421, 441`, `CUP:43`; WP11 B37).
- B3. Node order. Java iterates DTO deep-search lists (admin check, pre-order,
  `dto/sync/SyncTreeNodeDTOMethods.java:50-64`) and `HashMap` key sets (upload, `FUM:36, 46, 77`).
  Rust uses one deterministic **plan order** everywhere: pre-order over the stored child lists
  (`SyncTreeDirectory::walk`), root excluded. Order is not wire-visible (local-only, Q5).
- B4. Relative paths are computed from the tree structure (`a`, `a/b`, `a/b/c.pbo`). Java's DTO
  paths stop at the first ancestor **named** `racine` (`SyncTreeNodeDTOMethods.java:11-41`) and
  `syncToMap` skips every directory named `racine` (`FUM:90`), so a nested folder called `racine`
  makes Java upload files to the wrong remote path. Rust does not reproduce this (Q7, needs a user
  decision because it changes the remote layout in that edge case).

### Repository content check (`check/`)

- B5. Inputs: the local `Repository` (WP03): `name`, `protocol` (download protocol),
  `repository_check_connections()` (`min(raw, 4)` if `raw > 0`, else 4; `Repository.java:385-390`,
  re-applied at `RepositoryCheckProcessor.java:38-41`), plus caller `TransportOptions` for that
  protocol.
- B6. Connect one `RemoteConnection` (WP07) to `repository.protocol`. `SOCKS`/`A3S` → WP07's
  `InvalidProtocol` mapping (Java `"Unknown or unsupported protocol."`, `CS:85-86`). Log
  `"Checking repository content: {name} on url: {host_url}"` (`CS:356-358`, `tracing::info!`).
- B7. Fetch, in this order, with WP07 `fetch_a3s`: `sync`, `serverinfo`, `changelogs`,
  `autoconfig` (`RepositoryCheckProcessor.java:43-46`; **not** events). The first error aborts the
  check and is returned unchanged (`RemoteError`, Java's message texts come from WP07 B13)
  (`:78-82`). Each fetched file is kept in the report's `RemoteMetadata` (Java stores them on the
  repository in `finally`, `CS:100-106` etc.).
- B8. After the four fetches, Java throws `RemoteSyncFileNotFoundException`,
  `RemoteServerInfoFileNotFoundException`, `RemoteChangelogsFileNotFoundException`,
  `RemoteAutoconfigFileNotFoundException` in that order when a value is null
  (`RepositoryCheckProcessor.java:48-62`). In Rust `fetch_a3s` never yields "absent without an
  error", so these map to `RemoteError::MissingMetadata(file)` only if a fetch helper returns
  `None`; keep the order in code.
- B9. Expected files: B1 over the **remote** sync tree's nodes (plan order), with
  `compressed_pbo_files_only = remote server_info.compressed_pbo_files_only` (`CS:368`) and
  `with_zsync` per B2 (`CS:370-371`). Remove every directory entry (`CCP:67`). An empty list
  returns immediately with `checked = 0` (`CCP:77-79`).
- B10. Workers: `k = min(repository_check_connections(), files.len())` (`CCP:81`). Worker 0 reuses
  the metadata connection; workers 1..k connect lazily to the same protocol. Each worker takes the
  next index from a shared counter until the list is exhausted, the context is cancelled or a
  first error was recorded (`CCP:104-111`). For each file: `Transport::exists(transport_path)`.
- B11. Missing file (`exists == false`): record it, emit
  `SyncEvent::FileFailed { relative_path, error }` with `EventError { kind: NotFound, message:
  "File not found on repository: " + relative_file_path() }` (`CCP:114-121`). The number of
  `FileFailed` events is Java's error count (`observerCountErrors`,
  `RepositoryCheckProcessor.java:66-72`).
- B12. Progress after every checked file (found or missing): `count += 1`, `value = count * 100 /
  total` (integer), emitted as `SyncEvent::Progress { phase: Phase::CheckingRemoteFiles, percent }`
  only when it differs from the last emitted value (`CCP:142-149`; WP07 `PercentCounter`).
  `Phase(CheckingRemoteFiles)` (label `"Checking remote files..."`,
  `ui/repository/workers/RepositoryChecker.java:87`) is emitted once before the first `exists`.
- B13. An `exists` error (anything but `Ok(bool)`) aborts the check: the first error wins, all
  workers stop (cancel a child token, `CCP:124-130, 136-140`), the error is returned as
  `CheckError::Exists { relative_path, source }` (`CCP:97-100`). Errors after cancellation are
  ignored (`CCP:125`).
- B14. Result: `ContentCheckReport { metadata, checked, missing }` with `missing` sorted in plan
  order (Java order is thread-dependent). `is_synchronized() == missing.is_empty()`. Emit
  `Finished(Outcome::Success)` when nothing is missing, else
  `Finished(Outcome::CompletedWithErrors { errors })` (one `EventError` per missing file)
  (`RepositoryCheckProcessor.java:74-76`). Console texts (WP19 uses them):
  `"Repository {name} - repository is synchronized."`, `"Repository {name} - repository is not
  synchronized."` followed by each message, `"Repository check files... complete: {v} %"` for
  strictly increasing values (`console/CommandGeneral.java:171-190`). Provide them as
  `ContentCheckReport::console_lines(name)` and `console_progress_line(v)`.
- B15. Cancellation: return `Err(CheckError::Cancelled)` and emit `Finished(Outcome::Cancelled)`.
  (Java's workers just stop and `run()` reports the partial list, which the UI ignores because it
  set `canceled`, `RepositoryChecker.java:146-169`.)

### Upload pipeline (`upload/`)

Order of operations (`RUP:61-153`, `CS:394-451`, `CUP:64-94`):

- B16. Preconditions, before any network I/O:
  1. `repository.upload_protocol` is `None` → `UploadError::UploadProtocolNotSet`
     (`"Please use the upload options to configure a connection."`, `RUP:72-78`).
  2. `repository.path` is `None` or `""` → `UploadError::PathNotSet` (`"Please set the repository
     main folder location then build the repository."`, `ui/repository/AdminPanel.java:718-725`).
  3. Read the local metadata (B20).
- B17. Connections: `parallel = upload_protocol.protocol_type ∈ {Ftp, Sftp}` (FTPS and WebDAV are
  sequential, `RUP:81-84`; `UploadRepositoryConnectionDialog.java:160-162`). Connection count
  `n = parallel ? repository.parallel_upload_connections() : 1` (`min(raw,10)` or 4,
  `Repository.java:356-360`; `CS:59-64` maps 0 → 1). `Transport::supports_upload() == false`
  (HTTP/HTTPS upload protocol) → `UploadError::Transport` with `Unsupported` before planning.
  Log `"Uploading repository: {name} on url: {host_url(upload_protocol)}"` (`CS:403-406`).
- B18. Connection 0: `RemoteConnection::connect(upload_protocol)`; fetch `.a3s/sync` with
  `fetch_a3s::<SyncTreeDirectory>`. A `NotFound` error means "no remote repository yet":
  `remote = None` (`RUP:118-124`, `CS:378-392`). Any other error aborts.
- B19. Plan (B21-B24), then open `upload_session()` on connection 0 for the rest of the pipeline;
  it ends (guard dropped) on every exit path (`CS:413-414, 447-450`).
- B20. Local metadata (`RS:1394-1419`, `dao/repository/RepositoryDAO.java:242-288`): read
  `<path>/.a3s/{sync, serverinfo, changelogs, autoconfig, events}` in that order as raw graphs
  (WP11 `RawGraph`) with `Limits::JAVA_A3S` and the class allow-list of
  `dao/A3SFilesAccessor.java:116-141`. The first failure aborts with
  `UploadError::ReadLocal { file, path, source }`, displayed as `"Failed to read file:
  {name}\n{detail}"` (+ `"\nThe file seems to be corrupted."` for gzip/EOF errors,
  `A3SFilesAccessor.java:65-74`). A missing file is an error (Java's `FileInputStream` throws;
  the `events != null` guard at `CUP:223` is therefore dead). The typed `SyncTreeDirectory` for
  planning is decoded from the same graph.

### Planning (`upload/plan.rs`, `FUM`)

- B21. `plan_upload(local, remote)` returns three node lists (relative path + node kind + the
  node's flags), in plan order (B3). Root excluded (`FUM:90`).
- B22. `remote == None` → every local node goes to `to_upload` (`FUM:35-41`).
- B23. Otherwise, for each local node at path `p`: if the remote tree has a node at `p` (exact,
  case-sensitive) and (both are leaves with equal `sha1`, or both are directories) → `to_check`;
  else → `to_upload` (`FUM:43-75`; the name comparison at `:54` is implied by equal paths). A
  `None` sha1 on either side counts as "different" (Java would throw an NPE at `:58`; race only).
  The `compressed` flag is not compared; a changed compression state is caught by the check
  (B26) because the expected file set differs.
- B24. Every remote node whose path is absent from the local tree → `to_delete` (`FUM:77-83`),
  carrying the **remote** leaf's `compressed` flag. Rust drops entries whose ancestor directory is
  itself in `to_delete` (one recursive delete removes them; Java issues redundant deletes that hit
  "missing → Ok") (Q11).

### Check phase

- B25. Emit `Phase(CheckingRemoteFiles)` (`CS:418`). Expected files = B1 over `to_check` with
  `compressed_pbo_files_only = repository.upload_compressed_pbo_files_only` (`CS:420-422`) and
  `with_zsync` per B2; directories removed. Run on connection 0 **only**, sequentially, inside the
  session (`CS:420`: single-connection constructor). Progress / missing / first-error semantics as
  B11-B13, except that missing files are **not** errors: they are collected into
  `missing` (`CS:425`). An `exists` error aborts the upload.
- B26. Consequence (keep): files present on the server with stale content but the same name are
  not detected; only existence is checked (`ACD:362-391`).

### Upload phase

- B27. Emit `Phase(Uploading)` (`CS:429`). Upload list = B1 over `to_upload` (with
  `compressed_pbo_files_only = repository.upload_compressed_pbo_files_only`, `with_zsync` per B2,
  directories kept) followed by the `missing` files from B25 (`CUP:65-66`).
- B28. Resume (Q4): entries already recorded as uploaded in the caller's `UploadResume` are skipped
  when the resume state is valid (B44). Java's index slice (`CUP:68-78`) is not reproduced.
- B29. Local file of an entry = `Path::new(repository.path).join(transport_path)` (Java
  concatenates `path + "/rel"`, `CUP:110-112`). Before any transfer, every non-directory entry's
  local file must exist; the first missing one aborts with `UploadError::LocalFileMissing`
  (`"File not found: {absolute path}"`, `CUP:96-108`). `total` = sum of their lengths;
  emit `TransferTotal { bytes: total, files: number of non-directory entries }` (`CUP:80-81`).
  Metadata bytes are not part of `total` (`CUP:95-107`).
- B30. Sequential mode (`n == 1`, `CUP:114-123`): for each entry in order, check cancellation,
  emit `FileStarted { relative_path }` (Java text `"Uploading file: " + relative path`, `CUP:120`),
  then directory → `mkdirs`, file → `upload_file` (creates parents, WP06 B4).
- B31. Parallel mode (`n > 1`, `CUP:125-195`):
  1. Directories first, sequentially on connection 0, each `mkdirs` preceded by
     `FileStarted` (Java text `"Creating directory: …"`, `CUP:128-140`).
  2. If no file entries remain, or cancelled → done (`CUP:142-144`).
  3. Connect `w = min(n, files.len())` transports in total (connection 0 + `w-1` new ones, each
     with its own `upload_session()`; Java opens sessions for all `n-1` extra DAOs,
     `CUP:151-155`), all on the upload protocol.
  4. Distribute files over the workers. Java assigns statically, `files[i]` to worker
     `i % n` (`CUP:197-206`). Rust uses a shared work queue in list order (Q5).
  5. The first failure (by time) cancels every worker and is returned (Java waits for earlier
     workers to finish their whole share before cancelling, `CUP:171-186`; Q5). Non-I/O
     failures are wrapped as `"Parallel repository upload failed."` (`CUP:184`).
- B32. A file counts as uploaded only after `upload_file` returned `Ok`; then emit
  `FileDone { relative_path }`, record it in `UploadResume` (B44) and emit
  `LastIndexTransferred { index: resume.completed() }`. Java increments the resume index and
  progress in a `finally` block even when the upload failed or was cancelled (`ACD:410-421`), so a
  failed file is skipped on resume; Rust does not (Q4).
- B33. After the file phase (also when cancelled), the serverinfo to upload gets
  `compressedPboFilesOnly = repository.upload_compressed_pbo_files_only` (`CUP:89-90`). The local
  `.a3s/serverinfo` file is **not** rewritten (Java changes only the in-memory object).
- B34. If not cancelled, upload the metadata on connection 0, in this order: `sync`,
  `serverinfo`, `changelogs`, `autoconfig`, `events` (`CUP:91-93, 214-227`), each as
  `upload_bytes(roundtrip_bytes, ".a3s/<name>")` (`ACD:424-445`; remote folder `.a3s`,
  `DataAccessConstants.java:38-43`). All five are encoded (B60-B66) **before** the first
  metadata byte is sent; an encoding error aborts with nothing uploaded. Once the first metadata
  upload starts, cancellation is ignored until all five are written (separate `TransferCtx` with a
  fresh token and its own progress counter): Java's metadata `storeFile` does not observe the
  cancel flag (`ftp/FtpDAO.java:575-597`), and a half-written metadata set would leave the
  repository inconsistent (Q8). A transport error still aborts.

### Delete phase

- B35. Emit `Phase(DeletingRemoteFiles)` (`CS:437`). Entries = B1 over `to_delete` with
  `compressed_pbo_files_only = false` (hard-coded, `CS:440-441`) and `with_zsync` per B2. So a
  deleted compressed leaf removes `name`, `name.zip` and `name.zsync` (HTTP), regardless of the
  upload-only-zip setting.
- B36. For each entry, in order: stop if cancelled (`ConnectionDeleteProcessor.java:33-34`);
  `Transport::delete(transport_path, RemoteKind::Directory | File)` (directories recursively;
  missing → `Ok`, `ACD:447-469`, WP06 B8); then emit `Progress { phase: DeletingRemoteFiles,
  percent: count * 100 / total }` after **every** entry (not deduplicated,
  `ConnectionDeleteProcessor.java:42-46`). An error aborts the upload.
- B37. Deletion runs after the metadata upload. (The WP row says "metadata uploaded last"; Java
  uploads metadata after all files but **before** deletions, `CS:432-442`. Keep Java: old
  metadata never references files that are already gone.) When cancelled, the delete loop exits
  immediately.

### End of pipeline, errors, connection lost

- B38. Success: drop the session, `resume.clear()` (Java resets the index to 0 only if not
  cancelled, `RUP:148-150`), emit `Finished(Outcome::Success)`, return `UploadReport`.
- B39. Cancellation: return `Err(UploadError::Cancelled)`, emit `Finished(Outcome::Cancelled)`,
  keep `resume` (Java keeps the index, `RUP:148-150, 244-253`).
- B40. Connection lost: if the failing error's `is_connection_lost()` is true (Java catches
  `SocketTimeoutException | SocketException`, `RUP:157-160`), emit `SyncEvent::ConnectionLost`,
  then `Finished(Outcome::Failed { error })`, and return the error. `resume` is kept. Retrying is
  the caller's choice: Java's UI asks the user and reruns the whole pipeline
  (`ui/repository/AdminPanel.java:765-784`).
- B41. Any other error: emit `Finished(Outcome::Failed { error })` and return it (`RUP:161-167`).
- B42. `UploadReport { checked, missing, uploaded_files, uploaded_bytes, created_directories,
  skipped_by_resume, deleted, metadata_uploaded: bool }`. "A second upload without changes"
  yields `uploaded_files == 0`, `created_directories == 0`, `deleted == 0`,
  `metadata_uploaded == true` (Java always re-uploads the five metadata files).
- B43. Log lines (`tracing::info!`, local-only): `"Upload plan prepared: check={c}, upload={u},
  delete={d}"` (`RUP:135-137`), `"Repository upload finished successfully in {s} s."`
  (`RUP:154-155`, three decimals).

### Resume state (`upload/resume.rs`, Q4)

- B44. `UploadResume` is held by the caller in memory only (Java's `lastIndexFileTransfered` is a
  **transient** field, `domain/repository/Repository.java:73`; it is shared with downloads in
  Java, here it is upload-only). It stores the SHA-1 of the local `.a3s/sync` file bytes it was
  recorded against and a map `transport_path → (local length, local mtime ms)` of entries uploaded
  successfully (directories included). It is valid for a run iff the current local `.a3s/sync`
  digest matches; otherwise it is cleared at the start of the run. An entry is skipped iff it is
  recorded and its local file's length and mtime are unchanged. `completed()` = number of recorded
  entries.

### Progress (`upload/transfer.rs`)

- B45. Each worker gets a `TransferCtx` sharing the cancel token, with its own progress counter
  (WP06 B9: bytes as sent). The aggregate `transferred` = bytes of finished files + bytes of the
  files in flight, capped at `total` (`RUP:339-399`). Emit `Transfer(TransferProgress {
  transferred, total, current_file, current_file_percent, remaining })` at most every 100 ms and
  once after each file. `current_file_percent = sent * 100 / file_len` (0 for empty files,
  `ACD:584-592`). `percent()` gives the aggregate percent; with `total == 0` Java shows 100
  (`RUP:393`).
- B46. `remaining = elapsed_seconds * (total - transferred) / transferred` when
  `transferred > 0` (truncated to whole seconds, `RUP:209-219`), else `None`.
- B47. `Speed { bytes_per_second }` at most every 500 ms (`RUP:227-242`): Rust computes it from the
  aggregate byte delta over the window (Java sums per-connection speeds of the current file,
  measured after 0.25 s, `ACD:755-770`; local-only difference).
- B48. Uploads are never throttled (Java's `SpeedControlListener` is download-only,
  `ACD:792-812`): `ctx.throttle = None`.

### Java round trip of uploaded metadata (`upload/roundtrip.rs`)

Java uploads `repository.getLocalSync()` etc., objects obtained by **deserialising** the local
files (`RS:1407-1411`), and serialises them again with `ObjectOutputStream(GZIPOutputStream)`
(`ftp/FtpDAO.java:584-591`, `sftp/SftpDAO.java:318-321`, `webdav/WebdavDAO.java:335-340`). The
uploaded bytes are therefore "readObject then writeObject" of the local graph, which is **not**
always the identity.

- B60. `java_roundtrip(graph, overrides) -> Graph` re-emits the object graph from the root through
  `a3s_jserial::jdk::Builder` with a memo `old NodeId → new Value`, so every old node is emitted
  once and every further reference becomes a back-reference. Handles are then assigned in the new
  traversal order by `a3s_jserial::write` (as `ObjectOutputStream` does).
- B61. `fr.soe.a3s.*` objects are emitted with the **current** class descriptors from
  `a3s_types::wire` (`sync_tree_directory_desc`, `sync_tree_leaf_desc`, `server_info_desc`,
  `changelogs_desc`, `changelog_desc`, `events_desc`, `event_desc`, `auto_config_desc`,
  `abstract_protocole_desc`/`protocol_class_desc`, `favorite_server_desc`). Field values are copied
  by name; a field missing from the old stream is written as its default (null, 0, false); an old
  field unknown to the current class is dropped (Java's default serialization behaviour). Enum
  constants (`ProtocolType`, `EncryptionMode`) use `Builder::enum_value`.
- B62. JDK values: `String` → a new string node per old string node (`Builder::string`, never
  `interned`); `java.lang.Boolean` → a new Boolean object per old Boolean node (not the canonical
  `Builder::boolean`; deserialised Booleans are distinct objects, `Boolean` has no
  `readResolve`); `java.util.Date` → new `Date` with the same millis; `ArrayList` → same elements
  in order (`writeObject` writes `size` as capacity).
- B63. `java.util.HashMap` → `readObject` model then `writeObject` (WP11 B56): with `n` mappings,
  `n == 0` → table null, threshold 0 → written `buckets 16, threshold 0`; `n > 0` →
  `fc = n as f32 / lf + 1.0`, `cap = fc < 16 ? 16 : tableSizeFor(fc as i32)`,
  `threshold = (cap as f32 * lf) as i32`; entries re-inserted in stream order; written in the
  model's iteration order. (`lf` = the stream's `loadFactor` field clamped to `[0.25, 4.0]`,
  always 0.75 in practice.)
- B64. `java.util.HashSet` → OpenJDK 25 `HashSet.readObject` model then `writeObject`:
  read `capacity` (ignored), `loadFactor lf`, `size n`;
  `c0 = min(n as f32 * min(1.0 / lf, 4.0), 2^30) as i32`; backing map = `new HashMap(c0, lf)` →
  `threshold = tableSizeFor(c0)` (`tableSizeFor(0) == tableSizeFor(1) == 1`), table null; then
  `put` each element in stream order (first put: `resize()` with `oldThr > 0` → `cap = oldThr`,
  `thr = (int)(cap * lf)`; later puts double when `++size > threshold`; doubling below 16 recomputes
  `thr = (int)(newCap * lf)`, from 16 on doubles it). `writeObject` writes block data
  `[capacity(), lf, n]` then the elements in iteration order, where `capacity()` = table length,
  else threshold if > 0, else 16. Reference table (n → written capacity): **0 → 1, 1 → 2, 2 → 4,
  3 → 4, 4 → 8, 5 → 8, 6 → 8, 7..12 → 16, 13 → 32, 24 → 32, 25 → 64**. A freshly built set (WP11,
  `Builder::hash_set_str`) writes 16 for 0..12. Needs JDK-harness confirmation (follow-up, Q3).
- B65. Overrides: the serverinfo root's `compressedPboFilesOnly` field (B33). No other field
  changes.
- B66. Any other class (arrays, `TreeMap`, `LinkedHashMap`, …, allowed by Java's filter but never
  written by Java or Rust builders) → `UploadError::RoundTrip { file, reason }`. Every re-encoded
  stream must pass `a3s_jserial::read_with_limits(_, Limits::JAVA_A3S)` before upload. Gzip like
  `a3s_repo_files::encode_a3s` (mtime 0, OS 255).
- B67. Consequences (wire-visible, to preserve): a Rust- or Java-built `sync`, `changelogs`,
  `autoconfig` round-trips to the identical decompressed stream (no hash collections); `serverinfo`
  differs from the local file in `compressedPboFilesOnly` and in the `hiddenFolderPaths` capacity /
  order (B64); `events` maps built with `putAll` or many entries change capacity (e.g. a
  1-entry `userconfigFolderNames` built by WP11 with `putAll` (2/1) is uploaded as 16/12).

### Events editing (`events/`)

`EventsDoc` mirrors the Java `Events` object held in `Repository.events`. In the admin flow that
object is deserialised from the **remote** `.a3s/events` fetched over the download protocol
(`ui/repository/dialogs/progress/ProgressConnectionAsAdminDialog.java:51-54`), edited in memory
(`RS:979-1186`), then written to the local repository (`RS:1061-1067`) and/or uploaded
(`CS:453-462`). Its encoding must equal Java's `writeObject` of that object.

- B70. Identity model. Every `String` in the doc carries an identity: `Old(NodeId)` (deserialised;
  one new node per old node), `Fresh(id)` (a new Java instance created by an edit, e.g. a dialog
  text; one node per id, possibly referenced by several events) or `Session(value)` (selection
  keys taken from the tree; one node per distinct value via `Builder::interned`, Q9). Every
  `Boolean` is `Old(NodeId)` (one non-canonical object per old node, B62) or `Canonical(bool)`
  (autoboxing → `Builder::boolean`). Every map is a WP11 `java_hash` model instance (capacity,
  threshold, insertion order) plus `None` for a Java `null` field.
- B71. `EventsDoc::from_graph(graph)` (deserialise): `Events.list` elements in order; each
  `Event`'s `name`, `description` (nullable), `addonNames`, `dlcNames`, `userconfigFolderNames`
  (`domain/repository/Event.java:13-17`). Maps are built with the `readObject` model (B63) from
  the stream entries. Then apply the side effect of `RS.getEvents()` that the admin dialog
  triggers right after the fetch (`ProgressConnectionAsAdminDialog.java:67`, `RS:866-892`,
  `service/ObjectDTOtransformer.java:383-397`): a `null` `dlcNames` or `userconfigFolderNames`
  becomes a **new empty `HashMap`** (`Event.java:43-55`). A `null` `addonNames` makes Java throw
  an NPE; Rust materialises it as an empty map too (Q10). Old events streams without the
  `dlcNames` field (pre-fork) are thereby upgraded exactly as Java does.
- B72. `EventsDoc::new()` = `new Events()` with an empty `ArrayList` (used when the remote file is
  missing and the user adds an event, `RS:983-987`).
- B73. `events()` (`RS:866-892`, WP07 B12): typed `a3s_types::Event` views in list order,
  deduplicated by exact name keeping the first. Used by UI lists and by name validation.
- B74. `add_event(name, description)` (`RS:979-991`, `ObjectDTOtransformer.java:361-376`): append
  `Event { name: Fresh, description: Fresh, addonNames/dlcNames/userconfigFolderNames: new empty
  HashMap }`. (The DTO maps from `EventAddDialog` are empty, `EventAddDialog.java:42-45`; Java's
  `transformDTO2Event` drops userconfig entries, irrelevant here.)
- B75. `rename_event(name, new_name, new_description)` (`RS:993-1010`): **every** event whose name
  equals `name` gets `name = new_name` and `description = new_description`; one `Fresh` id per
  argument, shared by all renamed events (same Java instance). Returns the number renamed.
- B76. `duplicate_event(name)` (`RS:1012-1037`): for the **first** event named `name`, append
  `Event { name: Fresh(name + " - duplicate"), description: the source's description identity
  (same instance), maps: new HashMap + putAll(source map) }` for each of the three maps
  (`putAll` model, WP11 B56; keys and values keep the source identities). Calling the source's
  `getDlcNames()`/`getUserconfigFolderNames()` materialises null maps on the source too. Returns
  whether an event was found.
- B77. `remove_event(name)` (`RS:1039-1059`): removes the **first** event named `name`.
- B78. `save_event(name, selection)` (`RS:1155-1186`): for **every** event named `name`:
  `clear()` its three maps (Java `HashMap.clear()` keeps the table length and threshold, so a
  map's capacity never shrinks in a session), then `put` each selection entry: key identity
  `Session(key)`, value `Canonical(optional)`. The put order is the iteration order of the DTO
  map the UI filled (`ui/repository/EventsPanel.java:846-861`): model it as a `HashMap` whose
  capacity is `max(hash_map_capacity(previous len of the first matching event's map),
  hash_map_capacity(selection len))`, filled by sequential puts in the caller's order (Q9).
  `EventSelection` lists are in the UI's tree order; a later duplicate key replaces the value
  (`HashMap.put`). Returns the number of events updated.
- B79. Name validation helper `validate_event_name(doc, raw, renaming)` (`EventAddDialog.java:26-40`,
  `EventRenameDialog.java:39-54`): `trim()`; empty → `Err(Empty)` (Java silently ignores OK);
  equal to an existing event name in `events()` → `Err(Duplicate)` with message `"duplicate
  name!"`. Java's rename dialog also rejects the event's **own** name (renaming only the
  description is impossible); Rust excludes `renaming` from the comparison (Q13). Descriptions are
  trimmed by the caller (`.trim()` at `:27`/`:40`).
- B80. `encode()` = Java `writeObject(events)`: root `Events` (current descriptor) → `ArrayList`
  → `Event` objects with fields `addonNames, description, dlcNames, name, userconfigFolderNames`;
  maps written with `Builder::hash_map(entries in model iteration order, buckets, threshold)`
  (WP11 B57); `null` maps as null. Strings/Booleans per B70. Gzip like `encode_a3s`. The stream
  must pass `read_with_limits(JAVA_A3S)`.
- B81. `write_local(repository_path)` (`RS:1061-1067`, `RepositoryDAO.java:290-311`):
  - path `None`/`""` → `EventsError::PathNotSet` (`"Repository main folder location is
    missing.\nPlease checkout the Repository Administation panel."`, `EventsPanel.java:594-597`);
  - path not existing → `EventsError::PathNotFound` (`"Repository main folder location: {path} does
    not exist."`, `:598-600`);
  - create `<path>/.a3s` with a single-level `create_dir` if missing (`a3sFolder.mkdir()`,

    (`A3SFilesAccessor.java:144-162`). Failures → `EventsError::Write` (`"Failed to write file:

  Success text for callers: `EVENTS_SAVED_MESSAGE = "Events informatons have been saved to the

- B82. `upload_events(doc, repository, options, ctx)` (`CS:453-462`,

- B83. `fetch_admin_metadata(conn, repository_name, &mut AdminMetadata, ctx)`

### Java quirks to preserve (wire-visible)

- Uploaded metadata = Java round trip of the local files (B60-B67): HashSet/HashMap capacities from
  `readObject`, current descriptors, per-node string/Boolean identity.
- Uploaded `serverinfo` has `compressedPboFilesOnly` from the upload setting; the local file keeps
  `false` (B33).
- Metadata order `sync, serverinfo, changelogs, autoconfig, events`; metadata after files, before
  deletions (B34, B37). Metadata re-uploaded on every run (B42).
- Expected file sets: only-zip mode uploads neither the raw file nor its `.zsync`; deletes ignore
  the only-zip setting (B1, B35). `.zsync` presence follows the **download** protocol (B2).
- Upload check tests existence only; stale same-name files are not replaced (B26). Remote orphans
  outside the remote sync are never deleted (B24).
- Events: null-map materialisation on admin fetch (B71); rename applies to all same-named events,
  duplicate/remove to the first (B75-B77); `" - duplicate"` suffix; duplicate shares description,
  keys and values with the source; `clear()` keeps map capacity; `putAll` and `readObject` capacity
  rules; canonical Booleans for saved selections vs. per-node Booleans for untouched entries
  (B70-B80).
- Typos in user texts: `"informatons"`, `"Administation"` (B81, B82).

### Java quirks that may be dropped (local-only; needs an approved deviation)

- DV1 Resume by recorded paths + local sync digest instead of Java's in-memory index slice, which
  (a) counts failed/cancelled files as done (`ACD:412-421`), (b) re-uploads everything when only
  the last file is missing (`CUP:71` uses `<`), (c) skips wrong files when the plan changed
  between attempts, (d) is not recorded at all in parallel mode (`RUP:373-375`) (Q4).
- DV2 Shared work queue and cancel-on-first-error for parallel upload (Java: static round-robin,
  earlier workers finish their share first, `CUP:171-186, 197-206`) (Q5).
- DV3 Admin check workers keep one connection each and use an upload session for FTP listing
  caching; Java opens a temporary connection per file (`ACD:367-382`) (Q6).
- DV4 Plan order = tree pre-order instead of `HashMap` order; missing files reported in plan order
  (B3, B14).
- DV5 Nested `racine` folder paths computed from the tree (B4) — **remote-layout visible**, user
  decision (Q7).
- DV6 Metadata upload not interruptible once started (B34) (Q8).
- DV7 Redundant deletes below a deleted directory are skipped (B24) (Q11).
- DV8 Null `addonNames` materialised instead of an NPE (B71) (Q10); `None` sha1 compared as
  "different" instead of an NPE (B23).
- DV9 Rename validation ignores the event being renamed (B79) (Q13).
- DV10 Extra worker connections are opened only for workers that get files (B31.3).
- DV11 Speed measured on the aggregate byte delta (B47).
- DV12 Errors are typed (`CheckError`, `UploadError`, `EventsError`) implementing
  `a3s_error::UserFacing`; Java exception class names and `DebugLogger` texts are not reproduced.

### Errors, cancellation, progress

- No retries anywhere (Java has none; reconnect = caller reruns, B40).
- Check: first `exists`/fetch error aborts; missing files are results, not errors (B11-B14).
- Upload: every error aborts the pipeline at the current phase; files already uploaded stay
  (Java same); `resume` keeps the successfully uploaded entries (B32, B44). Partial remote file
  after a failed/cancelled transfer stays (WP06 Q2); because it is not recorded in `resume`, the
  next run re-uploads it when it is in the upload list, but a partial file of a **check**-list
  entry would be seen as present (inherent to existence checks, B26).
- Cancellation: `ctx.cancel` is checked before each node/entry and inside transfers (WP06 B9);
  must take effect within 1 s on local servers. Metadata exception: B34.
- Events emitted (all WP07 `SyncEvent`s): check — `Phase(CheckingRemoteFiles)`, `Progress`,
  `FileFailed`, `Finished`; upload — `Phase(CheckingRemoteFiles | Uploading |
  DeletingRemoteFiles)`, `Progress` (check/delete), `TransferTotal`, `Transfer`, `Speed`,
  `FileStarted`, `FileDone`, `LastIndexTransferred`, `ConnectionLost`, `Finished`. Events editing
  emits nothing.

### Concurrency

- Check: ≤ `repository_check_connections()` (≤ 4) connections, shared index (B10).
- Upload: 1 connection for FTPS/WebDAV, else `parallel_upload_connections()` (1..=10, default 4)
  for FTP/SFTP (B17); directory creation is sequential on connection 0 before parallel transfers
  (B31). Each worker is a tokio task owning its `Transport`; progress counters are `AtomicU64`s;
  a single aggregator emits `Transfer`/`Speed` (B45-B47). All public futures are `Send`.
- Events: synchronous, single-threaded; `upload_events` / `fetch_admin_metadata` async.
